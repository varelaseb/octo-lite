ADR 0005: Codex thread meta-operator activation

Specifications / operator control / ADR 0005

Thread-local authority for an explicitly activated Codex app session without replacing the dedicated Fable operator path.

Status

Accepted by shaping for TUR-641, pending delivery and operator acceptance.

Context

octo-lite currently gives meta-operator authority to one dedicated persistent Fable session launched through the role resolver, Herdr, and the canonical owner record.

A user already working in a Codex app thread may want that exact thread to supervise existing Herdr streams and spawn canonical issue orchestrators without opening a second operator session.

Codex app turns expose the exact current session as CODEX_THREAD_ID, and reopening the same thread preserves that identifier while a distinct thread receives a different identifier.

A foreground app thread cannot honestly inherit the dedicated Fable session's unattended Herdr route and heartbeat without adding a bridge, daemon, polling service, or background resume that would contradict pause and resume semantics.

Normal live handoff is safest when an active Fable owner cooperates, but the human may need the exact current Codex thread to take control immediately without permitting two decision makers or treating an ordinary activation request as takeover authority.

Decision

Only an explicit user request in the current Codex app thread starts activation.

Activation loads and follows the existing canonical meta-operator contract and existing Herdr, role resolver, stream-control, and handoff surfaces; it creates no parallel role, role prose, control tree, or worker path.

The existing operator-owner.toml is the sole authority record and binds Codex-thread ownership to the exact host-provided CODEX_THREAD_ID; a caller-supplied substitute is never accepted.

Because the Codex app thread is outside a Herdr pane, activation requires one read-verified Herdr workspace ID and stores it as mode-specific routing in the existing owner record; the workspace is not a second authority claim and cannot be changed by resume or successor activation.

Initial activation may create ownership only when no owner exists, same-thread activation is an idempotent resume, and ordinary activation under a different current owner requires the existing successor-readiness and atomic owner-transfer path or the existing manual-takeover law. The live-Fable forced exception is defined separately below.

Amended by the clarified TUR-641 contract: a direct human forced-takeover instruction in the exact validated Codex thread permits one exceptional transition away from a verified active dedicated Fable owner. The path captures authoritative durable context, retires and verifies the Fable session and timer, writes a durable takeover receipt, and atomically commits the exact Codex owner under the existing owner lock.

If active-Fable eligibility, context capture, fencing, receipt evidence, compare, or atomic transfer cannot be proven, the Codex thread remains ordinary and the Fable owner record is unchanged; dead or ambiguous owners still use ADR 0001 manual takeover outside role authority.

After either lawful transfer, the Codex owner loads the complete existing meta-operator capabilities and authoritative durable state: owner and control records, transfer artifact, source-tracked work, issue and pull-request state, canonical specs and ADRs, child statuses, and applicable configuration. Raw conversation history and prose never transfer authority.

Codex-thread mode is foreground and pull-reconciled: closing the thread pauses meta-operator supervision, child orchestrators may continue, and reopening the same thread first revalidates ownership and reconciles durable stream state before any mutation.

Codex-thread activation installs no timer, daemon, polling service, app-server dependency, background thread resume, surrogate operator agent, or duplicate inbox.

A distinct Codex thread inherits no authority from conversation history or a compact handoff brief and remains ordinary until its own explicit activation and the lawful owner transition both succeed.

Missing or invalid thread identity, stale or conflicting ownership, incomplete handoff, or any write failure leaves the current session ordinary and leaves existing authority unchanged with no partial control state.

The dedicated persistent Fable initial launch, heartbeat, Herdr route, live handoff, and exact model path remain available and behaviorally unchanged as the unattended operator option.

This decision adds no cryptographic authentication claim: it relies on the direct-human role gate, host-provided current thread identifier, verified live Fable identity and fence, pre-existing owner compare, successor readiness, owner-transfer caller check, and manual dead-owner boundary. A force flag or caller-supplied reason alone is never authorization.

Consequences

A user may keep operator work in the Codex app thread they explicitly selected while reusing the established octo-lite orchestration model.

Current-thread convenience trades away unattended meta-operator liveness while the thread is closed; users who need continuous supervision retain the dedicated Fable path.

Moving authority to another Codex thread or back to Fable is a real handoff through the existing owner transition, never an implicit consequence of opening or copying a conversation.

Normal live handoff remains preferred, while the human gains a narrow, auditable forced path for a verified live Fable owner at the cost of retiring that session before the owner commit and potentially leaving a blocked Fable owner record if a later atomic transfer fails.

The exact role and model map remains the dedicated launch map; current-thread activation is an explicit host-session authority binding, not a second generated adapter or an alternative worker runtime.
