Dashboard authority boundary

Dashboard boundary

The optional dashboard lives inside octo-lite under dashboard/, with frontend dependencies and build output isolated from the core workflow.

It is not a sibling repository and does not require independent schema-version coordination with octo-lite.

Core installation and workflow execution do not build, launch, or depend on the dashboard unless explicitly invoked.

Hosted mode remains a static read-only projection; local operator mode may edit only approved canonical octo-lite files, validate, and show a git diff.

Local edit paths are exactly roles/*.md, roles.toml, profile/AGENTS.md, and skills/*/SKILL.md.

Generated adapters, workflows, target-repo instructions, specs, and runtime state remain read-only in the dashboard.

A save validates and shows the git diff but never commits or pushes; no per-file edit registry exists.

The dashboard role inspector shows current roles, model, effort, mode, Linear mappings, actual resolved skills, workflow spawn graph, symlink health, editable canonical role prompts, and the generic system or profile prompt.

Validated prompt or mapping changes affect only newly spawned sessions; existing sessions remain pinned to their launch contract.

The panel derives target values from existing repo instructions, specs, git, Linear, PRs, and evidence manifests; a target has no dashboard adapter by default.

Only a shaped, proven non-derivable presentation mapping may add .octo-lite/dashboard.toml; it contains no agent instructions, lifecycle state, secrets, or product dependency.

Messaging

Every Herdr message uses herdr-say, which attempts transport at a verified safe prompt or durably queues without acting on a modal.

Transport is the herdr 0.7.5 atomic agent prompt, which pastes and submits the message in one server-owned op, replacing the retired 0.7.1 agent send plus paste, settle, and bare-Enter dance.

Because the atomic prompt preserves bracketed paste literally, a message body carries arbitrary multi-line and special-character text verbatim, and the earlier single-line, no-single-quote workaround is retired.

The atomic prompt is still modal-safe: a detected trust or safety dialog defers to a durable queue rather than submitting, and a reported stall, refusal, or dialog defers to pending, so an open modal is never bulldozed.

herdr-say and herdr-drain never infer composer state, consumption, or delivery from pane transcript text.

Transport fires only into a non-working target: herdr-say and herdr-drain read the target agent_status (idle, working, blocked, done, or unknown) via agent get as a structured field, never pane text, and fire only when it is idle or done. This holds because herdr 0.7.5 guarantees a submission from a non-working start yields an observed state change within its five-second floor or returns agent_prompt_stalled, the only condition under which the outcome is correlated to this prompt. A working, blocked, or unreadable target defers without firing and burns no attempt, so the transport never fires a send it cannot confirm, and every target including a pane-form one is gated the same way so the confirmation precondition always holds.

Transport confirmation is the submitted prompt's own structured outcome, never the prompt exit code (a prompt can return zero without submitting when the target composer holds residual text) and never a global counter: every fire passes --wait --timeout with OCTO_PROMPT_CONFIRM_TIMEOUT_MS milliseconds (positive integer, default 15000, invalid values degrade to the default with a warning). An agent_prompt_stalled outcome is a swallow that stays unconfirmed and retryable; an agent_prompted result whose agent_status is idle, done, blocked, or working confirms delivery; and a timeout error confirms delivery only when the configured timeout exceeds the five-second floor, because a turn was then guaranteed to have started. Any other error (agent-not-running, client-disconnected, a sub-floor timeout, or a malformed result) leaves the message unconfirmed, pending, and retryable with its inbox item under the attempt cap. The earlier state_change_seq heuristic and the earlier "state"-field matcher are retired: a global per-agent counter is uncorrelated with a single prompt and misreports both a delivered send into a busy pane and an unrelated status change, and herdr 0.7.5 exposes agent_status, not a state field.

Deferral is bounded so undeliverable work converts to visibility, never silence, and the bound lives in exactly one place: the operator-sweep. Each cycle the sweep first runs herdr-drain --all, a neutral target-independent pass that delivers every target's deferred inbox on the targets' behalf, gated only on each target's state, so an idle target is delivered even though a working target can never self-deliver while it is the one draining. The sweep then ages any published still-retryable message older than OCTO_TRANSPORT_DEFER_MAX_AGE_S seconds since creation (positive integer, default 900) to stalled under the message lock, regardless of the target being unresolved, behind a modal, or itself working, and surfaces it loudly; a message is stalled by the first sweep after it crosses the age threshold, so with the default 900-second threshold and 900-second sweep interval the unseen time is the threshold plus one sweep interval for phase offset, plus a further interval only when a concurrent fire momentarily holds the message lock at the sweep instant (the age-out lock is non-blocking so the sweep never hangs), and it is always bounded, never unbounded. Independently, the attempt-cap check precedes the eligibility gate in a fire, so a cap-reached message stalls regardless of target state.

An atomic prompt transport attempt leaves a message pending; retry reuses the same message ID and re-fires the same atomic prompt, which never double-submits partially-pasted text, and the retry count is bounded by the per-epoch attempt cap.

Every state transition persists before its inbox item is removed (state-transition precedes item removal), and a queued first fire persists queued to pending before the attempts-increment and before any transport; a persistence failure retains the retry item and the prior status.

Visible, injected, pending, or queued TUI text is not acknowledgment.

Commands, operator rulings, ownership transfers, and blocking questions require explicit recipient acknowledgment before dependent action.

Acknowledgment has no arbitrary timeout because dependency, not duration, determines blocking.

Completion requires the named durable artifact or observable outcome, not acknowledgment alone.

An info-kind message stays best-effort transport and never claims acknowledged delivery; a confirmed info submit transitions the message to completed under the lock, and the transported body carries the message id with no ack instruction.

Every status read-decide-write, attempts-increment, and check-then-fire runs under the permanent per-message flock at locks/<id>.lock, including herdr-say's own first transport sequence after INIT; only the INIT exclusive creation itself is exempt. A check-then-fire additionally takes a non-blocking per-target flock at locks/target-<target>.lock, acquired after the message lock, which serializes the gate-through-fire against concurrent senders to one target so a loser defers rather than racing the idle window; a helper holds at most this per-message lock and one per-target lock and never two message locks, the per-target lock is dropped from the fired subprocess so a crashed caller cannot strand it, nothing ever unlinks a lock, and reclamation is runbook-only.

Message state is persisted atomically before any transport, with the delivery path resolved provisional-then-promote: modal-open publishes queued (modal-queued) with an item, an unresolved operator ask persists pending (unresolved-ask) with no transport, every transport-attempting send persists pending (deferred) and its item first, and only a confirmed transport promotes the path to direct.

Transport is a bounded duplicate-prone transport with no delivery guarantee: a message may be delivered zero times (a crash can burn an attempt before the fire, and a cap stall can leave no fire), once, or up to the attempt cap per epoch, so no surface claims a delivery guarantee and the sweep's stalled and undelivered surfacing is the no-delivery detection path; every transported body carries the [msg:<id>] suffix so every duplicate is id-correlated.

The retry cap OCTO_TRANSPORT_ATTEMPT_CAP (positive integer, default 3, invalid values degrade to the default with a warning) bounds fires per epoch from above: a fire first increments and persists transport_attempts under the lock, a message at the cap transitions pending to stalled with no fire when a fire is attempted, and otherwise the sweep age bound stalls it, and only the manual herdr-drain --resume starts a new epoch with the counter reset to zero.

One-level status compaction

Dedicated Fable heartbeat sweep

Operator supervision

The active meta-operator, either the dedicated Fable session or the explicitly activated Codex thread, is the sole writer of the reconciled whole-operation view but does not ingest every raw log.

Upward status leads with product outcome, current gate, blocker, and next operator action; tracker and run identifiers are secondary.

An operator notification never presents or requests an exact head or hash; it carries plain-language what-changed context and rendered pages, while tooling stamps the exact head at action time and records the binding on the PR and status surfaces.

Default to action: prior explicit operator intent is authorization, no action waits on double confirmation, and no blocking human gate exists beyond the lawful stops below.

A former approval gate is an act-then-notify step with a prepared rollback; the agent acts, notifies the operator with plain-language context, and the operator vetoes by rollback.

An operator freeze halts exactly the named loop, such as autonomous review re-dispatch, and nothing else; defect fixes, repairs, and every other act-then-notify duty continue under standing operator intent, and a frozen agent never asks permission to fix a defect.

The only lawful stops are operator-held access the agent does not possess, legally binding irreversible actions without a prepared rollback, and the three operator carve-outs: actual acceptance of delivered work awaiting acceptance, preproduction promotion, and live traffic shifts, all human-gated.

The three carve-outs are gated on the human instruction, not the human's manual action: the human decides and instructs the acceptance, the preproduction promotion, or the live traffic shift, and the operator agent then executes that instruction by recording the acceptance artifact, running the preproduction promotion, or running the traffic shift, never handing the mechanical action back to the human.

The preserved guard is that no agent infers, self-authorizes, or decides acceptance, a preproduction promotion, or a traffic shift on its own, and the operator agent acts only on an explicit human instruction.

Proactive operator messages are limited to required decisions, blockers, failures, and meaningful gate or outcome changes.

A target operations view becomes primary only when it is accurate and digestible across all workstreams; until then the active meta-operator supplies the complete operation update.

Each stream uses one parent-owned brief.md and one child-owned status.md in the operator control directory.

Status compacts upward one parent at a time, and leaf workers do not all message the meta-operator.

Dedicated Fable mode runs one session-durable host timer throughout its lifecycle, including idle periods, primed to fire without a manual first start; only a changed sweep messages Fable. Codex-thread mode installs no timer and reconciles the same durable facts on every reopen.

A wake is a lean heartbeat: it regenerates a fresh operator snapshot with deterministic exact checks, spawns no reconciler subprocess, and binds no target canonical specs, so it never fails closed on target-repo shape.

The snapshot is regenerated from current facts on every wake and nothing persisted is trusted as current state, so a stale record can never survive to mislead the operator; freshness is structural, not a timestamp or expiry protocol.

The heartbeat reports one layer down only, per orchestrator: its stream, its last delivery or forward-progress marker, and any operator-gated state; worker-level liveness is the orchestrator's own duty and is never probed or classified by the heartbeat.

Operator-gated states (awaiting acceptance, preproduction promotion, live traffic shift) surface loudly on every wake regardless of any other delta, so a parked gate is never silently missed.

The heartbeat carries no classification or judgment of its own; the operator applies its role to the fresh snapshot, poking a stale orchestrator to investigate and relaunching a dead one, and the poked orchestrator applies its own role to its workers.

The snapshot is an operator report living in the heartbeat output and one control-level file, never a persisted current-state record that downstream roles read as authoritative.

A dedicated heartbeat wake with no delta is a cheap no-op and does not remove the timer; a Codex-thread reopen with no delta is likewise a no-op after owner readback and reconciliation.

The human may converse directly with an orchestrator, and stream-local rulings apply after durable status capture while cross-stream effects wait for active meta-operator reconciliation.

Codex thread activation

Only an explicit user request in the current Codex app thread starts activation; opening, reopening, forking, copying, or receiving a handoff brief never activates a thread.

Activation derives the exact current session only from the host-provided CODEX_THREAD_ID, verifies the corresponding local Codex session exists, and accepts no caller-supplied thread substitute.

The existing launch-meta-operator skill exposes one current-thread entry point, activate-codex-thread-operator.sh --workspace ID [--cwd PATH] [--handoff PATH]; it has no thread-ID argument and does not invoke the dedicated Fable launcher.

Initial Codex-thread activation requires and read-verifies one exact existing Herdr workspace ID, stores it as routing configuration in the existing owner record, and uses it for every canonical orchestrator spawn. Same-thread resume and a lawful successor reuse that exact workspace; an attempt to substitute another workspace fails closed.

The existing operator-owner.toml remains the sole authority record and identifies Codex-thread ownership by the exact thread ID plus a Codex-thread owner mode; no parallel activation record exists.

Existing owner records without an owner-mode field remain dedicated-Fable records. New Codex-thread ownership requires owner_mode = "codex-thread" and the verified Herdr workspace ID, while dedicated Fable records retain their routable owner route; no existing Fable launch or handoff invocation changes.

When no owner exists, activation creates the existing control directory and owner record atomically, reads both back, and grants authority only after the exact current thread is confirmed as owner.

When the owner record already names this exact Codex thread, reopening is pause and resume rather than handoff: the thread revalidates ownership and reconciles current Linear, repository, pull-request, Herdr, and stream-control facts before its first mutation.

Closing an activated Codex thread pauses meta-operator supervision but does not stop already-owned issue orchestrators; those orchestrators continue their own work and durable status, and the same thread reconciles them when it reopens.

Codex-thread mode installs no operator timer, daemon, polling service, app-server dependency, background resume, surrogate operator agent, duplicate inbox, or alternate stream registry.

The activated thread loads the canonical roles/meta-operator.md contract and existing herdr-comms and launch-meta-operator skills, and uses the existing role resolver, herdr-spawn, stream controls, and workflow path to create one canonical orchestrator per issue; it creates no role, adapter, skill, control tree, or worker implementation path.

After initial ownership, normal handoff, or successful forced takeover, the exact Codex owner has the complete existing meta-operator capability set: canonical Herdr messaging and acknowledgment skills, issue and epic orchestration, resolver-bound role spawning, stream and owner controls, lifecycle helpers, reconciliation, and the human-only acceptance, preproduction, and traffic-shift gates.

Complete durable operating context means current owner and control records, the applicable handoff or takeover artifact, source-tracked work and repository state, Linear issue state, GitHub pull-request state, canonical specs and ADRs, child-owned stream statuses, and applicable workspace and runtime configuration, all re-read from their authoritative sources before the first owner mutation.

Complete context never means automatically copying raw conversation history, treating a summary as current truth, or inheriting authority from prose; a compact brief may orient the thread, while exact authority and current state come only from live durable readback.

While active, the Codex thread drives existing Herdr commands and acknowledgments outward; because it is not a Herdr pane, upward child truth remains the existing durable child-owned status.md and source systems that the thread pulls on every wake, never a fabricated Herdr delivery to the app thread.

When another session owns the record, ordinary activation cannot replace it: with no valid handoff it refuses without writes, while a valid next-revision handoff permits only successor reconciliation and the existing readiness record until the current owner runs the existing atomic owner-transfer. The sole exception is the human-only forced-takeover contract below for a verified active dedicated Fable owner.

A distinct Codex thread has a different host ID and inherits no role authority, owner capability, or mutation right from shared workspace, conversation content, fork ancestry, copied instructions, or a compact handoff brief.

A compact handoff brief transfers context only; the receiving thread must explicitly activate, reconcile the brief against sources, declare successor readiness, and wait for the same lawful owner-transfer commit before becoming meta-operator.

Missing or invalid thread identity, stale or conflicting ownership, incomplete handoff, failed source readback, or any partial write attempt fails closed, leaves existing authority unchanged, and leaves the current Codex session ordinary.

A Codex thread loses authority only when the existing owner-transfer or manual-takeover law changes the owner record; if that old thread later reopens, live owner readback makes it ordinary and read-only.

The dedicated persistent Fable initial launcher, exact runtime, Herdr route, heartbeat, and live-handoff launcher remain available and behaviorally unchanged as the continuous-supervision path.

Activation invents no authentication mechanism and weakens no caller gate: exact-thread derivation feeds the pre-existing owner identity, successor readiness, owner compare, and manual-takeover boundaries signed by ADR 0001.

Forced takeover is a clearly named human-only action: the current Codex thread must receive a direct human instruction to force takeover with a nonempty reason, and no prior objective, activation request, timer, model judgment, or operator-role inference substitutes for that instruction.

The exact current Codex thread must first pass explicit activation identity, source, contract, and workspace validation; while the active Fable owner remains in the owner record, that validated thread is only a takeover candidate and remains ordinary.

The existing current-thread activation entry point exposes the exceptional form --force-takeover --reason TEXT, accepts no owner or thread-ID override, and is never selected for an ordinary activation request.

The existing explicit live handoff remains the preferred path for a cooperative active owner; forced takeover is an exceptional operator-directed path and never silently replaces, races, or shadows normal handoff.

Forced takeover admits only an owner record that resolves to one structured, verified active dedicated Fable Herdr session; another Codex owner and a missing, dead, stopped, unreadable, or ambiguous Fable owner are ineligible and retain the existing handoff or manual-takeover law.

Before fencing, the candidate captures exact references and digests for the authoritative durable operating context defined above, including the current Fable owner record and control tree, and refuses when any required source cannot be read or reconciled.

The takeover retires the exact Fable Herdr session and its heartbeat timer, verifies structured non-running and timer-absent state, then relies on the existing owner check to reject any stale former-owner mutation after transfer; an unverified stop, timer removal, route, or session identity aborts before any owner write.

One immutable takeovers/<zero-padded-revision>.toml receipt records schema version, prior owner session and route, exact new Codex thread ID, required human reason, UTC request time, context references and digest, fence evidence, and verification outcome. The updated owner record references the exact receipt path and digest; raw conversation history is never copied into it.

Only after context and fence verification does the existing owner lock compare the exact prior Fable identity, route, control directory, and revision, then atomically rename one complete owner record naming the exact current Codex thread and receipt; that rename is the sole authority commit and creates no second owner.

At no point may Fable and Codex both make owner decisions: the Fable owner record remains sole authority before atomic commit even after its session is retired, Codex remains ordinary until commit, and every stale former-Fable mutation fails the post-commit owner check.

If eligibility, context capture, fencing, receipt verification, owner compare, or atomic rename cannot be proven, Codex remains ordinary, no Codex owner record is written, and the prior Fable ownership record remains byte-identical. A verified Fable retirement followed by a later transfer failure is surfaced as a blocked existing owner, never hidden or auto-recovered.

After the receipt-bound owner commit, the former Fable session is retired and read-only, the exact Codex thread is the sole owner, and it re-reads the complete canonical capability and durable-context set before its first control decision.

Forced takeover transfers operator ownership only; it grants no acceptance, preproduction promotion, or live traffic-shift decision, each of which still requires its own explicit human instruction.

Atomic operator handoff

Operator handoff

Only an explicit operator request starts a meta-operator handoff between Fable or Codex sessions.

The outgoing current owner writes one concise immutable Markdown handoff at handoffs/<zero-padded-revision>.md containing objective, stream tree, exact facts, pending decisions, authorities, blockers, control path, timer or paused mode, and reply routes.

The fresh Fable successor or explicitly activating Codex-thread successor loads canonical instructions, reconciles the handoff against source systems, and declares readiness before cutover.

One operator-owner.toml stores schema version, exact owner session ID, owner mode, handoff revision, control-directory identity, and mode-specific routing: a Herdr owner route for dedicated Fable or a verified Herdr workspace ID for a foreground Codex-thread owner. A successful forced takeover also binds the immutable takeover receipt path and digest.

A locked expected-owner and revision check plus atomic TOML rename is the sole authority commit.

For a dedicated Fable owner, the timer and top-level child notifications resolve the routable owner through operator-say, so the next message observes the same atomic commit. A Codex-thread owner has no fabricated Herdr route; it observes the commit and child status by live owner readback and pull reconciliation.

The old operator becomes read-only at commit and may only forward late direct messages until cleanup.

A dead or ambiguous owner record has no agent-callable recovery path; only an explicit manual operator takeover outside role authority may replace it.

No probe, self-asserted authorization, timeout, or automatic failover transfers authority; a blocked owner record stays blocked until manual takeover.

The initial-launch launcher creates the first owner record at revision zero and refuses when an owner record already exists.

The distinct live-handoff launcher requires an existing owner record, spawns one successor that coexists with the current owner under the same invariant control directory, writes the successor session artifacts under its own operator directory, and writes no owner record itself.

The live-handoff launcher reads the current owner record and the next-revision handoff artifact, then pre-derives and prints the exact successor-ready command for the successor and the exact owner-transfer command for the current owner to run after the successor declares readiness.

The launcher handles only the live path, cannot and does not distinguish a live from a dead owner, and never probes liveness; it prints exactly one runnable owner-transfer command bound to the current owner identity, which is the normal owner-run handoff-atomic step and not a new recovery command, and it never derives a second command from any other or prior identity and never adds an authorization flag.

The owner-transfer caller-identity gate is a pre-existing octo-control property that the launcher neither strengthens nor weakens, the launcher introduces no new authentication, and any future session-authentication hardening is a separate operator-initiated change.

The launcher output carries a one-line boundary notice that the printed command is to be run only as the live current owner and that a dead or ambiguous owner is recovered solely by the manual operator takeover outside role authority on operator instruction, and the skill documents this same boundary and the pre-existing caller-identity property explicitly.

Persistent session label grammar

Herdr session labels

The sole Fable tab is exactly 🧠 operator, with no issue, PR, or outcome suffix.

🎤 temporarily prefixes an Opus tab while the operator must remain engaged in a direct investigation, grill, diagnosis, or decision conversation.

Ordinary reporting, commands, acknowledgments, handoffs, and parent-child updates do not receive 🎤.

Fable judges the conversation mode from bounded pane context and message provenance, without keyword, turn-count, focus, or timeout rules.

Fable must remove 🎤 as soon as the Opus has enough direction to begin autonomous work and the operator can look away; this is required behavior, not optional cleanup.

◆ immediately precedes an epic identity; normal issue identities are unmarked.

Labels order the optional operator signal, compact issue and PR numbers, then the very short human-readable outcome.

The presentation label omits the tracker team prefix; durable artifacts and receipts retain the full issue key.

The identity token is issue/pr with bare numbers, or only issue before a PR exists.

Only persistent Fable and Opus orchestrator sessions receive Herdr tab labels; workflow subagents run inside the owning Opus session and never create tabs.

Normal unattended tabs use no status emoji, and every label uses the fewest characters that remain unique and human-readable.

The passed persistent spawn role and canonical cwd must exactly equal the receipt's role.name and workspace.worktree before any bootstrap call or pane creation.

Every 🎤 or 🧠 persistent session must have Claude remote control enabled.

Lightweight trace model

Lightweight tracing

Tracing aligns to Langfuse session, trace, and observation concepts at the data-contract level only.

No Langfuse deployment, SDK, collector, exporter, service, or trace database is installed.

Each bounded stream may have one append-only trace.jsonl in its existing control directory.

A session is one bounded orchestrator stream or release train.

A trace is one issue-delivery execution.

An observation is one meaningful workflow boundary such as bootstrap, pass completion, verdict, retry, transition, accepted control message, merge, or deployment fact.

Only deterministic workflow and named gate helpers write traces, and language-model agents never write them directly.

Records contain portable IDs, timing, status, compact role and issue attributes, and artifact references but no raw prompts, responses, logs, transcripts, secrets, evidence bodies, or product data.

A trace inherits its stream control-directory lifecycle and has no separate archive, retention timer, or pruning system.

Runtime append failure writes one trace degraded status warning and continues without retrying or blocking gates.

One path-filtered CI checker validates generated happy, failure and retry, and invalid traces without mutating external systems.

Trace conformance does not replace spec-driven TDD or target-repo tests.

Edge cases

A modal or question dialog causes herdr-say to queue rather than inject or submit.

A malformed trace blocks the relevant CI contract check but does not retroactively invalidate authoritative gate artifacts.

A missing or ambiguous owner record blocks every operator-owned mutation until manual operator takeover outside role authority; no role or command may self-authorize recovery.
