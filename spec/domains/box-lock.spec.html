Box lock

Specifications / Box lock

This spec states octo-lite's box lock: how a box's heavy jobs share its CPUs and memory, the CPUs each job runs on, the order waiting jobs run in, how a job asking for one CPU runs beside them, what a waiting job is told of its place and what it waits on, the commit a job is told it runs on, how a job takes the lock, and how a job that takes it the old way stays safe.

Which jobs a lane runs under it is in the octo-lite spec; what an agent is told of its wait is in the Command time spec; the installer links its command as it links every helper (octo-lite install).

User stories

As an operator, my box's lock runs heavy jobs side by side until the CPUs they ask for fill the box, with memory to spare and nothing for me to set, so a big box runs many of my lanes' heavy jobs at once and a small one never runs more than it fits.

As an agent running a heavy job under the box lock, such as a full test suite, I ask for the CPUs my job needs and it runs on those, so it sizes its own parallelism to them with no change of its own, and a job asking for many is never passed over by a stream of small ones.

As an agent whose heavy job a merge waits on, such as a full test suite on the head its lane asks to merge, I ask the box lock to run it as merge-path, and it runs ahead of every waiting heavy job that is not, so my lane's merge never waits behind work that can wait.

As an agent running a short or light job under the box lock, such as an install or a build of one package, I ask for one CPU and it runs at once beside the full suites and captures holding the box, so a job of minutes never waits hours behind theirs.

As an agent whose heavy job waits under the box lock, I am told my job's place in line, the jobs ahead of it, and what it waits for, the jobs holding the CPUs it needs and how long each has held them or the memory it needs, so I can judge my wait instead of waiting blind.

As an agent whose heavy job waits under the box lock while my lane's head moves, I am told the commit my job starts on, and the commit it lined up on when they differ, so I never take a run of one head for a run of another.

As an operator updating octo-lite while my lanes' heavy jobs wait under the box lock, every job waiting still runs in its turn beside the jobs asked after the update, so the update loses or stalls no lane's job.

As an agent whose heavy job runs another heavy job, such as a test suite that installs its packages, the inner job runs at once on my job's CPUs, so my job never waits on itself.

As an agent running jobs that share a resource of their project's own, such as QA captures sharing a QA database's connections, I name that resource and how many jobs it fits as I take the box lock, so no more of those jobs run at once whatever the box's size.

As an operator updating octo-lite, my box gets the lock command with the update, under its own name and the name box-heavy my agents already run, and a job that still takes the box lock the old way keeps my box safe: it runs only while no other heavy job does, and every heavy job waits for it.

Acceptance criteria

Given an agent on a box whose every CPU is held by other agents' heavy jobs under the box lock, a fixture that must be added to provide it, When the agent runs a heavy job asking for more than one CPU under the box lock, Then the agent's job runs only once enough of the others end, and the agent is told its wait apart from its run: no screen shows it.

Given an operator whose box has memory to spare, a fixture that must be added to provide it, When agents each run a heavy job under the box lock, asking for no more CPUs in all than the box has, Then all their jobs run at once, none waiting: no screen shows it.

Given an operator whose box has fewer CPUs free under the box lock than an agent's heavy job asks for, more than one, a fixture that must be added to provide it, When the agent runs that job under the box lock, Then that job waits until as many CPUs as it asks for are free, then runs: no screen shows it.

Given an operator whose box's every CPU is held under the box lock, while an agent's heavy job asking for several CPUs waits, a fixture that must be added to provide it, When other agents then run heavy jobs asking for two CPUs each, then the jobs holding the CPUs end one by one, Then the job asking for several runs before any of the two-CPU jobs: no screen shows it.

Given an operator whose box's every CPU is held by other agents' heavy jobs under the box lock, while another heavy job asking for several CPUs waits, a fixture that must be added to provide it, When an agent runs a heavy job asking for one CPU under the box lock, Then that job runs at once, on one CPU only: no screen shows it.

Given an operator whose box has some CPUs held by a heavy job under the box lock and others free, a fixture that must be added to provide it, When an agent runs a heavy job asking for one CPU under the box lock, Then that job runs at once, on a CPU no other job holds: no screen shows it.

Given an operator whose box runs a heavy job asking for one CPU on each of its CPUs under the box lock, a fixture that must be added to provide it, When an agent runs another heavy job asking for one CPU under the box lock, Then that job waits until one of the others ends, then runs: no screen shows it.

Given an operator whose box's every CPU is held by a heavy job under the box lock, while an agent's heavy job asking for every CPU waits first in line, a fixture that must be added to provide it, When other agents run heavy jobs asking for one CPU each, one starting before the last ends, then the job holding the CPUs ends, Then the job asking for every CPU runs while the one-CPU jobs still run: no screen shows it.

Given an operator whose box's every CPU is held under the box lock, while other agents' heavy jobs wait, none asking as merge-path, one of them first in line holding some of the CPUs it asked for, a fixture that must be added to provide it, When an agent runs a heavy job under the box lock asking as merge-path, then the jobs holding the CPUs end, Then the merge-path job runs before every job that was waiting: no screen shows it.

Given an operator whose box's every CPU is held under the box lock, while an agent's heavy job asking as merge-path waits, a fixture that must be added to provide it, When another agent runs a heavy job under the box lock asking as merge-path, then the jobs holding the CPUs end one by one, Then the merge-path job that asked first runs first: no screen shows it.

Given an operator whose box's every CPU is held by a heavy job running under the box lock, not asking as merge-path, a fixture that must be added to provide it, When an agent runs a heavy job under the box lock asking as merge-path, Then the running job runs to its end, and the merge-path job runs once it ends: no screen shows it.

Given an agent on a box whose every CPU is held by another agent's heavy job under the box lock, a fixture that must be added to provide it, When the agent runs a heavy job under the box lock, Then, while its job waits, the agent is told the other job's command, the folder it runs in, and how long it has held its CPUs: no screen shows it.

Given an agent whose heavy job waits under the box lock for CPUs another agent's heavy job holds, a fixture that must be added to provide it, When that job ends, then a third agent's heavy job, first in line, takes those CPUs, Then, while its job still waits, the agent is told the third job's command, the folder it runs in, and how long it has held its CPUs: no screen shows it.

Given an agent on a box whose every CPU is held by a heavy job under the box lock, while other agents' heavy jobs wait in line, one of them asking as merge-path, a fixture that must be added to provide it, When the agent runs a heavy job under the box lock, not asking as merge-path, Then, while its job waits, the agent is told its job's place in line and each job ahead of it, by command and folder, the merge-path one marked as such: no screen shows it.

Given an agent whose heavy job waits in line under the box lock behind another agent's waiting heavy job, a fixture that must be added to provide it, When the job ahead of it starts running, Then, while its job still waits, the agent is told its job's new place in line: no screen shows it.

Given an agent on a box with CPUs free under the box lock but less free memory than the lock keeps to spare, while another heavy job asking for more than one CPU runs, a fixture that must be added to provide it, When the agent runs a heavy job under the box lock, Then, while its job waits, the agent is told it waits for memory, how much it waits for, and how much the box has free: no screen shows it.

Given an agent in a folder of a Git repository, When the agent runs a heavy job there under the box lock, Then, as its job starts, the agent is told the commit the folder is at: no screen shows it.

Given an agent whose heavy job waits under the box lock in a folder of a Git repository, a fixture that must be added to provide it, When the folder moves to another commit, then the job starts, Then the agent is told the commit the job starts on and the commit it lined up on: no screen shows it.

Given an operator whose box has heavy jobs waiting under the box lock as octo-lite ran them before merge-path jobs lined up first, a fixture that must be added to provide it, When the operator updates octo-lite, then agents run heavy jobs under the box lock, some asking as merge-path, Then every one of those jobs runs, each once the CPUs it asked for are free and the jobs ahead of it have run: no screen shows it.

Given an operator whose box has CPUs free under the box lock but less free memory than the lock keeps to spare, while another heavy job asking for more than one CPU runs, a fixture that must be added to provide it, When an agent runs a heavy job under the box lock, Then that job waits until the box has that memory free again, then runs: no screen shows it.

Given an operator whose box has as much memory free as a heavy job's share of the box's memory and little more, while another heavy job holding some of its CPUs runs, a fixture that must be added to provide it, When an agent runs a heavy job under the box lock asking for no more CPUs than are free, Then the job runs at once: no screen shows it.

Given an operator whose box runs and lines up heavy jobs under the box lock as an earlier octo-lite ran them, a fixture that must be added to provide it, When the operator updates octo-lite, then agents run heavy jobs under the box lock, some asking for one CPU, Then each job running runs to its end, and every job waiting and every job asked after the update runs: no screen shows it.

Given an agent on a box with less free memory than the lock keeps to spare and no heavy job running, a fixture that must be added to provide it, When the agent runs a heavy job under the box lock, Then the job runs at once: no screen shows it.

Given an agent on a box with fewer CPUs than a heavy job asks for, a fixture that must be added to provide it, When the agent runs that job under the box lock, Then the job runs, on every CPU of the box: no screen shows it.

Given an agent on a box where octo-lite is installed, a fixture that must be added to provide it, When the agent runs under the box lock a heavy job asking for every CPU of the box that leaves a server running as it ends, then another agent runs a heavy job under the box lock, Then the second job runs at once while that server still runs: no screen shows it.

Given an agent on a box where octo-lite is installed, When the agent runs under the box lock a heavy job that fails, Then the agent's command fails as the job did, with the job's own output: no screen shows it.

Given an agent on a box where octo-lite is installed, a fixture that must be added to provide it, When the agent runs under the box lock a heavy job asking for some of the box's CPUs that sizes its workers to the CPUs it may use, Then the job runs as many workers as the CPUs it asked for, not as many as the box has: no screen shows it.

Given an agent on a box where octo-lite is installed, a fixture that must be added to provide it, When the agent runs under the box lock a heavy job asking for some of the box's CPUs that sizes its workers to the count the lock tells it, Then the job runs as many workers as the CPUs it asked for: no screen shows it.

Given an agent on a box of more CPUs than a full test suite needs, a fixture that must be added to provide it, When the agent runs a heavy job under the box lock asking for no number of CPUs, Then the job runs on as many CPUs as a full test suite needs: no screen shows it.

Given an agent whose heavy job runs under the box lock while other agents' jobs hold every other CPU of the box, a fixture that must be added to provide it, When that job runs another heavy job under the box lock, Then the inner job runs at once, on the outer job's CPUs only: no screen shows it.

Given an operator whose box has CPUs for more of a project's captures than its QA database fits, a fixture that must be added to provide it, When agents start more of that project's captures under the box lock than the database fits, each naming it and how many captures it fits, Then only as many captures run at once as the database fits, and the rest wait: no screen shows it.

Given an operator whose box runs as many of a project's captures as its QA database fits, each under the box lock naming it, while another capture waits for the database and CPUs are still free, a fixture that must be added to provide it, When an agent runs another heavy job under the box lock, naming no resource, Then that job runs at once: no screen shows it.

Given an operator on a box where octo-lite is installed, When the operator runs the installer, then runs it again, Then the second run links the lock command, under its own name and as box-heavy, among every item and exits successfully, proven by a unit test: no screen shows it.

Given an agent on a box where octo-lite is installed, while another agent's heavy job holds some CPUs under the box lock, a fixture that must be added to provide it, When the agent runs a heavy job with box-heavy, asking for more CPUs than are free, Then the job waits as one under the box lock would, then runs on the CPUs it asked for: no screen shows it.

Given an operator whose box holds a box-heavy command of its own where octo-lite links box-heavy, a fixture that must be added to provide it, When the operator verifies the install, Then the check fails on one line naming that box-heavy with the step that fixes it, moving it aside then installing again, proven by a unit test: no screen shows it.

Given an operator whose box runs an agent's heavy job under the box lock with CPUs still free, a fixture that must be added to provide it, When a job takes the box lock the old way, locking the box lock's file whole, Then that job waits until no heavy job runs, then runs: no screen shows it.

Given an operator whose box has CPUs free under the box lock, while a job holds the box lock the old way, locking its file whole, a fixture that must be added to provide it, When an agent runs a heavy job under the box lock, Then the agent's job waits until the old job ends, then runs: no screen shows it.

Modular boundaries

The box lock owns admitting a box's heavy jobs by the CPUs each asks for and the memory the box has free, merge-path jobs first and one-CPU jobs beside the rest, the CPUs each job runs on, what a waiting job is told of its place and its wait, the commit a job is told it starts on, the cap on jobs naming a resource of their own, running a heavy job inside another at once, and keeping a job that locks its file whole safe. The caller-facing seam is octo-lite's lock command, octo-lite-lock, also named box-heavy, with its --cores, --cap, and --merge asks, the wait line it prints on the job's output, the line naming a waiting job's place and what it waits on, the line naming the commit a job starts on, and the count of CPUs it tells the job in BOX_HEAVY_CORES; and the box lock's file, heavy.lock in octo-lite's box state directory, which a job of the old way locks whole. Direction is external-provider: the box lock depends on the operating system's file locks, CPU affinity, and memory count, and on Git to read a folder's commit; octo-lite's skills and roles, and a peer's jobs such as annotateanything's release watch and a box's own install helpers, depend on it, and it depends on no role or skill. Observable scope: when each heavy job runs and in what order, the CPUs it may use, the count it is told, its wait line, its place and what it is told it waits on, and the commit it is told it starts on.

CPUs and memory

The box lock admits a box's heavy jobs, jobs that end by themselves and load the box, such as a full test suite, a QA capture, a build, an install, or a recording, by the CPUs each asks for: jobs run side by side while the CPUs they hold fit the box, and a job waits while too few are free, save a job asking for one CPU, which runs beside them (one CPU). It is box-wide, in octo-lite's state directory for the box, never a Herdr session's, so every lane and session on a box shares it.

Each of the box's CPUs is held by at most one heavy job at a time, save a one-CPU job beside it, and a job asks for as many as it needs: octo-lite-lock --cores N CMD. A job that asks for no number gets 4, what a full test suite needs, and a job never gets more CPUs than the box has, so on a smaller box it gets every CPU. The lock counts the box's own CPUs each time a job takes it, so no box has a number to set, and a box grown or shrunk counts anew.

A job runs on the CPUs it holds only. So the CPUs a job may use, as nproc and a test runner sizing its workers read them, are the CPUs it asked for, and a job sizes its parallelism to them with no change of its own. The lock also tells the job how many it holds in BOX_HEAVY_CORES, for a runner that takes a worker count instead of reading its CPUs, as node --test --test-concurrency does.

Jobs asking for more than one CPU that wait for them line up in the order they asked, behind every merge-path job waiting: the first in line takes CPUs as they come free and keeps them until it holds all it asked for, and the jobs behind it wait their turn. So a job asking for many CPUs is never passed over by a stream of jobs asking for few.

A job asking for one CPU, as a short or light job does, such as an install, a build of one package, or a check of one file, never lines up: each CPU is held by at most one job asking for more and also by at most one asking for one, so a one-CPU job runs at once, on a CPU no job holds when one is free, else on one beside the job holding it. It waits only while every CPU of the box runs a one-CPU job, or for memory, so it never waits behind a full suite or a capture holding the box. It takes no CPU a job in line waits for, so a job asking for many still runs as soon as the jobs holding its CPUs end, the one-CPU jobs beside it running on.

A job a merge waits on asks to run as merge-path: octo-lite-lock --merge CMD. It lines up ahead of every waiting job that is not merge-path, and behind the merge-path jobs that asked before it, in the order they asked. A job first in line that is not merge-path gives back the CPUs it holds as soon as a merge-path job waits, keeping its place ahead of the jobs behind it, so a merge-path job never waits on CPUs held for a job not yet running. A job already running is never stopped: a merge-path job waits for it to end like any other. Which jobs ask as merge-path is the caller's, as the octo-lite spec states for a lane's.

A box updates octo-lite while jobs wait under the box lock: each job that lined up before the update still runs, in the order it lined up, perhaps ahead of a merge-path job asked after the update. No two jobs ever hold the box's CPUs between them while neither can run, so the update stalls no job, and a job running as the box updates runs to its end.

The first in line, and a one-CPU job, also waits while the box has less memory free than the job's share of it, as many parts of the box's memory as the CPUs it asks for are of the box's CPUs, so the jobs already running and the agents around them keep memory to spare. The first in line runs with less free when the only other heavy jobs running are one-CPU jobs, and a one-CPU job when no other heavy job runs, so a box of little memory still runs its heavy jobs one at a time, and the one-CPU jobs beside them never hold a job of many CPUs from its turn. Taking CPUs never reads the box's load: the heavy jobs' own load would otherwise hold CPUs empty.

Taking the lock

A job takes the box lock by running under octo-lite's lock command, as octo-lite-lock [--cores N] CMD. The command waits for its CPUs, prints its wait on a line of its own, the line flock --verbose prints, names the commit the job starts on (commit), runs the job on those CPUs, lets them go when the job ends, and ends as the job ended, its output the job's own.

A job that cannot run at once says where it stands and what it waits on: on a line of its own on its output, before its wait line, it names its place in line and each job ahead of it, by its command and the folder it runs in, marking each merge-path one, and each other job holding CPUs under the box lock, by its command and folder, and how long it has held them. Holding every CPU it asks for, it says instead that it waits for memory, how much, and how much the box has free; waiting on a named resource, it says it waits for that resource. It says so again each time its place, the jobs it waits on, or what it waits for change, so an agent whose job waits long knows where its job stands and whose jobs it waits behind, and can judge how long it may still wait. That line is never the wait line, so an agent's wait is still told apart from its run as the Command time spec states.

As a job starts, the command names, on a line of its own on its output, the commit of the folder the job runs in, when that folder is in a Git repository, and, when the folder was at another commit as the job lined up, that commit too. So a job reads the head it runs as it starts, and never runs a head other than the one it lined up on without saying so; a job that checks out a commit of its own names that one itself. Reading the commit writes nothing in the folder, and the lock writes only its own files in octo-lite's box state directory, so it never writes a checkout's files (a lane never writes a main checkout's files).

The command holds the CPUs itself and never hands them to the job, so a server or browser the job leaves running holds no CPU once the job ends.

A heavy job run under the lock by a job already under it, such as an install a test suite runs, runs at once on the outer job's CPUs, on as many of them as it asks for, so a job never waits on CPUs its own outer job holds.

A job that shares a resource of its project's own with jobs like it, such as a QA capture sharing its QA database's connections, names that resource and how many such jobs it fits: octo-lite-lock --cap RESOURCE=N CMD. It waits until fewer than that many jobs naming that resource run before it lines up for CPUs, so while it waits it holds no CPU and no place in line, and jobs naming no resource take the CPUs it leaves. The project's AGENTS.md names the resource, its number, and the CPUs the job asks for beside the job's command.

The lock command is also on PATH as box-heavy, so box-heavy [--cores N] CMD takes the same box lock, and a box's helpers and briefs that run their heavy jobs that way count among every other heavy job on the box. A box that already holds a box-heavy of its own keeps it: the installer leaves it and reports it, as it does every occupied path, and the install check fails naming it with its fix, moving it aside then installing again, so the box's heavy jobs come under the one lock once the operator does.

A job of the old way locks the box lock's file whole, as flock does by default, and holds the whole box. The lock command keeps a shared hold on that file while each of its jobs runs, so a job of the old way waits until no heavy job runs, and every heavy job waits until it ends. Old and new callers are safe together in any order, so a box updates octo-lite, and a peer moves its jobs to the lock command, whenever each is ready.
