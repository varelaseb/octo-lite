Box lock

Specifications / Box lock

This spec states octo-lite's box lock: how many heavy jobs it runs at once on a box, the share of the machine each job gets, how a job takes it, and how a job that takes it the old way stays safe.

Which jobs a lane runs under it is in the octo-lite spec; what an agent is told of its wait is in the Command time spec; the installer links its command as it links every helper (octo-lite install).

User stories

As an operator, my box's lock runs as many heavy jobs at once as my machine fits, counted from its CPUs and memory with nothing for me to set, so a bigger box runs more of my lanes' heavy jobs at once and a small one never runs more than it fits.

As an agent running a heavy job under the box lock, such as a full test suite, my job gets its share of the machine as the CPUs it may use, so it sizes its own parallelism to its share with no change of its own.

As an agent running jobs that share a resource of their project's own, such as QA captures sharing a QA database's connections, I name that resource and how many jobs it fits as I take the box lock, so no more of those jobs run at once whatever the box's size.

As an operator updating octo-lite, my box gets the lock command with the update, and a job that still takes the box lock the old way keeps my box safe: it runs only while no other heavy job does, and every heavy job waits for it.

Acceptance criteria

Given an agent on a box whose CPUs and memory fit one heavy job, while another agent's heavy job holds the box lock, a fixture that must be added to provide it, When the agent runs a heavy job under the box lock, Then the agent's job runs only once the other ends, and the agent is told its wait apart from its run: no screen shows it.

Given an operator whose box's CPUs and memory fit several heavy jobs, a fixture that must be added to provide it, When as many agents as the box has slots each run a heavy job under the box lock, Then all their jobs run at once, none waiting: no screen shows it.

Given an operator whose box's every slot holds a heavy job, a fixture that must be added to provide it, When one more agent runs a heavy job under the box lock, Then that job waits until one of the others ends, then runs: no screen shows it.

Given an operator whose box has CPUs for more heavy jobs than its memory fits, a fixture that must be added to provide it, When as many agents as its CPUs fit each run a heavy job under the box lock, Then only as many jobs run at once as its memory fits, and the rest wait: no screen shows it.

Given an operator whose box has memory for more heavy jobs than its CPUs fit, a fixture that must be added to provide it, When as many agents as its memory fits each run a heavy job under the box lock, Then only as many jobs run at once as its CPUs fit, and the rest wait: no screen shows it.

Given an agent on a box with fewer CPUs and less memory than one slot holds, a fixture that must be added to provide it, When the agent runs a heavy job under the box lock, Then the job runs, with every CPU of the box its share: no screen shows it.

Given an agent on a box whose CPUs and memory fit one heavy job, a fixture that must be added to provide it, When the agent runs under the box lock a heavy job that leaves a server running as it ends, then another agent runs a heavy job under the box lock, Then the second job runs at once while that server still runs: no screen shows it.

Given an agent on a box where octo-lite is installed, When the agent runs under the box lock a heavy job that fails, Then the agent's command fails as the job did, with the job's own output: no screen shows it.

Given an agent on a box of several slots, a fixture that must be added to provide it, When the agent runs under the box lock a heavy job that sizes its workers to the CPUs it may use, Then the job runs as many workers as its slot's share of the box's CPUs, not as many as the box has: no screen shows it.

Given an operator whose box has more slots than a project's QA database fits captures, a fixture that must be added to provide it, When agents start more of that project's captures under the box lock than the database fits, each naming it and how many captures it fits, Then only as many captures run at once as the database fits, and the rest wait: no screen shows it.

Given an operator whose box runs as many of a project's captures as its QA database fits, each under the box lock naming it, with slots still free, a fixture that must be added to provide it, When an agent runs another heavy job under the box lock, naming no resource, Then that job runs at once: no screen shows it.

Given an operator on a box where octo-lite is installed, When the operator runs the installer, then runs it again, Then the second run links the lock command among every item and exits successfully, proven by a unit test: no screen shows it.

Given an operator whose box has several slots, one holding an agent's heavy job, a fixture that must be added to provide it, When a job takes the box lock the old way, locking the box lock's file whole, Then that job waits until no heavy job runs, then runs: no screen shows it.

Given an operator whose box has several slots, while a job holds the box lock the old way, locking its file whole, a fixture that must be added to provide it, When an agent runs a heavy job under the box lock, Then the agent's job waits until the old job ends, then runs: no screen shows it.

Modular boundaries

The box lock owns admitting a box's heavy jobs into slots counted from the box, each job's share of the box's CPUs, the cap on jobs naming a resource of their own, and keeping a job that locks its file whole safe. The caller-facing seam is octo-lite's lock command, octo-lite-lock, with the wait line it prints on the job's output, and the box lock's file, heavy.lock in octo-lite's box state directory, which a job of the old way locks whole. Direction is external-provider: the box lock depends on the operating system's file locks and CPU affinity; octo-lite's skills and roles, and a peer's jobs such as annotateanything's release watch, depend on it, and it depends on no role or skill. Observable scope: when each heavy job runs, the CPUs it may use, and its wait line.

Slots and shares

The box lock admits a box's heavy jobs, jobs that end by themselves and load the box, such as a full test suite, a QA capture, a build, or a recording, into its slots: one job per slot, and a job waits while every slot is taken. It is box-wide, in octo-lite's state directory for the box, never a Herdr session's, so every lane and session on a box shares it.

A box has one slot per 4 CPUs and one per 6 GB of memory, whichever gives fewer, and never fewer than one. The lock counts the box's own CPUs and memory each time a job takes it, so no box has a number to set, and a box grown or shrunk counts anew. A slot holds what one heavy job needs, such as a full test suite's parallel browsers, with memory to spare for the agents around it.

A job's share is its slot's part of the box's CPUs, the box's CPUs split evenly among its slots, and the job runs on those CPUs only. So the CPUs a job may use, as nproc and a test runner sizing its workers read them, are its share, and a job sizes its parallelism to it with no change of its own. A box of one slot gives its one job every CPU.

Every slot is alike, so no job asks for a share of its own size and no caller carries a number for the box. Taking a slot never reads the box's load or free memory: the slots count what the box has, and the heavy jobs' own load would otherwise hold slots empty.

Taking the lock

A job takes the box lock by running under octo-lite's lock command, as octo-lite-lock CMD. The command waits for a free slot, prints its wait on a line of its own, the line flock --verbose prints, runs the job on its slot's share, lets the slot go when the job ends, and ends as the job ended, its output the job's own.

The command holds the slot itself and never hands it to the job, so a server or browser the job leaves running holds no slot once the job ends.

A job that shares a resource of its project's own with jobs like it, such as a QA capture sharing its QA database's connections, names that resource and how many such jobs it fits: octo-lite-lock --cap RESOURCE=N CMD. It waits until fewer than that many jobs naming that resource run, and still takes a slot, so jobs naming no resource take the slots it leaves. The project's AGENTS.md names the resource and its number beside the job's command.

A job of the old way locks the box lock's file whole, as flock does by default, and holds the whole box. The lock command keeps a shared hold on that file while each of its jobs runs, so a job of the old way waits until no heavy job runs, and every heavy job waits until it ends. Old and new callers are safe together in any order, so a box updates octo-lite, and a peer moves its jobs to the lock command, whenever each is ready.
