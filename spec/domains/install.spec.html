octo-lite install

Specifications / octo-lite install

This spec states how octo-lite links its skills, roles, and helpers, the third-party skills it pins, and a project's declared skills, into a box's agent profiles, registers its command-time hook with each agent CLI, and keeps them current after a pull.

What the linked roles and skills do is in the octo-lite spec; what the command-time hook tells an agent is in the Command time spec.

User stories

As an operator, I can install or verify octo-lite with one script that names every problem it finds with the step that fixes it, any tool on my box that shows a peer's setup can run that verification from what octo-lite publishes, and after any pull of its clone the box comes current with no hand step, through the after-pull step octo-lite publishes or else the next agent spawn; on a box with an existing setup, the installer adopts compatible links, skips what belongs to someone else, and never overwrites them or fails on them.

As an operator whose project keeps its own skills, such as its design rules, every implementer on my lanes loads the ones its ticket needs from my live main checkout, and onboarding warns me when a skill link points at a stale clone.

As an operator, the third-party skills octo-lite's agents use install with octo-lite at the upstream commit it pins, with none of their files in octo-lite's repository, and a box that cannot fetch one still installs everything else, then fails the install naming that skill and how to fix it, so no lane works without it unnoticed.

As an operator, installing octo-lite registers its command-time hook with every agent CLI on my box, Claude Code and Codex, beside the hooks other tools registered, and undoing the install removes only octo-lite's.

Modular boundaries

The installer owns linking octo-lite's skills, roles, and helpers, the third-party skills it pins, and a project's declared skills, into the agent profiles, and registering octo-lite's command-time hook in each agent CLI's hook settings. The caller-facing seam is the installer's flags, the after-pull step it publishes, which hosts and herdr-spawn run, the setup check it publishes, which hosts run, and the target AGENTS.md Repo skills: line. Direction is external-provider: the installer reads the target's declaration from its checkout and fetches each pinned third-party skill from its upstream repository; the target names no octo-lite path, and octo-lite names no project skill. Observable scope: links in the profile skill, agent, and helper directories, octo-lite's entries in each agent CLI's hook settings, the onboarding file it publishes, and the installer's printed report and exit status.

Install

scripts/install-octo-lite symlinks skills/* into the Claude, Codex, and shared ~/.agents skill directories, agents/*.md into the Claude and Codex agent directories, the agents directory as each profile's octo-lite/adapters, and executable helpers into ~/.local/bin; --check verifies the install as the check states.

When a target path is already occupied, the installer classifies it: a symlink resolving into a different clone of this repository (matched by git remote get-url origin) is adopted and reported; any other existing file or symlink is skipped and reported; the installer never overwrites, never fails on an occupied path, and continues with the remaining items. A dangling link whose target was inside this repository is pruned. Any other dangling link, including one at a path the installer links, belongs to someone else: it is reported and left untouched, never replaced.

A target repository declares its own skills in its root AGENTS.md with one line, Repo skills: followed by comma-separated repository-relative paths to skill directories. install-octo-lite --project <checkout> reads that line from the project's live main checkout, the clone the operator keeps on main, and links each declared skill from that checkout under its directory name, into the same skill directories as octo-lite's own skills. A declared skill's existing link that resolves anywhere but that checkout is stale: the installer warns, naming the link and where it points, leaves it untouched, and continues, and a verifying run, --check or --after-pull, names it as a problem whose fix is to move the link aside, then install again. It never links a project skill from another clone and never repairs a link.

Each peer links only what it owns (toolchain ownership); Spec Chat's installer links Spec Chat's own skills. octo-lite pins two third-party skills by Skillfile into agents/skills, each at an exact upstream commit: tdd, committed with its one patch (ADR 0006), and Stageshow, never committed, since its upstream folder carries artwork under its owners' terms that octo-lite does not redistribute. The installer fetches Stageshow at its pinned commit, with the filming dependencies its lockfile at that commit names, and links it as it links tdd, so a pin change reaches the box through the after-pull step. When the fetch fails, the installer reports Stageshow as not installed, naming why and the step that fixes it, links every other item, and exits non-zero. When skillfile is missing, that step is the one command that installs skillfile, which the README also gives. An agent then works without Stageshow and says its checks did not run, as with a missing peer (alone), and its lane owner reports it as a problem of the box.

octo-lite's round video recorder installs with the browser driver it pins and a browser for it, fetched as the installer fetches Stageshow's filming dependencies and reported as Stageshow is when the fetch fails, so the recorder runs on a box without Stageshow. Its dependencies install at this clone's root, where the recorder finds them, and never inside a skill's folder, which holds only the files octo-lite tracks there, so each install and after-pull run passes as the first did. A run removes any dependencies it finds inside the recorder's folder.

--check reads the box and changes nothing, and reports every problem it finds, never stopping at the first: a link missing or wrong, a leftover link of an earlier install, a pinned skill not installed, missing hook entries, a version floor not met, or a stale project skill link. Each problem is one line of its error output naming the problem and the step that fixes it, and the check exits non-zero when it finds any. Every line of its error output is such a problem: what it reports that is not a problem, such as another owner's link it leaves untouched, goes to its standard output, so a host can show each error line as one of octo-lite's setup problems.

--check also checks version floors: for each tool octo-lite uses at runtime (git, herdr, jq, gh, node, python3, and at least one of claude or codex), it prints the version found to its standard output when the tool meets its floor, and otherwise names the tool as a problem, missing or too old (found version vs minimum), whose fix is to get it from its upgrade source. The installer never upgrades anything without the user's explicit consent.

With --onboard, the installer asks once whether agents may push, open pull requests, and file issues, and keeps the answers in octo-lite's one onboarding file, $XDG_STATE_HOME/octo-lite/onboarding.toml, beside its published onboarding status, done once answers are kept. Kept answers are not asked again; deleting that file asks afresh.

The installer publishes its after-pull step in the same onboarding file: after_pull, a list of arguments a host runs with no shell, after fast-forwarding this clone, to bring the box onto the pulled code. It runs install-octo-lite --after-pull from this clone with the prefix and project the installer last ran with. --after-pull installs as a plain run does, asking nothing, then verifies as --check does, and exits non-zero when the verification fails, its error output naming each failed check with the step that fixes it. Every run rewrites after_pull, so the step a host runs next is the pulled clone's, and records beside it the commit of this clone it ran at. herdr-spawn, through which octo-lite-start also starts each lane owner, first runs the published after-pull step when this clone's commit differs from that record, so a pull no host followed with the step still reaches the box at the next spawn. A failing step goes to the spawn's error output and the spawn goes on; since the step's own run records the commit, it runs once per move of the clone, and its failure is printed once. Pulling, installing, and spawning are safe in any order: a spawn before the step runs it, and one after finds nothing to do.

The installer publishes its setup check in the same onboarding file: check, a list of arguments a host runs with no shell to learn octo-lite's setup problems (peer seams O10). It runs install-octo-lite --check from this clone with the prefix and project the installer last ran with, so it verifies the box that run set up. Every run but --check rewrites it beside after_pull. It runs this clone's own script, so a pull changes what it checks at once. Pulling, installing, and checking are safe in any order: a check run before the after-pull step names what that step fixes, and one run after it does not.

The installer registers octo-lite's command-time hook in each agent CLI's hook settings, Claude Code's .claude/settings.json and Codex's .codex/hooks.json under the prefix, as the entries that hook needs. These files hold the operator's and other tools' settings, and each CLI reads hooks only from them, so here alone the installer edits a file instead of linking one: it adds only its own entries, changes no other entry or setting, and leaves a file it cannot read as settings, or cannot write, untouched, reporting it. Each entry runs the hook through its link in ~/.local/bin, so a pull changes what the hook does without changing the entry. --check fails, naming the settings file, when octo-lite's entries are missing from it, and --undo removes only octo-lite's entries. Codex runs a new or changed hook only once the operator trusts it in Codex: the installer's report says so, and the installer never records that trust for the operator. Installing, pulling, and trusting the hook in Codex are safe in any order: until each one an agent CLI needs has happened, its agents are not told command times, and no command is affected.

On a box with Herdr, the installer registers herdr-wake as Spec Chat's wake provider; a provider file someone else wrote is kept unchanged, and --undo leaves the registration in place because Spec Chat's review service depends on it. herdr-wake, and the herdr-say it runs, reach Herdr on their caller's search path or in Herdr's install directory, ~/.local/bin, so a review service started by any launcher (a box user service, a timed job, a shell) wakes owners as a pane does. A failed check or send writes a one-line reason to its error output: Herdr not found, naming the path searched; the owner pane not found in its session; Herdr not answering; or Herdr's own error.
