octo-lite current state

Specifications / octo-lite

This spec describes only what exists in this repository today.

It replaces the operating-model, delivery-lifecycle, role-runtime, and operator-control domain specs, which described deleted apparatus; they remain in git history.

User stories

As an operator, I can shape an idea into an accepted spec, then have it filed as a ticket graph and delivered on one PR ready for my review.

As an operator, I can install or verify octo-lite with one script, and after any pull of its clone the after-pull step octo-lite publishes keeps the box current with no hand step; on a box with an existing setup, the installer adopts compatible links, skips what belongs to someone else, and never overwrites or fails.

As the fleet operator, I append one line per prod, note to the human, lane I start, and issue I file to my own hand-off file, so the floor shows what I did beside each lane's own lines.

As a lane owner, I append one line per hand-off moment to my lane's hand-off file, so the floor shows what happened on my lane, and each ask I make of the human is one gate line naming where to answer and the one action, so the human's pages show the ask without the operator relaying it.

As an operator, I see each lane in its own Herdr space named after the lane, holding its owner and every worker of that lane, while I work in a space of my own; closing a finished lane's space leaves nothing of it running.

As an operator, every QA criterion that failed on my lane reaches my merge ask ended by the lane's one finish rule: fixed and recaptured when it is about the change, proven by a named test when no browser can show it, or, outside the change, filed with its consequence or dropped, beside what the judge saw and the head it judged, so no failure ships as a note and no wrong triage reaches my merge.

As an operator, a lane never stalls silently: every worker delivers its result to its lane owner as a message, the owner, whatever agent runs it, wakes as soon as a worker it waits on stops or its tab closes, resumes one whose turn died on an API error, recovers any other worker that ended without reporting, and tells me, an owner whose turn dies while I await its reply is resumed the same way, a worker whose owner cannot be reached sends its result to me and stops instead of retrying without end, and every report reaches me as a message.

As an operator on a box short of memory, I can park an idle lane owner or worker so it holds no memory while it waits, and a later message to it resumes it under the same name with its conversation intact.

As an operator running several Herdr sessions on one box, I work in each without coordinating: an agent in one session never sees, wakes, or tears down a lane of another.

As an operator whose project keeps its own skills, such as its design rules, every implementer on my lanes loads the ones its ticket needs from my live main checkout, and onboarding warns me when a skill link points at a stale clone.

As an operator whose project declares a changelog or worklog convention, every change my lanes ship that the convention logs carries its entry in the same PR, in my project's format, and my merge ask names that entry or why there is none, so the log never falls behind what shipped.

As an operator, a wording-only correction to a spec I accepted rides on my original acceptance, while any change to what the spec makes the system do comes back to me for acceptance.

As an operator, work that passes the cases at hand without following the rule the spec states never reaches my merge ask.

As an operator, every agent takes a repo-wide rule to mean one thing, an every-feature criterion its home spec marks as a project rule so Jev checks it at every shaping, and a cross-cutting decision a lane settles becomes one, so I never explain the term again.

As an operator, review never buries what matters: a note about the change is fixed in its PR, a privacy, data loss, money, or security consequence blocks the merge until it is fixed, a note about old code outside the change becomes a tracker ticket when the lane closes only when it names a real consequence, at most five per PR, labeled by its kind, and every other note is dropped.

As an operator, a PR that review keeps sending back comes to me with its open blockers after two fix rounds, instead of looping.

As an operator, every merge ask opens with a few plain lines anyone can read, saying what changes, what review found that matters, and the QA call, and everything else waits in the PR.

As an operator, a merge ask means my whole issue is done in that one PR, built, tested, and QA-captured, with nothing in scope left to a later slice, a follow-up ticket, a phase 2, or an open question, and anything that truly cannot be done before merge reaches me with why before it is cut.

As an operator, a screen my lane changes ships looking like the mockup I accepted with its spec: the implementer builds it from that mockup, review compares the built screen with it, and QA shows them side by side, so I never find the drift after merge.

As an operator, I can fire a repo health pass on a repository whenever I choose, and its few real findings on architecture and cleanliness arrive as ranked tickets, never a report, that I triage and fire off like bugs.

As an operator, a message or spec review hand-off whose agent's turn dies at once on an API rate limit is sent again until the agent processes it, and a sender whose message never got through is told so, so no agent sits idle on a message it never read.

Acceptance criteria

Given an operator with an accepted spec in a lane, When the lane owner runs implement-spec to completion and the operator opens the lane's PR, Then that one PR shows every ticket's work, a clear review, and passing required checks, ready for the operator's review.

Given an operator on a box where some install paths are already occupied by someone else's files, When the operator runs the installer, Then it reports each occupied path as skipped, links every other item, and exits successfully, proven by a unit test: no screen shows it.

Given an operator whose installed octo-lite clone was fast-forwarded to a commit that ships a new helper, a fixture that must be added to provide it, When a host runs the after-pull step octo-lite publishes, Then the new helper is linked and the step exits successfully, proven by a unit test: no screen shows it.

Given an operator whose installed octo-lite clone was fast-forwarded and whose box holds a leftover the check rejects, needs an induced failure: a leftover link the check rejects, When a host runs the after-pull step octo-lite publishes, Then the step exits non-zero and the last line of its error output names the failed check, proven by a unit test: no screen shows it.

Given the fleet operator and a live lane owner, When the fleet operator sends the lane owner a prod, Then the operator's hand-off file gains one prod line naming the lane, proven by a unit test: no screen shows it.

Given the fleet operator woken by an action event that asks it to start a lane, When it starts that lane, Then the operator's hand-off file gains one start line naming the lane's issue and the event, proven by a unit test: no screen shows it.

Given the fleet operator woken by an action event that asks it to file an issue, When it files that issue, Then the operator's hand-off file gains one filed line naming the new issue and the event, proven by a unit test: no screen shows it.

Given a lane owner that sends the human a review link for a choice to answer, When it sends the link, Then the lane's hand-off file gains one gate line asked, naming the gate answer, the verb Answer, and that link, proven by a unit test: no screen shows it.

Given a lane owner whose merge ask goes out with QA skipped, When it sends the merge ask, Then the lane's hand-off file gains one gate line asked, naming the gate merge, the verb Accept and merge, the PR as its link, and its QA call in words, proven by a unit test: no screen shows it.

Given a lane owner whose lane served a report under review that is removed before merge, When the owner closes the lane, Then before its review rows are removed the lane's PR body holds a permalink to that report at the last commit holding it, proven by a unit test: no screen shows it.

Given a lane owner waiting on an implementer, When the owner consumes the implementer's result, Then the lane's hand-off file gains one attempt line naming the worker's role, ticket, pane, and commit, proven by a unit test: no screen shows it.

Given a lane owner whose worker's result is consumed, When the owner closes that worker's tab with what the close prints appended to the lane's hand-off file, Then the lane's hand-off file gains one closed line naming that tab, proven by a unit test: no screen shows it.

Given a lane owner with an idle worker, When the owner parks that worker with both what the park prints and its error output appended to the lane's hand-off file, Then the lane's hand-off file gains one closed line and one parked line and nothing else, proven by a unit test: no screen shows it.

Given an operator in its own Herdr space, When the operator launches a lane, Then Herdr shows a new space named after the lane holding only that lane's owner, and the operator's space is unchanged.

Given a lane owner delivering a spec, When it spawns implementer, integrator, and reviewer workers, Then Herdr shows each worker in the lane's space under a name that carries its role and its ticket, and no worker in any other space.

Given a lane with live workers in its space, When a reader reads the lane's workers, Then it gets each worker's pane, role, and ticket from the lane's space and the workers' names, with no worker list in the lane record, proven by a unit test: no screen shows it.

Given a finished lane whose space still holds its owner and a worker that started a background process, When the operator closes the lane's space, Then Herdr lists neither the space nor any of the lane's agents.

Given a finished lane whose space still holds its owner and a worker that started a background process, When the operator closes the lane's space, Then none of the lane's agents or their background processes is still running, proven by a unit test: no screen shows it.

Given a finished lane whose owner was started in a space shared with the operator and other lanes, When its owner reports the lane closed, Then the owner's report names its owner tab to close and no space.

Given a finished lane whose owner was started in a space shared with the operator and other lanes, When its owner reports the lane closed and the operator closes the tab the report names, Then Herdr no longer shows that tab and still shows the shared space, the operator, and every other lane in it running.

Given an operator installing octo-lite with no kept consent answers, When the operator runs the installer with onboarding and answers whether agents may push, open pull requests, and file issues, Then the answers are kept in octo-lite's published onboarding status, which reads done, proven by a unit test: no screen shows it.

Given an operator whose kept consent answer refuses push, When the lane owner runs implement-spec to completion, Then the owner's report to the operator names the local integration head that holds every ticket's work.

Given an operator whose kept consent answer refuses push, When the lane owner runs implement-spec to completion, Then no lane branch is pushed, proven by a unit test: no screen shows it.

Given an operator on a box with Herdr, When the operator installs octo-lite and later uninstalls it, Then octo-lite is registered as Spec Chat's wake provider after install and stays registered after uninstall, proven by a unit test: no screen shows it.

Given an operator on a box with Herdr whose review service was started with a search path that lacks Herdr's directory, a fixture that must be added to provide it, When a spec review hand-off for a live lane owner's row is sent, Then the hand-off reaches that owner, proven by a unit test: no screen shows it.

Given an operator on a box whose wake provider cannot find Herdr, needs an induced failure: Herdr is missing, When a spec review hand-off for a lane owner's row is sent, Then the wake check fails and its error output names Herdr as not found, proven by a unit test: no screen shows it.

Given an operator with a lane owner whose pane is gone and was never parked, When a spec review hand-off for that owner's row is sent, Then the wake check fails and its error output names the owner pane as not found in its session, proven by a unit test: no screen shows it.

Given a lane owner started with an operating model file, When it spawns a worker and that worker spawns a child, Then the worker and the child each start with that operating model and the caller's home, proven by a unit test: no screen shows it.

Given a lane owner whose next worker's agent fails to start, needs an induced failure: agent start fails, When the lane owner spawns that worker and the spawn ends, Then the spawn reports the failure and Herdr shows no tab left for that worker.

Given an operator with a lane whose owner fails to start, needs an induced failure: owner agent start fails, When the operator launches the lane with octo-lite-start and it ends, Then it reports the failure and Herdr shows no space for the lane.

Given a lane owner and a worker waiting on an interactive dialog, When the owner sends the worker a message with herdr-say, Then nothing is typed into the dialog and the message is reported not delivered, to retry once the worker frees, proven by a unit test: no screen shows it.

Given a lane owner and a Claude worker whose replies an API rate limit refuses until it clears, needs an induced failure: the API refuses the worker's replies for a while, When the owner sends the worker a message with herdr-say and the rate limit clears, Then the worker's pane shows its reply to that message.

Given a lane owner and a Claude worker whose replies an API rate limit refuses until it clears, needs an induced failure: the API refuses the worker's replies for a while, When the owner sends the worker a message with herdr-say and the send ends, Then the send is reported delivered only after the worker replied to the message, which no screen shows.

Given a lane owner and a Claude worker whose replies an API rate limit keeps refusing, needs an induced failure: the API refuses every reply, When the owner sends the worker a message with herdr-say and the send ends, Then the send is reported not processed, naming the rate limit, which no screen shows.

Given an operator with a spec under review whose lane owner's replies an API rate limit refuses until it clears, needs an induced failure: the API refuses the owner's replies for a while, When the operator sends a spec review hand-off from the review page and the rate limit clears, Then the owner's pane shows it processing that hand-off.

Given a lane owner and a Claude worker that is working, needs an induced failure: the API refuses the worker's reply to the next message it takes in until the limit clears, When the owner sends the worker a message with herdr-say and the rate limit clears, Then the worker's pane shows its reply to that message.

Given a lane owner and a Claude worker that is working, needs an induced failure: the API refuses the next reply of the worker's running turn and no later one, When the owner sends the worker a message with herdr-say and the send ends, Then the worker's pane shows that message once, with the worker's reply to it.

Given a lane owner and a Claude worker that is working, needs an induced failure: the worker's Claude exits before it takes in the next message, When the owner sends the worker a message with herdr-say and the send ends, Then the send is reported failed, naming the worker and that the message was never taken in, which no screen shows.

Given a lane owner and a Claude worker whose replies an API rate limit refuses until it clears, needs an induced failure: the API refuses the worker's replies for a while, When the owner sends the worker a message with herdr-say, then parks the worker while that send waits, then the rate limit clears, Then Herdr shows the worker in the lane's space under the same name, its pane showing its reply to that message.

Given an operator with a spec under review whose lane owner's replies an API rate limit keeps refusing, needs an induced failure: the API refuses every reply, When the operator sends a spec review hand-off from the review page and the send ends, Then the operator's pane shows a message that the hand-off was not processed, naming the owner and the rate limit.

Given an operator with a ticket whose behavior the spec on main already states, When the lane owner runs implement-spec on that ticket to completion and the operator opens the lane's PR, Then no spec review was asked, and that one PR shows the ticket's work, a clear review, and passing required checks, ready for the operator's review.

Given an operator with a lane's spec under review, When the operator accepts the spec in chat with the fleet operator, the fleet operator records it, and the operator opens the lane's PR, Then the PR shows a receipt comment from the fleet operator, not from the lane owner.

Given an operator who told the fleet operator in chat that a lane's spec changes are accepted ahead of review, When the lane's owner sends the fleet operator its spec's review link, then the operator opens the lane's PR, Then the PR shows a receipt comment from the fleet operator quoting the operator's words and naming that spec at the commit the owner sent.

Given an operator with a lane whose two specs are under review, When the operator accepts both in chat with the fleet operator, the fleet operator records it, and the operator opens the lane's PR, Then the receipt comment names each spec by its full repository path, each followed by at and the accepted commit.

Given an operator with a lane's spec under review, When the operator accepts the spec in chat with the fleet operator and the fleet operator records it, Then the box holds no record of that acceptance besides the PR's receipt comment, proven by a unit test: no screen shows it.

Given a lane owner whose PR merged and whose lane kept notes, When it closes the lane, Then the lanes directory no longer lists the lane or its notes, and its archive holds the lane's record, hand-off log, and notes unchanged, proven by a unit test: no screen shows it.

Given a lane owner delivering a ticket graph, When a ticket moves state, Then the lane record holds no ticket entry, proven by a unit test: no screen shows it.

Given an operator with a lane whose review, validation, and QA are done, When the owner sends the lane's merge ask, Then the operator's message opens with three to five plain lines, with no file path, anchor, or command, saying what changes for the user, what review found that matters, and the QA call, followed by the PR's link.

Given a lane whose integration head leaves part of its accepted spec unbuilt, When a fresh code reviewer judges the head, Then its verdict to the owner lists a blocker naming the unbuilt part.

Given an operator with a lane whose merge ask has gone out, When the operator opens the lane's PR, Then its body leaves no work its issue or accepted spec holds to a later slice, a follow-up ticket, a phase 2, or an open TBD.

Given a lane whose accepted spec holds a measurement only production gives, When the owner has done every other step its merge ask needs, Then the operator gets a message from the owner naming that measurement and why it cannot be done before merge, asking whether to cut it, in place of a merge ask.

Given a lane whose integration head works but copies one new check into four of the handlers it adds, When a fresh code reviewer judges the head, Then its verdict to the owner lists a duplication note naming the four copies, marked to fix in this PR.

Given a lane whose integration head works and calls an old function, outside its change, whose check is copied into four handlers, When a fresh code reviewer judges the head, Then its verdict to the owner lists a duplication note naming the copies and what a fix to only one of them would break, not marked to fix in this PR.

Given a lane owner whose QA capture could not test a criterion of the lane's change because its outcome shows only in a native tooltip, When the operator reads the lane's merge ask, Then the merge ask lists that criterion as proven by the test it names.

Given a lane whose accepted spec's mockup set draws a screen a ticket changes, When the owner starts that ticket's implementer and the operator opens the implementer's pane, Then its brief names that screen's mockup at the spec's accepted commit.

Given a lane whose integration head shows a changed screen with a section its accepted mockup does not draw, When a fresh code reviewer judges the head, Then its verdict to the owner lists a blocker naming that section.

Given an operator with a lane that changes a screen its accepted mockup draws, When the lane's merge ask has gone out and the operator opens that screen at the width of one of its mockup's frames, Then the screen shows what that frame shows, in its layout and proportions, with only sample values differing.

Given an operator in a repository whose specs are Spec Chat's, with a ticket that changes a screen its spec's mockup set does not draw, When the lane owner runs implement-spec on that ticket, Then the operator gets the spec's review link, with a mockup of that screen, before any implementer starts.

Given an open health ticket and a lane whose PR lists a review note naming the same issue with a consequence, When the PR merges and the lane's owner closes the lane, then the operator opens that health ticket, Then it shows a comment linking the lane's PR as a new source of that issue, filed in place of a second ticket.

Given the fleet operator with two merged PRs whose notes name the same issue with a consequence that no open health ticket names, When the fleet operator files both PRs' notes in one batch, then opens the tracker's open health tickets, Then they show one ticket for that issue, naming both PRs as its sources.

Given the fleet operator with a merged PR whose notes name two issues with a consequence, one of which the target's main no longer has, When the fleet operator files that PR's notes, then opens the tracker's open health tickets, Then they show a ticket for the issue main still has and none for the one main no longer has.

Given the fleet operator with an open health ticket whose issue the target's main no longer has, When the fleet operator fires a health pass on that repository, then opens that ticket, Then the ticket shows done, with a comment naming the main commit it was checked at and why the issue is gone.

Given the fleet operator and a repository whose code holds an issue with a consequence that no open health ticket names, a fixture that must be added to provide it, When the fleet operator fires a health pass on that repository, then opens the tracker's open health tickets, Then they show a new ticket for that issue with its category label, its consequence, and a priority from its rank.

Given the fleet operator and a repository holding more real issues than one pass files, a fixture that must be added to provide it, When the fleet operator fires a health pass on that repository, then opens the tracker's open health tickets, Then they show new tickets only for the pass's highest-ranked issues, as many as one pass files.

Given the human and a fleet operator, When the human asks the fleet operator for a health pass on a repository and the pass ends, Then the fleet operator's reply names each ticket the pass filed, commented on, or closed, by its key, and carries no finding outside those tickets.

Modular boundaries

The Herdr wrappers (octo-lite-start, herdr-spawn, herdr-say, herdr-await, herdr-close) own placing lane agents in spaces, messaging them, waiting on them, parking and resuming them, and closing tabs and spaces. The caller-facing seam is each wrapper's arguments, its printed pane= and workspace= lines, and the message herdr-await sends its caller when a wait ends. Direction is external-provider: the wrappers depend on the Herdr CLI, the session key Herdr exports, and Claude's own per-process session file, with --resume for parking and the session's transcript for confirming a Claude agent processed a message; roles and skills depend on the wrappers, never the reverse. Observable scope: Herdr spaces, tabs, and agents, and process exit.

octo-lite owns and publishes the lane record and hand-off formats; roles write them at the named moments. The caller-facing seam is the files in each Herdr session's state directory, plus the lane's Herdr space and spawn names for workers. Direction is self-contained: readers such as a board depend on the format and locate a session's files from the Herdr session key; octo-lite names no reader. Observable scope: file contents and the lane's space membership.

Role contracts and skills own shaping, delivery, review, and gates. The caller-facing seam is the role contracts in agents/ and the skills in skills/. Direction is downward: roles use the wrappers, Herdr's own agent state, and the lane record format; external providers are Linear, GitHub, Spec Chat, whose mockup set is each changed screen's accepted target, and annotateanything's QA capture program, whose rules (when QA runs, outcomes, owner triage) live in its jev-capture spec under QA rules, while the finish rule that ends each failure, like each review note, is octo-lite's. Observable scope: tickets, the PR, and the lane record.

The installer owns linking octo-lite's skills, roles, and helpers, and a project's declared skills, into the agent profiles. The caller-facing seam is the installer's flags and the target AGENTS.md Repo skills: line. Direction is external-provider: the installer reads the target's declaration from its checkout; the target names no octo-lite path, and octo-lite names no project skill. Observable scope: links in the profile skill, agent, and helper directories, and the installer's printed report.

The filing rule and the repo-health skill own turning review notes and health findings into health tickets. The caller-facing seam is the health tickets in the box's tracker, with their Health label and priority, and the tagged notes in each PR body. Direction is external-provider: the filer depends on the tracker the lanes already file in, and octo-lite names no reader of health tickets. Observable scope: health tickets, their labels, priorities, comments, and states, and the pass's one message.

Install

scripts/install-octo-lite symlinks skills/* into the Claude, Codex, and shared ~/.agents skill directories, agents/*.md into the Claude and Codex agent directories, the agents directory as each profile's octo-lite/adapters, and executable helpers into ~/.local/bin; --check verifies the links.

When a target path is already occupied, the installer classifies it: a symlink resolving into a different clone of this repository (matched by git remote get-url origin) is adopted and reported; any other existing file or symlink is skipped and reported; the installer never overwrites, never fails on an occupied path, and continues with the remaining items. A dangling link whose target was inside this repository is pruned as a known legacy path. Any other dangling link, including one at a path the installer links, belongs to someone else: it is reported and left untouched, never replaced.

A target repository declares its own skills in its root AGENTS.md with one line, Repo skills: followed by comma-separated repository-relative paths to skill directories. install-octo-lite --project <checkout> reads that line from the project's live main checkout, the clone the operator keeps on main, and links each declared skill from that checkout under its directory name, into the same skill directories as octo-lite's own skills. A declared skill's existing link that resolves anywhere but that checkout is stale: with or without --check, the installer warns, naming the link and where it points, leaves it untouched, and continues. It never links a project skill from another clone and never repairs a link.

Each peer links only what it owns (toolchain ownership); Spec Chat's installer links Spec Chat's own skills. Only the third-party tdd skill is pinned, by Skillfile into agents/skills (ADR 0002).

--check also reports version floors: for each tool octo-lite uses at runtime (git, herdr, jq, gh, node, python3, and at least one of claude or codex), it prints ok, missing, or too old (found version vs minimum) with the upgrade source. The installer never upgrades anything without the user's explicit consent.

With --onboard, the installer asks once whether agents may push, open pull requests, and file issues, and keeps the answers in octo-lite's one onboarding file, $XDG_STATE_HOME/octo-lite/onboarding.toml, beside its published onboarding status, done once answers are kept. Kept answers are not asked again; deleting that file asks afresh.

The installer publishes its after-pull step in the same onboarding file: after_pull, a list of arguments a host runs with no shell, after fast-forwarding this clone, to bring the box onto the pulled code. It runs install-octo-lite --after-pull from this clone with the prefix and project the installer last ran with. --after-pull installs as a plain run does, asking nothing, then verifies as --check does, and exits non-zero, the last line of its error output naming the first failed check, when the verification fails. Every run rewrites after_pull, so the step a host runs next is the pulled clone's.

On a box with Herdr, the installer registers herdr-wake as Spec Chat's wake provider; a provider file someone else wrote is kept unchanged, and --undo leaves the registration in place because Spec Chat's review service depends on it. herdr-wake, and the herdr-say it runs, reach Herdr on their caller's search path or in Herdr's install directory, ~/.local/bin, so a review service started by any launcher (a box user service, a timed job, a shell) wakes owners as a pane does. A failed check or send writes a one-line reason to its error output: Herdr not found, naming the path searched; the owner pane not found in its session; Herdr not answering; or Herdr's own error.

Roles

agents/*.md are the hand-written role contracts: orchestrator, implementer, integrator, code-reviewer, and meta-operator; none pins a model.

Every spawned worker with a role contract (implementer, integrator, or code-reviewer) loads it: Claude through --agent ROLE, Codex as developer instructions, and pi as an appended system prompt, via herdr-spawn --role ROLE.

An implementer loads by name each skill the target AGENTS.md declares under Repo skills: that bears on its ticket, beside the octo-lite skills its contract lists; a declared skill outranks an octo-lite skill on the same subject, as a project's UI skill outranks frontend-design. Its report to the owner names the declared skills it loaded; a declared skill it needs that does not resolve is a missing environment, reported as a blocker.

An implementer implements the general rule the spec states, so every case the rule covers holds, not only the criterion, fixture, label, or evaluation case at hand. A code reviewer blocks code keyed to the instances at hand, such as a named criterion, fixture, label, or evaluation case, in place of the rule the spec states: it passes the check while the behavior stays wrong.

A repo-wide rule is an every-feature acceptance criterion its home spec marks as a project rule, Spec Chat's data-project-rule mark, which Jev checks against every spec at shaping and each review hand-off names under rules checked. A line in a target AGENTS.md only points implementers at such a criterion; a rule stated only there, or in spec prose outside a criterion, is not yet a repo-wide rule. When a lane's spec settles a cross-cutting decision, such as an identity key, an exposure contract, or a single source, that no project-rule criterion states, its owner names the decision and its home spec in its review hand-off. The fleet operator then asks a lane on that home spec, this lane when the home is its own spec, for a criterion marked as a project rule that states the decision, so Jev enforces it from the next shaping, and that spec's acceptance is recorded by the PR receipt like any other. The set stays small: a decision earns a rule only if a later feature could plausibly break it. The meta-operator and orchestrator contracts and the implement-spec skill state this where they ask, shape, and brief.

Waiting agents hold no memory: the fleet operator parks a lane owner idle at a human gate, on another lane, or held back for load, and resumes it by sending it the wake message, or when load allows, one owner at a time as memory frees. A parked owner is resumed, never relaunched fresh; only an owner with no parked line and no live pane is relaunched. A lane owner parks a worker it would otherwise keep idle through a long wait, such as a human gate or another lane, and messages it to resume; a worker whose result is consumed is closed, not parked. A resumed owner first sets its lane record's owner to its new pane, then acts on the message that resumed it. The meta-operator and orchestrator contracts and the herdr-comms and implement-spec skills state these moves where they wait or close.

Every lane owner, and every operator-like pane, runs under a /goal for its lane outcome, so goal check-ins keep invoking it while work is unfinished. Every report goes to its recipient through herdr-say; text left in the sender's own pane is not reported. A worker's last step sends its result to the owner pane its brief names, and only a herdr-say exit 0 confirms the send; a send that does not exit 0 is sent again, a bounded number of times, unless it exits 69, which its sender never sends again. When no send to the owner is confirmed, the worker sends its result once to the operator's pane, read from the session's operator.toml, and stops whether or not that send is confirmed, so an unreachable owner never holds a worker in a send loop. The operator brings the lane's owner back as parking states and forwards it the result. Each time the owner sets a worker to work, by its brief, a resume, or a repair, it sends that work with herdr-await, which starts one wait on that worker by name; the wait ends when the worker is idle, done, stuck on an interactive prompt, or gone, and its end wakes the owner with a message, whatever agent runs the owner, so a worker that stops wakes an owner idle on it, with no timer. A send that is not confirmed ends the wait at once, and its message says so. An owner relaunched from a park starts one such wait, sending nothing, on each worker it still waits on, since its earlier waits ended with its process. When a wait on a worker it still waits on ends, the owner reads the worker's pane. A finished result there is consumed as the worker's report. A turn that ended on an API error is resumed by sending the same worker continue the same way, which sends again while a rate limit lasts; a resume that is not confirmed leaves the worker blocked. A worker still at its task, such as one waiting on its own background command, gets a new wait that ends only once the worker has changed state since the stop the owner read and has stopped again, so an owner never wakes again on a worker that has not moved, and a worker that works and stops before that wait starts still ends it. Otherwise the worker is blocked, and the owner recovers or respawns it. Except for a worker still at its task, the owner tells the operator which worker ended without reporting and what it did. The fleet operator does the same for a lane owner it sends work it awaits a reply to: it sends that work with herdr-await, with the same rules when the wait ends, and never a standing wait on every owner. The herdr-comms skill states these rules once, as its wait recipe, and the orchestrator and meta-operator contracts and the implement-spec skill link that recipe where they send work.

Before a heavy job, such as a full test suite, a QA capture, or a build, the owner checks box load; when load is high it runs one heavy job at a time.

At lane close the owner first files its PR's notes by the filing rule and adds to its PR body a permalink to each report the lane kept outside main, at the last commit holding it, since a report never merges and its review row goes at teardown, then removes the lane's review rows before removing any worktree, closes its workers, removes its own /tmp scratch, and archives the lane record last, per the archive moment.

The fleet operator acts on annotateanything's Bitbucket plugin watch: a red report starts a fix lane.

An optional operating model given to herdr-spawn reaches the agent at start and passes to every agent it spawns, and each spawn forwards the caller's HOME.

Delivery

spec-chat-shape produces the reviewed canonical spec, committed locally, and never publishes; it sends the review link as soon as the draft validates and is hosted, with no agent browser pass. In parallel, never before that link, the orchestrator files the Linear issue, pushes, and opens the draft PR, only as consent allows. A processed human spec acceptance (page action Accept spec, formerly called Finish review) permits implementation dispatch under the reviewed canonical spec.

Operator briefs carry the human decisions already made and exact source pointers (files and anchors), so shaping reads only those before drafting.

implement-spec first files the dependency-linked ticket graph from the accepted spec, runs its pre-dispatch mechanical checks, then fills the ready ticket frontier with implementer workers, each in its own worktree; repository tests run in delivery, never during shaping.

A screen a ticket changes is built and reviewed from its accepted mockup: that screen's file in its spec's mockup set as it stands at the spec's accepted commit (accepted set), the one mockup format octo-lite reads. The owner's briefs to the ticket's implementer and to the code reviewer name those mockups at that commit. The implementer builds the screen from them, its sections in their order, its copy, and its styles, lifting the mockup's markup and design tokens where the product's stack allows and mapping them onto the product's own components and tokens where it does not, and checks each changed screen against each frame at that frame's width. The code reviewer renders each changed screen at each frame's width and compares it with the frame: a visible difference, judged as QA judges one (outcome checks), is a blocker naming the difference, and QA then judges the same screens beside the same mockups. A screen that must differ from its mockup is a spec change: the mockup changes and goes back to spec review before the build differs. In a repository whose specs are Spec Chat's, a ticket that changes a screen its spec's mockup set does not draw goes back to shaping, which draws it, before any implementer starts, whatever picture of the screen exists elsewhere.

An optional exploration worker writes its notes only in the lane's notes directory, lanes/<lane record name>-notes/ beside the lane record, and the tickets it serves link them; the owner archives that directory with the record at lane close.

A target repository declares its changelog convention, such as a worklog or release notes, in its instruction files: its AGENTS.md or CLAUDE.md, or a rule file one of them points to, stating the file, the format, and which changes get an entry, by default every change its users can see; octo-lite names no changelog path or format. Before filing the ticket graph, the lane owner reads that convention, and when the lane makes a change it logs, gives the entry to one ticket, whose brief names the convention's file, so its implementer writes the entry in the same PR. The PR body carries one line, Changelog: <entry title>, or Changelog: none: <reason> when the lane makes no change the convention logs or the repository declares no convention, and the merge ask carries that line. The code-reviewer reads the convention and blocks a change it logs that has no entry, or an entry off its format, since the log otherwise falls behind what ships.

One integrator at a time integrates finished commits onto the single integration branch and PR.

A code-reviewer judges the integration head. Its blockers are broken behavior, clearly over-built work, in-scope work left undone (whole issue), a changed screen that differs visibly from its accepted mockup (mockup), and any privacy, data loss, money, or security consequence, however small to fix. Blockers send the PR back for at most two fix rounds: the first a fix batch, the second a fresh step-back pass toward the simplest design that meets the spec, each followed by a review of its fix delta. Blockers the review after the second round still finds go from the owner to the operator, with each blocker named, in place of a third round; review clear and required checks passing end the rounds sooner. Its non-blocking notes end as the finish rule states, tagged as review notes state.

A merge ask covers its whole issue: every ticket and the accepted spec are built, tested, and QA-captured in its one PR, and no in-scope work is left to a later slice, a follow-up ticket, a phase 2, or an open TBD. Only separate work, such as a new feature, gets its own ticket, and the PR body says why it is separate. One finish rule ends everything the lane finds before its merge ask, a review note and a failed QA criterion alike, by the first row below that fits; the review note, QA triage, and filing rules link it and never restate it.

Linear stays truthful: a ticket is Done only once integrated, and pushed when consent allows, and a merged accepted PR completes the worklane.

Pushing, opening pull requests, and filing issues follow the kept consent answers alone when present, overriding any instruction; when absent, target instructions decide. Without push consent the lane stays on local branches and ends at a local integration head.

A ticket whose behavior the spec on main already states needs no shaping or new acceptance: that spec's commit on main is the acceptance receipt, the ticket is a one-node graph, and one implementer, one integrator, and one reviewer still run.

Before the merge ask, the owner triages every criterion the lane's QA capture shows failed, from its evidence, whatever owner the bundle names, by annotateanything's owner triage rule, the one home of QA rules, and each failure then ends as the finish rule states. A code fault's repair is a ticket under the spec issue, worked by a fresh implementer and integrated like any ticket; a fault in the QA program itself is fixed through annotateanything's own lane. A reshaped criterion keeps its meaning; one whose meaning changes is a spec change and goes back to spec review. Every verdict the merge ask lists was judged at the merge ask's head: a failure carried from an older head is recaptured at that head before it is triaged. The merge ask lists, in its PR body, each failed criterion with the bundle's evidence_state, its decision_source and the head it was judged at, its triage, its cause or reason, and its outcome. A failure whose evidence_state is complete, where the judge reached the state and saw the product not match the criterion, is listed as a code fault unless a specific capture cause is named, such as a wrong fixture, a wrong page reached, or the criterion's shape.

The owner sends one merge ask to the operator once every step it needs is done. It opens with a plain summary of three to five lines that a reader who is not an engineer follows: what changes for the user, what review found that matters, the PR body's changelog line, and the QA call, then the PR's link. The summary names no file path, anchor, command, or evidence field. Everything else the merge ask carries, such as the failed QA criteria with their evidence, validation, review notes, and wording-only commits, is in the PR body, which the link opens. The orchestrator contract holds the template.

Repo health

A health ticket is a tracker ticket for one real architecture or cleanliness issue in a repository, in the box's tracker, the one its lanes already file tickets in; no other store holds health issues. It names the issue, its consequence, where in the repository it lives, and each source that raised it: a PR or a health pass. It carries one label of the tracker's Health label group, naming its category, and a priority from its rank. It is filed unassigned, with no parent, in a state not yet started, so it waits in the tracker beside the bugs a human triages and fires off.

The categories are architecture, cleanliness, naming, duplication, test, and docs. A consequence is what the issue will cost or break, named concretely, such as the next change to acceptance must edit four copies. A note or finding that names no consequence stays history and never becomes a ticket.

A code reviewer gives every non-blocking note the end the finish rule gives it, tagged with its category, so a note never buries what matters: a note to fix is marked to fix in this PR, and a note to file names its consequence. The owner has every note marked to fix fixed in the PR before the merge ask, in a fix batch already running or one batch of its own, which is no fix round and needs no review of its own, and lists every note to file in the PR body, tagged as given, so the PR keeps it and a filer reads it there. At lane close, after the PR merges and before teardown, the agent closing the lane, its owner or the fleet operator, files the PR's notes by the filing rule.

One filing rule turns notes and findings into health tickets: one PR's notes at lane close, many PRs' notes in one batch, and a health pass's findings. The filer first reads every open health ticket and the target's current main, then gives each note or finding the first disposition below that fits. Two notes name the same issue when one fix would remove both, whatever their wording. A filing checks only its own notes and findings against main; only the health pass checks the open health tickets themselves against main. Each source, one PR or one pass, files at most five new tickets, highest rank first; the rest stay history, and a later pass that still finds one files it then.

A health issue's rank is its consequence: high when it will cause wrong behavior or block a change, medium when it makes the next change in that area cost more, such as a duplicate, a dead store, or a misleading name, and low when it costs only reading time. The rank is the ticket's tracker priority, so it orders health tickets among the tracker's other work.

The repo-health skill is the repo health pass, fired by hand by the fleet operator, at its own call or when the human asks for one, and never on a timer. The fleet operator starts one fresh agent for it on the target's main checkout; that agent changes no repository file and writes only health tickets. It reads the target's instructions, its specs' modular boundaries, the open health tickets, and the code, and looks across the whole repository for architecture, cleanliness, best-practice, and trimming issues, a deletion first wherever one would do. It checks every open health ticket against main, closing each one main fixed as done, with a comment naming the main commit it was checked at and why the issue is gone, and files its findings by the filing rule. Its result is the tickets, never a report: its one message to the fleet operator names each ticket it filed, commented on, or closed, by key, and the fleet operator relays that list to the human who asked.

The code-reviewer, orchestrator, and meta-operator contracts and the implement-spec skill state these moves where they review, list notes, close a lane, and fire the pass.

Herdr session

The Herdr session is octo-lite's isolation unit: an agent sees, messages, parks, wakes, and tears down only the lanes of its own session, and sessions need no coordination. Every wrapper and role acts in its caller's session and reads and writes only that session's state.

The session key is the Herdr session name, read from Herdr alone. Herdr exports the name as HERDR_SESSION to every pane of a named session, and a pane of the default session has none, so a process reads the key as ${HERDR_SESSION:-default}. The Herdr CLI selects its own session by the same variable, so a process outside any pane that sets it acts in that session, and one that does not acts in the default session; a set HERDR_SOCKET_PATH pins the session over it. Herdr limits session names to ASCII letters, digits, ., _, and -, so the key is safe as a path component. Any repository that scopes its own state by Herdr session reads this same key from Herdr directly.

octo-lite's state directory for a session is $XDG_STATE_HOME/octo-lite/ for the key default, and $XDG_STATE_HOME/octo-lite/sessions/<key>/ for any other key, as Herdr keeps its own named sessions under sessions/<name>. It holds the session's lanes/ directory, with each lane's record, hand-off log, and notes, and the archive, and the session's operator.toml and operator.handoffs.jsonl; the store table gives each its lifetime. octo-lite-state prints the caller's session state directory, and roles and wrappers locate lane and operator files through it. The onboarding file belongs to the box, not a session, and stays at $XDG_STATE_HOME/octo-lite/onboarding.toml.

Herdr pane, tab, and space ids are unique only within a session; another session repeats them. Every id in a session's state is read and acted on in that session: a message, park, wake, or close by id reaches only the caller's session, unless a wake owner names its own session (wake owner), and a close stops only processes of the caller's session. No record key names a session.

The one box-wide service, Spec Chat's review service, runs in one session and wakes owners of every session, so a review row's owner names its session: a lane registers with --owner "${HERDR_SESSION:-default}/$HERDR_PANE_ID", for example second/wP:p2. herdr-wake checks and wakes a <session>/<pane> owner in that session, with that session's state for its parked lines and its operator's pane, and a bare pane in its caller's session; it never searches sessions for a pane, since ids repeat across them.

Stores

Every file or folder octo-lite writes on the box, each with one lifetime and the writer that ends it. A Log is appended to, or rewritten only by its writers, and is never deleted automatically; it ends in its lane's archive or by the box owner's hand. octo-lite keeps no Cache, and no store keeps a copy of a fact another store owns: an acceptance is the PR receipt, a ticket's state is the tracker's, and a lane's workers are its Herdr space. A path no row names is no store of octo-lite: a lane's worktrees are the target repository's, in Git, and the owner removes them and its own /tmp scratch at lane close; the installer's links are its install, and the wake provider file it registers is Spec Chat's provider configuration (wake provider).

Transport

herdr-spawn opens one tab and agent at an explicit worktree, and herdr-say delivers a message, returning only once Herdr observes a state change and, for a Claude agent, once the agent has processed it. A target blocked on interactive input gets nothing typed, and herdr-say exits 75, not delivered, so the caller retries once it frees.

A Claude agent whose turn dies at once on an API rate limit, as it does while Claude's credentials are cooling down, has not processed the message, though Herdr saw it work and then go idle. herdr-say reads this from the transcript of the target pane's Claude session: the message is processed unless the agent's first reply to it is an API rate-limit error. The agent's reply to a message is the first reply after the transcript record that carries that message: Herdr does not track turns, so for an agent already working when the message lands, the state change Herdr sees and the reply after it belong to the running turn. Such a message waits behind the running turn until that turn takes it in or ends, and herdr-say waits for the message's own reply however long that turn runs. A message still not taken in once that turn has ended or the agent's Claude has exited never reached the agent: herdr-say exits failed, and its error output names the target and that the message was never taken in. When that reply is a rate-limit error, herdr-say sends the same message again, each wait longer than the last because the error names no time it clears, until a send is processed and it exits 0. Every send reaches its target as the first one does, so a target parked during a wait is resumed as a parked target is, and the message goes to the resumed agent. When its bound passes and every send's turn died on a rate limit, it exits 69, not processed, and its error output names the target, the number of sends, and the last API error. Exit 69 already holds every re-send, so its sender never sends that message again. The retry lives in that one send, so no inbox, timer, or service holds the message, and its re-sends can take up to about two hours, besides any running turn a message waits behind; a caller bounded tighter does not hold it in the foreground. A Codex or pi agent keeps no Claude transcript, so the state change alone confirms a message to it.

A pane's Claude session is found by one lookup that herdr-say and herdr-close --park share: Claude's own per-process session records whose live process carries that pane's HERDR_PANE_ID, and the caller's HERDR_SESSION, in its environment. A process counts whether or not Herdr reports it as the pane's foreground, since a spare Claude process claimed into the pane is that pane's live agent. A record counts only when the process start time it records matches the live process at its pid, so a record an ended Claude left at a pid since reused is never read. Of the records that count, the pane's session is the one whose transcript holds the pane's latest reply.

herdr-wake send runs herdr-say in a session of its own and returns its exit when it ends within Spec Chat's send bound: 0 sent, 75 deferred, and any other failed, with its one-line reason. A send that outlives that bound, resuming a parked owner or waiting out a rate limit, keeps delivering after Spec Chat counts it sent, so a spec review hand-off whose first wake dies on a rate limit still reaches its owner. When such a send then ends deferred or failed, Spec Chat no longer waits on it, so herdr-wake sends its one-line reason, naming the owner, once to the operator's pane, read from the operator.toml of the owner's session.

herdr-spawn starts the agent bare, and its brief follows by herdr-say.

A failed spawn closes the tab it created, and a failed octo-lite-start closes the lane space it created, so no orphan is left. herdr-spawn answers the agent's startup trust dialog at the pane, confirming only once the affirmative row is selected and never a refusal; a dialog that does not clear fails the spawn closed.

There is no acknowledgement step, inbox, or drain.

Each lane, one PR, runs in its own Herdr space labelled with the lane name; the fleet operator runs in a space of its own. octo-lite-start creates the lane space and starts the owner in it, leaving no other tab there, and prints its workspace= beside pane=. The owner spawns every worker of its lane into its own space, $HERDR_WORKSPACE_ID. A lane's own space is the one octo-lite-start created for it; a lane started in a space shared with the operator or other lanes has no space of its own.

A lane's space id is the prefix of its owner pane id, w7 in "w7:p1", so no record key holds it. That space is the lane's own when no other lane's owner pane and not the operator's pane, both read from the session's state, carries the same prefix.

Every worker is spawned under the name <role>-<ticket>, lowercase, for example implementer-ann-64, where the role is the role contract it runs and the ticket is the issue key it works; the lane space already names the lane, and Herdr accepts only lowercase names of at most 32 characters. The ticket is the issue key ending the name, read back in upper case; a worker serving the whole lane, such as the integrator or a reviewer of the integration head, carries the lane's primary issue key. An agent in the lane's space whose name does not follow this form is still a worker of the lane, with no role or ticket. The owner closes a worker once its result is consumed, before spawning the next one under the same name, so a name is live at most once; Herdr refuses a spawn under a live name.

A lane pane never moves to another space: Herdr rewrites a moved pane's pane and tab ids, which breaks the lane record, review rows, and teardown.

herdr-await is the one wait on a lane agent; roles never run Herdr's own agent wait themselves. Given a message, it first sends that message to the agent with herdr-say, and a send that does not exit 0 ends the wait at once. Otherwise the wait ends when the agent is idle, done, or stuck on an interactive prompt, or is gone because its agent exited or its tab closed. When the wait ends, herdr-await sends its caller's pane one message naming the agent and the stop it ended on: the state the agent stopped in, gone, or the send's failure. It returns at once and waits apart from its caller, so its end reaches a Claude, Codex, or pi caller the same way, and a send that waits out a rate limit holds no caller in the foreground. Given the stop its caller last read, as that message named it, the wait ends only once the agent has changed state since that stop and has stopped again, or is gone, so an agent that works and stops before the wait starts still ends it. Each Herdr wait it runs is bounded, and at the bound it waits again, so the wait ends within that bound once the agent is gone by any means, its tab closed outside herdr-close included, or once an agent has worked and stopped between two of its Herdr waits. It runs as a process of its caller's tab, so closing or parking the caller ends it with the caller's other processes, and a wait whose caller is gone by any other means ends at its bound, waking no one.

Herdr leaves its own wait on an agent running when the agent's tab closes, so a wait on that agent ends as gone at its bound and wakes its caller, whoever else closed the tab. herdr-close, parking included, ends its own caller's waits on every agent in the tab or space it closes, waking no one, so an owner that closed a worker itself no longer waits on it and never reads that close as news of a worker spawned again under the same name.

herdr-close reports each close as one closed line, on stdout for a close and on stderr for a park, whose stdout is its parked line. An owner that closes a consumed worker appends that closed line to the lane's hand-off log, so every line herdr-close prints for a close or a park, on either stream, is one a hand-off log can hold.

At teardown the operator closes a lane's own space with herdr-close <space id>, which closes the space and stops every process started in it, including detached ones. A lane started in a shared space ends at its owner tab: the operator closes it with herdr-close <owner tab>, and the owner's close report names that tab, never the space.

An idle Claude lane agent is parked with herdr-close --park <pane>: it reads the agent's session id and role from the record of the pane's Claude session, taking the role a worker's spawn name carries when that record names none, closes the agent's tab, or the lane's own space when the agent is that lane's owner, and prints one parked line. The parker appends that line to the lane's hand-off log: the operator when it parks an owner, the owner when it parks a worker. A working agent or a Codex or pi agent is refused with nothing closed; only Claude keeps a per-process session file, so parking is Claude only.

A parked agent resumes as it was launched, plus --resume <session>: an owner through octo-lite-start --resume <session> in a new lane space under the lane's name at its worktree, a worker through herdr-spawn --resume <session> in the caller's space under its old name and role, the parked line's role or, when the line names none, the role its spawn name carries; Claude starts with --agent <role> --resume <session> and keeps its conversation.

When Herdr finds no agent for a herdr-say target, the latest parked line naming that pane or name decides: if an agent already runs under the line's name, the message goes to it; otherwise the agent is resumed first, then the message is delivered, and herdr-say prints the resumed agent's pane=. herdr-wake check counts a parked owner as present, so a spec review hand-off to it resumes it.

Risk: whether Herdr keeps space and pane ids across a Herdr server restart is unproven; if it does not, a restart breaks every lane record owner pane and every space derived from it.

Lane record

Octo-lite owns and publishes the lane record format: one TOML file per open lane in the lanes/ directory of its Herdr session's state directory, named by the owner agent name, with the keys below, written at the moments below. A closed lane's record, hand-off log, and notes live in archive/ inside that directory. Readers follow this format; octo-lite names no reader.

The record holds no ticket state: a ticket's state, holder, and repair passes live in the tracker only.

The record lists no workers. A lane's workers are the Herdr agents in the lane's space other than the owner; each worker's pane is its Herdr pane id, and its role and ticket come from its spawn name.

At each hand-off moment the owner appends one line to <lane record name>.handoffs.jsonl beside the lane record, per the hand-off field list; only the owner writes the file, except the parked line for the owner itself, which the operator appends when it parks the owner.

Every line of a hand-off log is one JSON object, appended whole. A reader of hand-off logs skips a line that is not one, naming that log and the line's number once, so one bad line hides nothing else in its log and breaks no other lane.

The fleet operator appends one line per operator moment to operator.handoffs.jsonl beside operator.toml, with the same common fields and the kinds below; it is the file's only writer. This is the lane hand-off mechanism with a different writer; readers follow this format, and octo-lite names no reader.

Human gates

Spec acceptance, acceptance of delivered work, merge of unaccepted work, preproduction promotion, and live traffic shifts require explicit human instruction.

A spec acceptance the human gives the fleet operator in chat is recorded by the fleet operator at once, as the receipt comment on the PR, and the owner is told; an owner never records it, since that reads as self-approval. A standing acceptance the human gives the fleet operator before the spec head exists is recorded the same way, at once, when the lane owner sends the fleet operator that spec's review link or head, quoting the human's standing words. The fleet operator also runs review-host.py reviewed --id <resource id> for each accepted spec, which moves its review row's base to the accepted commit and records no acceptance.

Every acceptance, of a spec or of delivered work, is recorded once, as a receipt comment on the lane's PR, and everything that needs it reads that comment. The receipt quotes the human's words, gives the date, names what is accepted (the spec or the PR), the exact accepted commit, and who recorded it. A spec receipt starts Spec acceptance receipt: and names each accepted spec once, by its full repository path followed by at and the accepted commit. A spec accepted on the review page is recorded by the owner processing that hand-off, quoting the action; a spec accepted in chat by the fleet operator; delivered work by the agent receiving the instruction, before it merges. A delivered-work receipt goes on the PR before the merge, and the merge commit closes it; nothing else records the merge. Spec Chat records no acceptance: the Accept spec hand-off in its spool is the instruction a spec receipt quotes, never a second record.

On a human instruction to merge, the receiving agent checks that the PR head is the accepted commit and that required checks pass, then records the receipt and merges. It re-checks no QA evidence: a merge ask goes out only after every step it needs, that evidence included.

A spec commit after acceptance that is wording-only keeps the original acceptance, with no new review and no new receipt. Wording-only means the commit changes only wording, labels, or anchors: it adds or removes no criterion and changes no stated behavior, value, or outcome. The lane owner decides, and lists each such commit in the PR body with one line saying what it rewords, so the human sees it at the merge gate. A commit the owner cannot plainly call wording-only is not, and goes back to spec review for a fresh acceptance.

Not present

There is no sweep or host timer, loop workflow, role resolver or roles.toml, control CLI, owner file, readiness envelope, trust root, conformance checker, or wording-only diff detector; do not rebuild them. There is no cross-session addressing or coordination and no session key in any record: the session scopes state by directory alone. The removed owner file was coordination and control state; the lane record is a read-only declaration for observation that nothing gates on.
