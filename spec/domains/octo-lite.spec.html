octo-lite current state

Specifications / octo-lite

This spec describes only what exists in this repository today.

It replaces the operating-model, delivery-lifecycle, role-runtime, and operator-control domain specs, which described deleted apparatus; they remain in git history.

User stories

As an operator, I can shape an idea into an accepted spec, then have it filed as a ticket graph and delivered on one PR ready for my review.

As an operator, I can install or verify octo-lite with one script and a plain git pull keeps it current; on a box with an existing setup, the installer adopts compatible links, skips what belongs to someone else, and never overwrites or fails.

As the fleet operator, I append one line per prod, note to the human, lane I start, and issue I file to my own hand-off file, so the floor shows what I did beside each lane's own lines.

As a lane owner, I append one line per hand-off moment to my lane's hand-off file, so the floor shows what happened on my lane.

As an operator, I see each lane in its own Herdr space named after the lane, holding its owner and every worker of that lane, while I work in a space of my own; closing a finished lane's space leaves nothing of it running.

As an operator, every QA criterion that failed on my lane reaches my merge ask either fixed and recaptured or named as outside the lane with why, beside what the judge saw and the head it judged, so no failure ships as a note and no wrong triage reaches my merge.

As an operator, a lane never stalls silently: every worker delivers its result to its lane owner as a message, the owner notices a worker that ended without reporting, recovers it, and tells me, a worker whose owner cannot be reached sends its result to me and stops instead of retrying without end, and every report reaches me as a message.

As an operator on a box short of memory, I can park an idle lane owner or worker so it holds no memory while it waits, and a later message to it resumes it under the same name with its conversation intact.

As an operator running several Herdr sessions on one box, I work in each without coordinating: an agent in one session never sees, wakes, or tears down a lane of another.

As an operator whose project keeps its own skills, such as its design rules, every implementer on my lanes loads the ones its ticket needs from my live main checkout, and onboarding warns me when a skill link points at a stale clone.

As an operator, a wording-only correction to a spec I accepted rides on my original acceptance, while any change to what the spec makes the system do comes back to me for acceptance.

As an operator, work that passes the cases at hand without following the rule the spec states never reaches my merge ask.

As an operator, every agent takes a repo-wide rule to mean one thing, an every-feature criterion its home spec marks as a project rule so Jev checks it at every shaping, and a cross-cutting decision a lane settles becomes one, so I never explain the term again.

As an operator, every review note that names what it will cost becomes one tracker ticket when its lane closes, labeled by its kind, instead of shipping only as PR history, so architecture and cleanliness debt stops piling up across PRs.

As an operator, I can fire a repo health pass on a repository whenever I choose, and its few real findings on architecture and cleanliness arrive as ranked tickets, never a report, that I triage on the Roadmap and fire off with Fix like bugs.

Acceptance criteria

Modular boundaries

The Herdr wrappers (octo-lite-start, herdr-spawn, herdr-say, herdr-close) own placing lane agents in spaces, messaging them, parking and resuming them, and closing tabs and spaces. The caller-facing seam is each wrapper's arguments and its printed pane= and workspace= lines. Direction is external-provider: the wrappers depend on the Herdr CLI, the session key Herdr exports, and, for parking, on Claude's own per-process session file and --resume; roles and skills depend on the wrappers, never the reverse. Observable scope: Herdr spaces, tabs, and agents, and process exit.

octo-lite owns and publishes the lane record and hand-off formats; roles write them at the named moments. The caller-facing seam is the files in each Herdr session's state directory, plus the lane's Herdr space and spawn names for workers. Direction is self-contained: readers such as a board depend on the format and locate a session's files from the Herdr session key; octo-lite names no reader. Observable scope: file contents and the lane's space membership.

Role contracts and skills own shaping, delivery, review, and gates. The caller-facing seam is the role contracts in agents/ and the skills in skills/. Direction is downward: roles use the wrappers and the lane record format; external providers are Linear, GitHub, Spec Chat, and annotateanything's QA capture program, whose rules (when QA runs, outcomes, owner triage) live in its jev-capture spec under QA rules. Observable scope: tickets, the PR, and the lane record.

The installer owns linking octo-lite's skills, roles, and helpers, and a project's declared skills, into the agent profiles. The caller-facing seam is the installer's flags and the target AGENTS.md Repo skills: line. Direction is external-provider: the installer reads the target's declaration from its checkout; the target names no octo-lite path, and octo-lite names no project skill. Observable scope: links in the profile skill, agent, and helper directories, and the installer's printed report.

The filing rule and the repo-health skill own turning review notes and health findings into health tickets. The caller-facing seam is the health tickets in the box's tracker, with their Health label and priority, and the tagged notes in each PR body. Direction is external-provider: the filer depends on the tracker the lanes already file in; annotateanything's Roadmap reads health tickets from that tracker like any loose end, so octo-lite names no Roadmap code and the Roadmap names no octo-lite path. Observable scope: health tickets, their labels, priorities, comments, and states, and the pass's one message.

Install

scripts/install-octo-lite symlinks skills/* into the Claude, Codex, and shared ~/.agents skill directories, agents/*.md into the Claude and Codex agent directories, the agents directory as each profile's octo-lite/adapters, and executable helpers into ~/.local/bin; --check verifies the links.

When a target path is already occupied, the installer classifies it: a symlink resolving into a different clone of this repository (matched by git remote get-url origin) is adopted and reported; any other existing file or symlink is skipped and reported; the installer never overwrites, never fails on an occupied path, and continues with the remaining items. A dangling link whose target was inside this repository is pruned as a known legacy path. Any other dangling link, including one at a path the installer links, belongs to someone else: it is reported and left untouched, never replaced.

A target repository declares its own skills in its root AGENTS.md with one line, Repo skills: followed by comma-separated repository-relative paths to skill directories. install-octo-lite --project <checkout> reads that line from the project's live main checkout, the clone the operator keeps on main, and links each declared skill from that checkout under its directory name, into the same skill directories as octo-lite's own skills. A declared skill's existing link that resolves anywhere but that checkout is stale: with or without --check, the installer warns, naming the link and where it points, leaves it untouched, and continues. It never links a project skill from another clone and never repairs a link.

Each peer links only what it owns (toolchain ownership); Spec Chat's installer links Spec Chat's own skills. Only the third-party tdd skill is pinned, by Skillfile into agents/skills (ADR 0002).

--check also reports version floors: for each tool octo-lite uses at runtime (git, herdr, jq, gh, node, python3, and at least one of claude or codex), it prints ok, missing, or too old (found version vs minimum) with the upgrade source. The installer never upgrades anything without the user's explicit consent.

With --onboard, the installer asks once whether agents may push, open pull requests, and file issues, and keeps the answers in octo-lite's one onboarding file, $XDG_STATE_HOME/octo-lite/onboarding.toml, beside its published onboarding status, done once answers are kept. Kept answers are not asked again; deleting that file asks afresh.

On a box with Herdr, the installer registers herdr-wake as Spec Chat's wake provider; a provider file someone else wrote is kept unchanged, and --undo leaves the registration in place because Spec Chat's review service depends on it. herdr-wake, and the herdr-say it runs, reach Herdr on their caller's search path or in Herdr's install directory, ~/.local/bin, so a review service started by any launcher (a box user service, a timed job, a shell) wakes owners as a pane does. A failed check or send writes a one-line reason to its error output: Herdr not found, naming the path searched; the owner pane not found in its session; Herdr not answering; or Herdr's own error.

Roles

agents/*.md are the hand-written role contracts: orchestrator, implementer, integrator, code-reviewer, and meta-operator; none pins a model.

Every spawned worker with a role contract (implementer, integrator, or code-reviewer) loads it: Claude through --agent ROLE, Codex as developer instructions, and pi as an appended system prompt, via herdr-spawn --role ROLE.

An implementer loads by name each skill the target AGENTS.md declares under Repo skills: that bears on its ticket, beside the octo-lite skills its contract lists; a declared skill outranks an octo-lite skill on the same subject, as a project's UI skill outranks frontend-design. Its report to the owner names the declared skills it loaded; a declared skill it needs that does not resolve is a missing environment, reported as a blocker.

An implementer implements the general rule the spec states, so every case the rule covers holds, not only the criterion, fixture, label, or evaluation case at hand. A code reviewer blocks code keyed to the instances at hand, such as a named criterion, fixture, label, or evaluation case, in place of the rule the spec states: it passes the check while the behavior stays wrong.

A repo-wide rule is an every-feature acceptance criterion its home spec marks as a project rule, Spec Chat's data-project-rule mark, which Jev checks against every spec at shaping and each review hand-off names under rules checked. A line in a target AGENTS.md only points implementers at such a criterion; a rule stated only there, or in spec prose outside a criterion, is not yet a repo-wide rule. When a lane's spec settles a cross-cutting decision, such as an identity key, an exposure contract, or a single source, that no project-rule criterion states, its owner names the decision and its home spec in its review hand-off. The fleet operator then asks a lane on that home spec, this lane when the home is its own spec, for a criterion marked as a project rule that states the decision, so Jev enforces it from the next shaping, and that spec's acceptance is recorded by the PR receipt like any other. The set stays small: a decision earns a rule only if a later feature could plausibly break it. The meta-operator and orchestrator contracts and the implement-spec skill state this where they ask, shape, and brief.

Waiting agents hold no memory: the fleet operator parks a lane owner idle at a human gate, on another lane, or held back for load, and resumes it by sending it the wake message, or when load allows, one owner at a time as memory frees. A parked owner is resumed, never relaunched fresh; only an owner with no parked line and no live pane is relaunched. A lane owner parks a worker it would otherwise keep idle through a long wait, such as a human gate or another lane, and messages it to resume; a worker whose result is consumed is closed, not parked. A resumed owner first sets its lane record's owner to its new pane, then acts on the message that resumed it. The meta-operator and orchestrator contracts and the herdr-comms and implement-spec skills state these moves where they wait or close.

Every lane owner, and every operator-like pane, runs under a /goal for its lane outcome, so goal check-ins keep invoking it while work is unfinished. Every report goes to its recipient through herdr-say; text left in the sender's own pane is not reported. A worker's last step sends its result to the owner pane its brief names, and only a herdr-say exit 0 confirms the send; a send that does not exit 0 is sent again, a bounded number of times. When no send to the owner is confirmed, the worker sends its result once to the operator's pane, read from the session's operator.toml, and stops whether or not that send is confirmed, so an unreachable owner never holds a worker in a send loop. The operator brings the lane's owner back as parking states and forwards it the result. At each check-in the owner reads the Herdr state of every worker it waits on; one that is idle, gone, or stuck on an interactive prompt ended without reporting, and the owner reads its pane. A finished result on that pane is consumed as the worker's report; otherwise the owner recovers or respawns the worker. Either way the owner tells the operator which worker ended without reporting and what it did.

Before a heavy job, such as a full test suite, a QA capture, or a build, the owner checks box load; when load is high it runs one heavy job at a time.

At lane close the owner first files its PR's notes by the filing rule, then removes the lane's review rows before removing any worktree, closes its workers, removes its own /tmp scratch, and archives the lane record last, per the archive moment.

The fleet operator acts on annotateanything's Bitbucket plugin watch: a red report starts a fix lane.

An optional operating model given to herdr-spawn reaches the agent at start and passes to every agent it spawns, and each spawn forwards the caller's HOME.

Delivery

spec-chat-shape produces the reviewed canonical spec, committed locally, and never publishes; it sends the review link as soon as the draft validates and is hosted, with no agent browser pass. In parallel, never before that link, the orchestrator files the Linear issue, pushes, and opens the draft PR, only as consent allows. A processed human spec acceptance (page action Accept spec, formerly called Finish review) permits implementation dispatch under the reviewed canonical spec.

Operator briefs carry the human decisions already made and exact source pointers (files and anchors), so shaping reads only those before drafting.

implement-spec first files the dependency-linked ticket graph from the accepted spec, runs its pre-dispatch mechanical checks, then fills the ready ticket frontier with implementer workers, each in its own worktree; repository tests run in delivery, never during shaping.

An optional exploration worker writes its notes only in the lane's notes directory, lanes/<lane record name>-notes/ beside the lane record, and the tickets it serves link them; the owner archives that directory with the record at lane close.

One integrator at a time integrates finished commits onto the single integration branch and PR.

A code-reviewer judges the integration head, and findings get bounded repair until review is clear and required checks pass. Its non-blocking notes ship tagged in the PR body and become health tickets at lane close.

Linear stays truthful: a ticket is Done only once integrated, and pushed when consent allows, and a merged accepted PR completes the worklane.

Pushing, opening pull requests, and filing issues follow the kept consent answers alone when present, overriding any instruction; when absent, target instructions decide. Without push consent the lane stays on local branches and ends at a local integration head.

A ticket whose behavior the spec on main already states needs no shaping or new acceptance: that spec's commit on main is the acceptance receipt, the ticket is a one-node graph, and one implementer, one integrator, and one reviewer still run.

Before the merge ask, the owner triages every criterion the lane's QA capture shows failed, from its evidence, whatever owner the bundle names, by annotateanything's owner triage rule, the one home of QA rules. A code fault's repair is a ticket under the spec issue, worked by a fresh implementer and integrated like any ticket; a fault in the QA program itself is fixed through annotateanything's own lane. A reshaped criterion keeps its meaning; one whose meaning changes is a spec change and goes back to spec review. Every verdict the merge ask lists was judged at the merge ask's head: a failure carried from an older head is recaptured at that head before it is triaged. The merge ask lists each failed criterion with the bundle's evidence_state, its decision_source and the head it was judged at, its triage, its cause or reason, and its outcome. A failure whose evidence_state is complete, where the judge reached the state and saw the product not match the criterion, is listed as a code fault unless a specific capture cause is named, such as a wrong fixture, a wrong page reached, or the criterion's shape.

Repo health

A health ticket is a tracker ticket for one real architecture or cleanliness issue in a repository, in the box's tracker, the one its lanes already file tickets in; no other store holds health issues. It names the issue, its consequence, where in the repository it lives, and each source that raised it: a PR or a health pass. It carries one label of the tracker's Health label group, naming its category, and a priority from its rank. It is filed unassigned, with no parent, in a state not yet started, so annotateanything's Roadmap lists it as a loose end the human triages and fires off with Fix, like a bug.

The categories are architecture, cleanliness, naming, duplication, test, and docs. A consequence is what the issue will cost or break, named concretely, such as the next change to acceptance must edit four copies. A note or finding that names no consequence stays history and never becomes a ticket.

A code reviewer tags every non-blocking note with its category and, when it has one, its consequence. The owner lists the reviewer's notes in the PR body, tagged as given, so the PR keeps them and a filer reads them there. At lane close, after the PR merges and before teardown, the agent closing the lane, its owner or the fleet operator, files the PR's notes by the filing rule.

One filing rule turns notes and findings into health tickets: one PR's notes at lane close, many PRs' notes in one batch, and a health pass's findings. The filer first reads every open health ticket and the target's current main, then gives each note or finding the first disposition below that fits. Two notes name the same issue when one fix would remove both, whatever their wording. An open health ticket whose issue the filer finds gone from main is closed as done, with a comment naming the main commit it was checked at and why the issue is gone.

A health issue's rank is its consequence: high when it will cause wrong behavior or block a change, medium when it makes the next change in that area cost more, such as a duplicate, a dead store, or a misleading name, and low when it costs only reading time. The rank is the ticket's tracker priority, so the Roadmap orders health tickets among its loose ends by it.

The repo-health skill is the repo health pass, fired by hand by the fleet operator, at its own call or when the human asks for one, and never on a timer. The fleet operator starts one fresh agent for it on the target's main checkout; that agent changes no repository file and writes only health tickets. It reads the target's instructions, its specs' modular boundaries, the open health tickets, and the code, and looks across the whole repository for architecture, cleanliness, best-practice, and trimming issues, a deletion first wherever one would do. It checks every open health ticket against main, closing each one main fixed, and files its findings by the filing rule, at most five new tickets per pass, highest rank first; the rest wait for a later pass that still finds them. Its result is the tickets, never a report: its one message to the fleet operator names each ticket it filed, commented on, or closed, by key, and the fleet operator relays that list to the human who asked.

The code-reviewer, orchestrator, and meta-operator contracts and the implement-spec skill state these moves where they review, list notes, close a lane, and fire the pass.

Herdr session

The Herdr session is octo-lite's isolation unit: an agent sees, messages, parks, wakes, and tears down only the lanes of its own session, and sessions need no coordination. Every wrapper and role acts in its caller's session and reads and writes only that session's state.

The session key is the Herdr session name, read from Herdr alone. Herdr exports the name as HERDR_SESSION to every pane of a named session, and a pane of the default session has none, so a process reads the key as ${HERDR_SESSION:-default}. The Herdr CLI selects its own session by the same variable, so a process outside any pane that sets it acts in that session, and one that does not acts in the default session; a set HERDR_SOCKET_PATH pins the session over it. Herdr limits session names to ASCII letters, digits, ., _, and -, so the key is safe as a path component. Any repository that scopes its own state by Herdr session reads this same key from Herdr directly.

octo-lite's state directory for a session is $XDG_STATE_HOME/octo-lite/ for the key default, and $XDG_STATE_HOME/octo-lite/sessions/<key>/ for any other key, as Herdr keeps its own named sessions under sessions/<name>. It holds the session's lanes/ directory, with each lane's record, hand-off log, and notes, and the archive, and the session's operator.toml and operator.handoffs.jsonl; the store table gives each its lifetime. octo-lite-state prints the caller's session state directory, and roles and wrappers locate lane and operator files through it. The onboarding file belongs to the box, not a session, and stays at $XDG_STATE_HOME/octo-lite/onboarding.toml.

Herdr pane, tab, and space ids are unique only within a session; another session repeats them. Every id in a session's state is read and acted on in that session: a message, park, wake, or close by id reaches only the caller's session, unless a wake owner names its own session (wake owner), and a close stops only processes of the caller's session. No record key names a session.

The one box-wide service, Spec Chat's review service, runs in one session and wakes owners of every session, so a review row's owner names its session: a lane registers with --owner "${HERDR_SESSION:-default}/$HERDR_PANE_ID", for example second/wP:p2. herdr-wake checks and wakes a <session>/<pane> owner in that session, with that session's state for its parked lines, and a bare pane in its caller's session; it never searches sessions for a pane, since ids repeat across them.

Stores

Every file or folder octo-lite writes on the box, each with one lifetime and the writer that ends it. A Log is appended to, or rewritten only by its writers, and is never deleted automatically; it ends in its lane's archive or by the box owner's hand. octo-lite keeps no Cache, and no store keeps a copy of a fact another store owns: an acceptance is the PR receipt, a ticket's state is the tracker's, and a lane's workers are its Herdr space. A path no row names is no store of octo-lite: a lane's worktrees are the target repository's, in Git, and the owner removes them and its own /tmp scratch at lane close; the installer's links are its install, and the wake provider file it registers is Spec Chat's provider configuration (wake provider).

Transport

herdr-spawn opens one tab and agent at an explicit worktree, and herdr-say delivers a message, returning only once Herdr observes a state change. A target blocked on interactive input gets nothing typed, and herdr-say exits 75, not delivered, so the caller retries once it frees.

herdr-spawn starts the agent bare, and its brief follows by herdr-say.

A failed spawn closes the tab it created, and a failed octo-lite-start closes the lane space it created, so no orphan is left. herdr-spawn answers the agent's startup trust dialog at the pane, confirming only once the affirmative row is selected and never a refusal; a dialog that does not clear fails the spawn closed.

There is no acknowledgement step, inbox, or drain.

Each lane, one PR, runs in its own Herdr space labelled with the lane name; the fleet operator runs in a space of its own. octo-lite-start creates the lane space and starts the owner in it, leaving no other tab there, and prints its workspace= beside pane=. The owner spawns every worker of its lane into its own space, $HERDR_WORKSPACE_ID. A lane's own space is the one octo-lite-start created for it; a lane started in a space shared with the operator or other lanes has no space of its own.

A lane's space id is the prefix of its owner pane id, w7 in "w7:p1", so no record key holds it. That space is the lane's own when no other lane's owner pane and not the operator's pane, both read from the session's state, carries the same prefix.

Every worker is spawned under the name <role>-<ticket>, lowercase, for example implementer-ann-64, where the role is the role contract it runs and the ticket is the issue key it works; the lane space already names the lane, and Herdr accepts only lowercase names of at most 32 characters. The ticket is the issue key ending the name, read back in upper case; a worker serving the whole lane, such as the integrator or a reviewer of the integration head, carries the lane's primary issue key. An agent in the lane's space whose name does not follow this form is still a worker of the lane, with no role or ticket. The owner closes a worker once its result is consumed, before spawning the next one under the same name, so a name is live at most once; Herdr refuses a spawn under a live name.

A lane pane never moves to another space: Herdr rewrites a moved pane's pane and tab ids, which breaks the lane record, review rows, and teardown.

At teardown the operator closes a lane's own space with herdr-close <space id>, which closes the space and stops every process started in it, including detached ones. A lane started in a shared space ends at its owner tab: the operator closes it with herdr-close <owner tab>, and the owner's close report names that tab, never the space.

An idle Claude lane agent is parked with herdr-close --park <pane>: it reads the agent's session id and role from Claude's own session file for the process in that pane, closes the agent's tab, or the lane's own space when the agent is that lane's owner, and prints one parked line. The parker appends that line to the lane's hand-off log: the operator when it parks an owner, the owner when it parks a worker. A working agent or a Codex or pi agent is refused with nothing closed; only Claude keeps a per-process session file, so parking is Claude only.

A parked agent resumes as it was launched, plus --resume <session>: an owner through octo-lite-start --resume <session> in a new lane space under the lane's name at its worktree, a worker through herdr-spawn --resume <session> in the caller's space under its old name and role; Claude starts with --agent <role> --resume <session> and keeps its conversation.

When Herdr finds no agent for a herdr-say target, the latest parked line naming that pane or name decides: if an agent already runs under the line's name, the message goes to it; otherwise the agent is resumed first, then the message is delivered, and herdr-say prints the resumed agent's pane=. herdr-wake check counts a parked owner as present, so a spec review hand-off to it resumes it.

Risk: whether Herdr keeps space and pane ids across a Herdr server restart is unproven; if it does not, a restart breaks every lane record owner pane and every space derived from it.

Lane record

Octo-lite owns and publishes the lane record format: one TOML file per open lane in the lanes/ directory of its Herdr session's state directory, named by the owner agent name, with the keys below, written at the moments below. A closed lane's record, hand-off log, and notes live in archive/ inside that directory. Readers follow this format; octo-lite names no reader.

The record holds no ticket state: a ticket's state, holder, and repair passes live in the tracker only.

The record lists no workers. A lane's workers are the Herdr agents in the lane's space other than the owner; each worker's pane is its Herdr pane id, and its role and ticket come from its spawn name.

At each hand-off moment the owner appends one line to <lane record name>.handoffs.jsonl beside the lane record, per the hand-off field list; only the owner writes the file, except the parked line for the owner itself, which the operator appends when it parks the owner.

The fleet operator appends one line per operator moment to operator.handoffs.jsonl beside operator.toml, with the same common fields and the kinds below; it is the file's only writer. This is the lane hand-off mechanism with a different writer; readers follow this format, and octo-lite names no reader.

Human gates

Spec acceptance, acceptance of delivered work, merge of unaccepted work, preproduction promotion, and live traffic shifts require explicit human instruction.

A spec acceptance the human gives the fleet operator in chat is recorded by the fleet operator at once, as the receipt comment on the PR, and the owner is told; an owner never records it, since that reads as self-approval. The fleet operator also runs review-host.py reviewed --id <resource id> for each accepted spec, which moves its review row's base to the accepted commit and records no acceptance.

Every acceptance, of a spec or of delivered work, is recorded once, as a receipt comment on the lane's PR, and everything that needs it reads that comment. The receipt quotes the human's words, gives the date, names what is accepted (the spec or the PR), the exact accepted commit, and who recorded it. A spec receipt starts Spec acceptance receipt: and names each accepted spec once, by its full repository path followed by at and the accepted commit. A spec accepted on the review page is recorded by the owner processing that hand-off, quoting the action; a spec accepted in chat by the fleet operator; delivered work by the agent receiving the instruction, before it merges. A delivered-work receipt goes on the PR before the merge, and the merge commit closes it; nothing else records the merge. Spec Chat records no acceptance: the Accept spec hand-off in its spool is the instruction a spec receipt quotes, never a second record.

On a human instruction to merge, the receiving agent checks that the PR head is the accepted commit and that required checks pass, then records the receipt and merges. It re-checks no QA evidence: a merge ask goes out only after every step it needs, that evidence included.

A spec commit after acceptance that is wording-only keeps the original acceptance, with no new review and no new receipt. Wording-only means the commit changes only wording, labels, or anchors: it adds or removes no criterion and changes no stated behavior, value, or outcome. The lane owner decides, and lists each such commit in the PR body with one line saying what it rewords, so the human sees it at the merge gate. A commit the owner cannot plainly call wording-only is not, and goes back to spec review for a fresh acceptance.

Not present

There is no sweep or host timer, loop workflow, role resolver or roles.toml, control CLI, owner file, readiness envelope, trust root, conformance checker, or wording-only diff detector; do not rebuild them. There is no cross-session addressing or coordination and no session key in any record: the session scopes state by directory alone. The removed owner file was coordination and control state; the lane record is a read-only declaration for observation that nothing gates on.
