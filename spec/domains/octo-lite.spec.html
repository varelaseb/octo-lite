octo-lite current state

Specifications / octo-lite

This spec describes only what exists in this repository today.

It replaces the operating-model, delivery-lifecycle, role-runtime, and operator-control domain specs, which described deleted apparatus; they remain in git history.

User stories

As an operator, I can shape an idea into an accepted spec, then have it filed as a ticket graph and delivered on one PR ready for my review.

As an operator, I can install or verify octo-lite with one script and a plain git pull keeps it current; on a box with an existing setup, the installer adopts compatible links, skips what belongs to someone else, and never overwrites or fails.

As the fleet operator, I append one line per prod and note to the human to my own hand-off file, so the floor shows what I did beside each lane's own lines.

As an operator, I see each lane in its own Herdr space named after the lane, holding its owner and every worker of that lane, while I work in a space of my own; closing a finished lane's space leaves nothing of it running.

Acceptance criteria

Given an operator with an accepted spec in a lane, When the lane owner runs implement-spec to completion and the operator opens the lane's PR, Then that one PR shows every ticket's work, a clear review, and passing required checks, ready for the operator's review.

Given an operator on a box where some install paths are already occupied by someone else's files, When the operator runs the installer, Then it reports each occupied path as skipped, links every other item, and exits successfully, proven by a unit test: no screen shows it.

Given the fleet operator and a live lane owner, When the fleet operator sends the lane owner a prod, Then the operator's hand-off file gains one prod line naming the lane, proven by a unit test: no screen shows it.

Given an operator in its own Herdr space, When the operator launches a lane, Then Herdr shows a new space named after the lane holding only that lane's owner, and the operator's space is unchanged.

Given a lane owner delivering a spec, When it spawns implementer, integrator, and reviewer workers, Then Herdr shows each worker in the lane's space under a name that carries its role and its ticket, and no worker in any other space.

Given a lane with live workers in its space, When a reader reads the lane's workers, Then it gets each worker's pane, role, and ticket from the lane's space and the workers' names, with no worker list in the lane record, proven by a unit test: no screen shows it.

Given a finished lane whose space still holds its owner and a worker that started a background process, When the operator closes the lane's space, Then Herdr lists neither the space nor any of the lane's agents.

Given a finished lane whose space still holds its owner and a worker that started a background process, When the operator closes the lane's space, Then none of the lane's agents or their background processes is still running, proven by a unit test: no screen shows it.

Given a finished lane whose owner was started in a space shared with the operator and other lanes, When its owner reports the lane closed, Then the owner's report names its owner tab to close and no space.

Given a finished lane whose owner was started in a space shared with the operator and other lanes, When its owner reports the lane closed and the operator closes the tab the report names, Then Herdr no longer shows that tab and still shows the shared space, the operator, and every other lane in it running.

Given an operator installing octo-lite with no kept consent answers, When the operator runs the installer with onboarding and answers whether agents may push, open pull requests, and file issues, Then the answers are kept in octo-lite's published onboarding status, which reads done, proven by a unit test: no screen shows it.

Given an operator whose kept consent answer refuses push, When the lane owner runs implement-spec to completion, Then the owner's report to the operator names the local integration head that holds every ticket's work.

Given an operator whose kept consent answer refuses push, When the lane owner runs implement-spec to completion, Then no lane branch is pushed, proven by a unit test: no screen shows it.

Given an operator on a box with Herdr, When the operator installs octo-lite and later uninstalls it, Then octo-lite is registered as Spec Chat's wake provider after install and stays registered after uninstall, proven by a unit test: no screen shows it.

Given a lane owner started with an operating model file, When it spawns a worker and that worker spawns a child, Then the worker and the child each start with that operating model and the caller's home, proven by a unit test: no screen shows it.

Given a lane owner whose next worker's agent fails to start, needs an induced failure: agent start fails, When the lane owner spawns that worker and the spawn ends, Then the spawn reports the failure and Herdr shows no tab left for that worker.

Given an operator with a lane whose owner fails to start, needs an induced failure: owner agent start fails, When the operator launches the lane with octo-lite-start and it ends, Then it reports the failure and Herdr shows no space for the lane.

Given a lane owner and a worker waiting on an interactive dialog, When the owner sends the worker a message with herdr-say, Then nothing is typed into the dialog and the message is reported not delivered, to retry once the worker frees, proven by a unit test: no screen shows it.

Given an operator with a ticket whose behavior the spec on main already states, When the lane owner runs implement-spec on that ticket to completion and the operator opens the lane's PR, Then no spec review was asked, and that one PR shows the ticket's work, a clear review, and passing required checks, ready for the operator's review.

Given an operator with a lane's spec under review, When the operator accepts the spec in chat with the fleet operator, the fleet operator records it, and the operator opens the lane's PR, Then the PR shows a receipt comment from the fleet operator, not from the lane owner.

Given a lane owner whose PR merged, When it closes the lane, Then the lanes directory no longer lists the lane, and its archive holds the lane's record and hand-off log unchanged, proven by a unit test: no screen shows it.

Given a lane owner delivering a ticket graph, When a ticket moves state, Then the lane record holds no ticket entry, proven by a unit test: no screen shows it.

Given a lane owner delivering a ticket graph, When a ticket moves state and the operator opens that ticket in the tracker, Then the tracker shows the ticket's new state.

Given an operator with a lane's PR ready to merge, When the operator tells the fleet to merge it and the PR merges, Then the box holds no record of that acceptance besides the PR's receipt comment, proven by a unit test: no screen shows it.

Given an operator with a lane's PR ready to merge, When the operator tells the fleet to merge it, the PR merges, and the operator opens the PR, Then the PR shows one receipt comment quoting the operator's words and the accepted commit.

Modular boundaries

The Herdr wrappers (octo-lite-start, herdr-spawn, herdr-say, herdr-close) own placing lane agents in spaces, messaging them, and closing tabs and spaces. The caller-facing seam is each wrapper's arguments and its printed pane= and workspace= lines. Direction is external-provider: the wrappers depend on the Herdr CLI; roles and skills depend on the wrappers, never the reverse. Observable scope: Herdr spaces, tabs, and agents, and process exit.

octo-lite owns and publishes the lane record and hand-off formats; roles write them at the named moments. The caller-facing seam is the files under $XDG_STATE_HOME/octo-lite/lanes/, plus the lane's Herdr space and spawn names for workers. Direction is self-contained: readers such as a board depend on the format; octo-lite names no reader. Observable scope: file contents and the lane's space membership.

Role contracts and skills own shaping, delivery, review, and gates. The caller-facing seam is the role contracts in agents/ and the skills in skills/. Direction is downward: roles use the wrappers and the lane record format; external providers are Linear, GitHub, and Spec Chat. Observable scope: tickets, the PR, and the lane record.

Install

scripts/install-octo-lite symlinks skills/* into the Claude, Codex, and shared ~/.agents skill directories, agents/*.md into the Claude and Codex agent directories, the agents directory as each profile's octo-lite/adapters, and executable helpers into ~/.local/bin; --check verifies the links.

When a target path is already occupied, the installer classifies it: a symlink resolving into a different clone of this repository (matched by git remote get-url origin) is adopted and reported; any other existing file or symlink is skipped and reported; the installer never overwrites, never fails on an occupied path, and continues with the remaining items. A dangling link whose target was inside this repository is pruned as a known legacy path. Any other dangling link, including one at a path the installer links, belongs to someone else: it is reported and left untouched, never replaced.

Each peer links only what it owns (toolchain ownership); Spec Chat's installer links Spec Chat's own skills. Only the third-party tdd skill is pinned, by Skillfile into agents/skills (ADR 0002).

--check also reports version floors: for each tool octo-lite uses at runtime (git, herdr, jq, gh, node, python3, and at least one of claude or codex), it prints ok, missing, or too old (found version vs minimum) with the upgrade source. The installer never upgrades anything without the user's explicit consent.

With --onboard, the installer asks once whether agents may push, open pull requests, and file issues, and keeps the answers in octo-lite's one onboarding file, $XDG_STATE_HOME/octo-lite/onboarding.toml, beside its published onboarding status, done once answers are kept. Kept answers are not asked again; deleting that file asks afresh.

On a box with Herdr, the installer registers herdr-wake as Spec Chat's wake provider; a provider file someone else wrote is kept unchanged, and --undo leaves the registration in place because Spec Chat's review service depends on it.

Roles

agents/*.md are the hand-written role contracts: orchestrator, implementer, integrator, code-reviewer, and meta-operator; none pins a model.

Every spawned worker with a role contract (implementer, integrator, or code-reviewer) loads it: Claude through --agent ROLE, Codex as developer instructions via herdr-spawn --role ROLE.

An optional operating model given to herdr-spawn reaches the agent at start and passes to every agent it spawns, and each spawn forwards the caller's HOME.

Delivery

spec-chat-shape produces the reviewed canonical spec, committed locally, and never publishes; it sends the review link as soon as the draft validates and is hosted, with no agent browser pass. In parallel, never before that link, the orchestrator files the Linear issue, pushes, and opens the draft PR, only as consent allows. A processed human spec acceptance (page action Accept spec, formerly called Finish review) permits implementation dispatch under the reviewed canonical spec.

Operator briefs carry the human decisions already made and exact source pointers (files and anchors), so shaping reads only those before drafting.

implement-spec first files the dependency-linked ticket graph from the accepted spec, runs its pre-dispatch mechanical checks, then fills the ready ticket frontier with implementer workers, each in its own worktree; repository tests run in delivery, never during shaping.

One integrator at a time integrates finished commits onto the single integration branch and PR.

A code-reviewer judges the integration head, and findings get bounded repair until review is clear and required checks pass.

Linear stays truthful: a ticket is Done only once integrated, and pushed when consent allows, and a merged accepted PR completes the worklane.

Pushing, opening pull requests, and filing issues follow the kept consent answers alone when present, overriding any instruction; when absent, target instructions decide. Without push consent the lane stays on local branches and ends at a local integration head.

A ticket whose behavior the spec on main already states needs no shaping or new acceptance: that spec's commit on main is the acceptance receipt, the ticket is a one-node graph, and one implementer, one integrator, and one reviewer still run.

Transport

herdr-spawn opens one tab and agent at an explicit worktree, and herdr-say delivers a message, returning only once Herdr observes a state change. A target blocked on interactive input gets nothing typed, and herdr-say exits 75, not delivered, so the caller retries once it frees.

herdr-spawn starts the agent bare, and its brief follows by herdr-say.

A failed spawn closes the tab it created, and a failed octo-lite-start closes the lane space it created, so no orphan is left. herdr-spawn answers the agent's startup trust dialog at the pane, confirming only once the affirmative row is selected and never a refusal; a dialog that does not clear fails the spawn closed.

There is no acknowledgement step, inbox, or drain.

Each lane, one PR, runs in its own Herdr space labelled with the lane name; the fleet operator runs in a space of its own. octo-lite-start creates the lane space and starts the owner in it, leaving no other tab there, and prints its workspace= beside pane=. The owner spawns every worker of its lane into its own space, $HERDR_WORKSPACE_ID. A lane's own space is the one octo-lite-start created for it; a lane started in a space shared with the operator or other lanes has no space of its own.

A lane's space id is the prefix of its owner pane id, w7 in "w7:p1", so no record key holds it. That space is the lane's own when no other lane's owner pane and not the operator's pane carries the same prefix.

Every worker is spawned under the name <role>-<ticket>, lowercase, for example implementer-ann-64, where the role is the role contract it runs and the ticket is the issue key it works; the lane space already names the lane, and Herdr accepts only lowercase names of at most 32 characters. The ticket is the issue key ending the name, read back in upper case; a worker serving the whole lane, such as the integrator or a reviewer of the integration head, carries the lane's primary issue key. An agent in the lane's space whose name does not follow this form is still a worker of the lane, with no role or ticket. The owner closes a worker once its result is consumed, before spawning the next one under the same name, so a name is live at most once; Herdr refuses a spawn under a live name.

A lane pane never moves to another space: Herdr rewrites a moved pane's pane and tab ids, which breaks the lane record, review rows, and teardown.

At teardown the operator closes a lane's own space with herdr-close <space id>, which closes the space and stops every process started in it, including detached ones. A lane started in a shared space ends at its owner tab: the operator closes it with herdr-close <owner tab>, and the owner's close report names that tab, never the space.

Risk: whether Herdr keeps space and pane ids across a Herdr server restart is unproven; if it does not, a restart breaks every lane record owner pane and every space derived from it.

Lane record

Octo-lite owns and publishes the lane record format: one TOML file per open lane in $XDG_STATE_HOME/octo-lite/lanes/, named by the owner agent name, with the keys below, written at the moments below. A closed lane's record and hand-off log live in archive/ inside that directory. Readers follow this format; octo-lite names no reader.

The record holds no ticket state: a ticket's state, holder, and repair passes live in the tracker only.

The record lists no workers. A lane's workers are the Herdr agents in the lane's space other than the owner; each worker's pane is its Herdr pane id, and its role and ticket come from its spawn name.

At each hand-off moment the owner appends one line to <lane record name>.handoffs.jsonl beside the lane record, per the hand-off field list; only the owner writes the file.

The fleet operator appends one line per operator moment to operator.handoffs.jsonl beside operator.toml, with the same common fields and the kinds below; it is the file's only writer. This is the lane hand-off mechanism with a different writer, matching the consumer's operator log.

Human gates

Spec acceptance, acceptance of delivered work, merge of unaccepted work, preproduction promotion, and live traffic shifts require explicit human instruction.

A spec acceptance the human gives the fleet operator in chat is recorded by the fleet operator at once, on the review page and as a receipt comment on the PR, and the owner is told; an owner never records it, since that reads as self-approval.

Every acceptance, of a spec or of delivered work, is recorded once, as a receipt comment on the lane's PR, and everything that needs it reads that comment. The receipt quotes the human's words, gives the date, names what is accepted (the spec path or the PR), the exact accepted commit, and who recorded it. A spec accepted on the review page is recorded by the owner processing that hand-off, quoting the action; a spec accepted in chat by the fleet operator; delivered work by the agent receiving the instruction, before it merges. A delivered-work receipt goes on the PR before the merge, and the merge commit closes it; nothing else records the merge. The review host's accepted flag is a view cache for screens and is never cited as the record.

Not present

There is no sweep or host timer, loop workflow, role resolver or roles.toml, control CLI, owner file, readiness envelope, trust root, or conformance checker; do not rebuild them. The removed owner file was coordination and control state; the lane record is a read-only declaration for observation that nothing gates on.
