octo-lite

Specifications / octo-lite

This spec states how octo-lite works.

It is octo-lite's domain spec for roles, delivery, lane records, repo health, and human gates; Herdr transport and install have their own, and its decisions are the ADRs the index lists.

User stories

As an operator, I can shape an idea into an accepted spec, then have it filed as a ticket graph and delivered on one PR ready for my review.

As the fleet operator, I append one line per prod, note to the human, lane I start, issue I file, and complaint to my own hand-off file, so the floor shows what I did beside each lane's own lines.

As a lane owner, I append one line per hand-off moment to my lane's hand-off file, so the floor shows what happened on my lane, and each ask I make of the human is one gate line naming where to answer and the one action, so the human's pages show the ask without the operator relaying it.

As a lane owner, each ask I make of the human also carries why I ask, what backs it, and the answers I offer, up to four, each with its own line saying what choosing it does, so the human decides from the ask itself, with one choice, wherever a reader shows it.

As an operator, every QA criterion that failed on my lane reaches my merge ask ended by the lane's one finish rule: fixed and recaptured when it is about the change, proven by a named test when no browser can show it, or, outside the change, filed with its consequence or dropped, beside what the judge saw and the head it judged, so no failure of the change ships as a note and no wrong triage reaches my merge.

As an operator, a Bitbucket release annotateanything's plugin watch reports red starts a fix lane of that release without my asking.

As an operator, I can ask the fleet operator to launch a self improvement lane on one goal I name, a measurable outcome of any of my projects, the workbench's own included, and get a lane that builds or checks the check that scores it, runs experiments, builds models, spends the tokens it needs, keeps only what measurably moves that goal, and brings me the result through my usual gates.

As an operator, no self-improvement lane runs unless I name its goal: none starts by itself, none picks its own goal or moves on to another, and none rewrites my agents, role contracts, or skills unless the goal I named is about them, so the team is a tool I point, never a standing loop.

As an operator, no one agent directs my self-improvement lane's research: its scientists read one shared experiment state, gather around the hypotheses they judge most promising, have each experiment critiqued by a peer before it spends tokens, and share every success and failure, so no dead end is tried twice and the search goes where the evidence points.

As an operator, my self-improvement lane proves its eval can see the code it improves, and leaves a change room to win, before it spends tokens on tries, and brings me as one question any input only I can give, so no lane spends a night on an eval no change can move.

As an operator, my self-improvement lane spends the tokens it needs with no cap, stops by itself when a whole round of its hypotheses gains nothing, or when I say stop, and names its spend so far in every report and ask it sends me, so it spends only while it gains and never runs away on tokens or disk.

As an operator, a self-improvement lane runs on my fleet like any lane: the fleet operator launches it in its own Herdr space with a lane record the board reads, parks and resumes it, and hears its gates and reports from one steward, which holds its PR and sends me its questions, review links, and merge ask.

As an operator whose project declares a changelog or worklog convention, every change my lanes ship that the convention logs carries its entry in the same PR, in my project's format, and my merge ask names that entry or why there is none, so the log never falls behind what shipped.

As an operator, a wording-only correction to a spec I accepted rides on my original acceptance, a fix that only restates a decision I accepted rides on that acceptance too, by a receipt quoting the decision that I hear of in one line, and any other change to what the spec makes the system do comes back to me for acceptance.

As an operator, a merge I approve merges only the head I approved: its receipt is on the PR before the merge, a merge whose receipt cannot be recorded does not happen, and a merge set to run once checks pass never merges a commit pushed after my go.

As an operator, work that passes the cases at hand without following the rule the spec states never reaches my merge ask.

As an operator, every agent takes a repo-wide rule to mean one thing, an every-feature criterion its home spec marks as a project rule so Jev checks it at every shaping, and a cross-cutting decision a lane settles becomes one, so I never explain the term again.

As an operator, a general rule I state in chat comes back to me as one question offering it as a project rule in its home spec, and a lane whose Jev checks did not run says which rules went unchecked, so no rule I set lives only in chat or goes unchecked silently.

As an operator, my lanes offer a project rule only for a promise my product or system makes, and a convention for how my UI looks or moves goes into my design system with a code check that enforces it, under at most one project rule saying UI uses the design system's shared parts, so my rule set stays small and my design conventions are enforced exactly.

As an operator whose project has a design system, the prototype I accept already passes my design system's checks, and review blocks a part drawn by hand or nearly copied where a shared part draws it, and a new shared part missing its entry, its convention, or its code check, so my UI's patterns live in my design system alone and no build inherits a fix its brief never named.

As an operator, a standing rule I set for how agents work becomes an issue against the role contract or operating model that governs that work, so every agent started after it merges carries it, and my running lanes hear of it only when it changes the step one of them is on right now.

As an operator, a merged change to a role contract or the operating model reaches each running lane owner whose remaining steps it touches, by parking and resuming that owner with its conversation kept, and a change to the meta-operator contract or the operating model reaches the fleet operator itself, by replacing it in its own pane with a fresh session that starts from a short brief of what is in flight, once I have gone quiet, never while I am in dialogue with it, so it stops carrying its whole old conversation, and never by a message asking either to re-read instructions it cannot reload.

As an operator, lanes that need the same shared surface of my product, such as its design system, take turns editing it, at most two open on it at once, and app-wide UI changes merge one at a time with a check between them, so no wave of UI changes collides or reaches my users with no clear culprit.

As an operator, the fleet operator relays to me only gates, decisions, real blockers, lane closes, and each problem of my box once, gives me progress in one line or none, and brings its clear-cut questions together as one question asking whether to take its recommendations.

As an operator, a problem of my box that my lanes work around, such as a pinned skill that never installed, reaches me once with the step that fixes it, never only inside a lane's reports.

As an operator, every agent on my box answers, before it finishes, whether anything about the system annoyed it, and each one that did leaves one sentence, with when, which agent and lane, its session, and the project, that the fleet operator relays to me, so I hear what annoys my agents without any of them waking anyone or filing anything for it.

As an operator, my lanes' heavy jobs wait on my box's lock only for another heavy job that ends by itself, never for a server, a watcher, or a ticket's own tests, which never take it, and each lane runs its full suite only on a head it would ask me to merge, so no lane's heavy work stalls on another's.

As an operator, my lanes' merge-path work gets my box's lock first: a lane's full suite and its merge ask's capture run ahead of other lanes' builds, recordings, and research runs, and a suite waiting in line runs on its lane's head as it is when the suite starts, so no fix batch makes a waiting suite stale.

As an operator, no change a lane shapes depends on my remembering which step comes next: its steps across systems trigger each other and are safe in any order, and only my explicit gates wait on me.

As an operator, review never buries what matters: a note about the change is fixed in its PR, a privacy, data loss, money, or security consequence blocks the merge until it is fixed, a note about old code outside the change becomes a tracker ticket when the lane closes only when it names a real consequence, at most five per PR, labeled by its kind, and every other note is dropped.

As an operator, a PR that review keeps sending back comes to me with its open blockers after two fix rounds, instead of looping.

As an operator, my lanes' code reviewers send only what they have run: each reviewer runs the changed behavior and the failing case behind each finding itself, from a checkout of its own that no other agent works in, and proves each fix's test fails without its fix, so my lane owner never rechecks a guessed finding or waits on a suite run twice.

As an operator, my lane reaches its merge ask on the shortest path that keeps every check: each check starts as soon as the head it checks is ready, never waiting on a step it does not read, every finding on a head goes into one fix batch, main is merged into the lane once, and each one-shot run, such as the full suite or a QA capture, runs only on a head the lane would ask me to merge.

As an operator, every status a lane owner sends me says when it expects its next ask of me, how sure it is, and what could slip it, and tells me again when that time moves later, so I know when to come back.

As an operator, a lane that finds a simpler or sturdier way than the one I asked for says so once, up front, in its first review link's message, as "Are you sure you want X? Y is simpler because Z", challenging the frame and not only the details, then goes the way I choose; its silence means it checked and what I asked is the best path.

As an operator, every merge ask opens with a few plain lines anyone can read, saying what changes, what review found that matters, and the QA call, and everything else waits in the PR.

As an operator, every merge ask for a change I can see carries a See it link for each screen or state it changes, opening that screen in that state in what my project says a link opens, so I review the change without hunting for it.

As an operator, a merge ask means my whole issue is done in that one PR, built, tested, and QA-captured, with nothing in scope left to a later slice, a follow-up ticket, a phase 2, or an open question, and anything that truly cannot be done before merge reaches me with why before it is cut.

As an operator, a screen my lane changes ships looking like the mockup I accepted with its spec: the implementer builds it from that mockup, review compares the built screen with it, and QA shows them side by side, so I never find the drift after merge.

As an operator, I can fire a repo health pass on a repository whenever I choose, and its few real findings on architecture and cleanliness arrive as ranked tickets, never a report, that I triage and fire off like bugs.

As an operator, my lanes keep no QA environment up that they are not capturing in: a lane takes its PR's environments down as soon as its bundle is published and brings one back only for a recapture, so idle environments never fill the box's shared QA services.

As an operator, no spec a lane shapes lives only on the box: the lane pushes its branch at every spec commit and opens its draft PR at the first, so a lost box loses no accepted or pending spec.

As an operator, a spec my lane shapes that changes my product's screens comes to review, without my asking, as a working prototype of those screens in the product itself, built from its shipped components on real data where that is safe, with a short captioned video and a table placing each surface on its route, and every round of my notes comes back with both updated.

As an operator, the first round of a screen my lane prototypes shows me two directions for it side by side, each saying what it gives up, with the lane's pick and its reason, and one press picks another, so I see the choice weighed without an extra round.

As an operator, every prototype round reaches me already watched by the lane as a first-time user would watch it, with what read unclear or slow fixed, so my notes go to what only I can judge.

As an operator, every prototype round video shows my screen used the way a person uses it, a visible pointer moving, hovering, pressing, holding, right-clicking, typing each key, picking from a list, scrolling, and dragging the item lifted, each change at the product's own speed with no cut and the last step held to its end, whether or not Stageshow is installed and however loaded my box is, so I understand the change from the video alone.

As an operator, I give a note on a prototype as the problem I hit, and the next round brings the fix the lane chose for it, without asking me how.

As an operator, a lane that tells me a commit is pushed, or that a spec or PR is ready for my accept, has first proved the remote branch holds every commit it names, so I never accept a head missing what I was shown.

As an operator, every screen an agent designs or builds for my project, prototype included, carries no secondary label or description it does not need, since its layout does the explaining, even when my project has its own UI skill.

As an operator, every string an agent writes on my product's screens is one my users need: no caption restating its label, no hint planting a worry they never had, and no line about a bug already fixed.

As an operator, my lanes ship no tautological label, test, or UI component, one that only restates what the screen, the code, or its own setup already says, so nothing in my product costs upkeep while adding or proving nothing.

As an operator, my lane agents never stall at a permission prompt nobody in their pane answers for a command they could have run another way, so my box watch shows no agent blocked by one.

As an operator, my lane owners act only on review findings their reviewer has checked against the code: a review reaches the owner as the reviewer's one verdict, never as the raw findings of a pass it ran.

As an operator, every octo-lite agent on any of my boxes links each fact, rule, or decision at its one source and makes each change or fix there, never restating it or correcting a copy, so nothing my agents write drifts from its source.

As an operator, a question I put to a lane or to the fleet operator comes back as a very easy to digest executive summary I take in within minutes on my phone: it leads with the answer, gives each finding as a plain sentence beside the chart, numbers, or examples that show it, and asks each decision it needs as one question with its answers offered and its pick marked; I read it in Proof and comment on any part of it where I read it, so I decide without reading the research and my comments reach the lane.

As an operator, every executive summary comes with a research findings document one press away holding every finding the research made, each linked to its source at the exact place, dated, and labeled by how far it can be trusted, with the plan the research set out with, each source it could not read, and each direction that came to nothing named, so I can check any claim of the summary at its source and no later round repeats a dead end.

As an operator, every agent that answers me a question in writing, a researcher, a lane owner, or the fleet operator, writes it as the same executive summary and research findings from one report skill, published in Proof where I comment on it, so every report reads the same way and my comments reach the agent that owes me the answer, the lane's owner or, for a report outside any lane, the fleet operator.

As an operator, my researcher goes to the best sources for my question: the papers that bear on it, found across the scholarly literature and read, not skimmed; the current best practice of the people and teams leading the field, dated so I see what is current; and X, where practitioners and researchers often say first what they found, so the summary rests on evidence rather than on what someone wrote about it.

Acceptance criteria

Given an operator with an accepted spec in a lane, When the lane owner runs implement-spec to completion and the operator opens the lane's PR, Then that one PR shows every ticket's work, a clear review, and passing required checks, ready for the operator's review.

Given the fleet operator and a live lane owner, When the fleet operator sends the lane owner a prod, Then the operator's hand-off file gains one prod line naming the lane, proven by a unit test: no screen shows it.

Given the fleet operator woken by an action event that asks it to start a lane, When it starts that lane, Then the operator's hand-off file gains one start line naming the lane's issue and the event, proven by a unit test: no screen shows it.

Given the fleet operator woken by an action event that asks it to file an issue, When it files that issue, Then the operator's hand-off file gains one filed line naming the new issue and the event, proven by a unit test: no screen shows it.

Given a lane owner with a choice for the human to answer on a review page, When it sends the human that page's review link, Then the lane's hand-off file gains one gate line asked, naming the gate answer, the verb Answer, and that link, proven by a unit test: no screen shows it.

Given a lane owner whose lane's QA is skipped, When it sends the lane's merge ask, Then the lane's hand-off file gains one gate line asked, naming the gate merge, the verb Accept and merge, the PR as its link, and its QA call in words, proven by a unit test: no screen shows it.

Given a lane owner with a question for the human that has two answers, When it sends the human the question, Then the lane's hand-off file gains one gate line asked carrying why it asks, its evidence, and both answers, each with its own line saying what choosing it does, proven by a unit test: no screen shows it.

Given a lane owner whose lane is ready to merge, When it sends the lane's merge ask, Then the lane's hand-off file gains one gate line asked carrying why it asks, its evidence, and the answer Accept and merge with its own line saying what choosing it does, proven by a unit test: no screen shows it.

Given a lane owner whose spec is ready for review, When it sends the spec's review link, Then the lane's hand-off file gains one gate line asked carrying why it asks and the answer Accept spec with its own line saying what choosing it does, proven by a unit test: no screen shows it.

Given a lane owner whose lane served a report under review that is removed before merge, When the owner closes the lane, Then before its review rows are removed the lane's PR body holds a permalink to that report at the last commit holding it, proven by a unit test: no screen shows it.

Given a lane owner waiting on an implementer, When the owner consumes the implementer's result, Then the lane's hand-off file gains one attempt line naming the worker's role, ticket, pane, and commit, proven by a unit test: no screen shows it.

Given a lane owner whose worker's result is consumed, When the owner closes that worker's tab with what the close prints appended to the lane's hand-off file, Then the lane's hand-off file gains one closed line naming that tab, proven by a unit test: no screen shows it.

Given a lane owner with an idle worker, When the owner parks that worker with both what the park prints and its error output appended to the lane's hand-off file, Then the lane's hand-off file gains one closed line and one parked line and nothing else, proven by a unit test: no screen shows it.

Given an operator whose kept consent answer refuses push, When the lane owner runs implement-spec to completion, Then the owner's report to the operator names the local integration head that holds every ticket's work.

Given an operator whose kept consent answer refuses push, When the lane owner runs implement-spec to completion, Then the lane's work stands at a local integration head and no lane branch is pushed, proven by a unit test: no screen shows it.

Given an operator whose lane owner may push and is shaping a new spec, When the owner commits the spec's first draft and sends its review link, Then the repository's remote shows the shaping branch at that commit and a draft PR for it.

Given an operator whose lane owner may push and has a spec in review, When the owner commits a spec change from that review, Then the repository's remote shows the shaping branch at that commit.

Given an operator whose lane owner's worktree has left its branch holding two new spec commits, When the owner reports them pushed and the spec ready for accept, then the operator opens the lane's PR, Then the PR's head holds both commits.

Given an operator with a lane whose spec review page shows a commit the lane's PR branch lacks, When the operator presses Accept spec, then the owner records the receipt, then the operator opens the lane's PR, Then the receipt names that commit and the PR's head holds it.

Given an operator with a ticket whose behavior the spec on main already states, When the lane owner runs implement-spec on that ticket to completion and the operator opens the lane's PR, Then no spec review was asked, and that one PR shows the ticket's work, a clear review, and passing required checks, ready for the operator's review.

Given an operator with a lane's spec under review, When the operator accepts the spec in chat with the fleet operator, the fleet operator records it, and the operator opens the lane's PR, Then the PR shows a receipt comment from the fleet operator, not from the lane owner.

Given an operator who told the fleet operator in chat that a lane's spec changes are accepted ahead of review, When the lane's owner sends the fleet operator its spec's review link, then the operator opens the lane's PR, Then the PR shows a receipt comment from the fleet operator quoting the operator's words and naming that spec at the commit the owner sent.

Given an operator with a lane whose two specs are under review, When the operator accepts both in chat with the fleet operator, the fleet operator records it, and the operator opens the lane's PR, Then the receipt comment names each spec by its full repository path, each followed by at and the accepted commit.

Given an operator with a lane's PR whose merge ask is out and whose acceptance receipt cannot be posted (needs an induced failure: posting the PR comment fails), When the operator tells the fleet operator to merge it, then opens the lane's PR, Then the PR is still open and not merged.

Given an operator with a lane's PR whose checks are still running, When the operator tells the fleet operator to merge it once checks pass, then the lane pushes a new commit to the PR before they pass, then the operator opens the lane's PR, Then the PR is still open and not merged at the new commit.

Given an operator with a lane's spec under review, When the operator accepts the spec in chat with the fleet operator and the fleet operator records it, Then the box holds no record of that acceptance besides the PR's receipt comment, proven by a unit test: no screen shows it.

Given a lane owner delivering a ticket graph, When the owner moves a ticket to its next state, Then the lane record holds only its lane keys and no ticket entry, proven by a unit test: no screen shows it.

Given an operator with a lane owner delivering a ticket graph, When the owner moves a ticket to its next state, then the operator opens that ticket in the tracker, Then the tracker shows the ticket's new state.

Given an operator with an accepted spec in a lane whose spec issue is filed, When the lane owner files the spec's tickets with implement-spec, then the operator opens the lane's PR, Then the PR body holds one Closes line naming the spec issue and one naming each ticket.

Given a live lane owner and a fleet operator started in place of the one that launched its lane, When the new fleet operator takes over the fleet, Then the owner's pane shows a message from the new fleet operator naming that operator's pane as the one to report gates and completion to.

Given a live lane owner whose lane has no lane record and a fleet operator started in place of the one that launched it, a fixture that must be added to provide it, When the new fleet operator takes over the fleet, Then the lanes directory holds a record for that lane naming the owner's pane, which no screen shows.

Given an operator with a lane's PR ready to merge, When the operator tells the fleet to merge it and the PR merges, Then the box holds no record of that acceptance besides the PR's receipt comment, proven by a unit test: no screen shows it.

Given an operator with a lane's PR ready to merge, When the operator tells the fleet to merge it, the PR merges, and the operator opens the PR, Then the PR shows one receipt comment quoting the operator's words and the accepted commit.

Given a lane owner whose QA capture shows a criterion failed because the product does not do what it states, When the owner triages that failure and the operator opens the lane's issue in the tracker, Then the tracker shows a repair ticket under that issue naming the criterion, worked by a new implementer.

Given a lane owner whose QA capture shows a criterion failed because the product does not do what it states, When the owner has the repair integrated, then sends the lane's merge ask, then the operator opens the PR it links, Then the PR body lists that criterion as a code fault with its repair ticket and its outcome in a recapture at the repaired head.

Given a lane owner whose QA capture shows a criterion failed because the capture never reached or showed the state it names, When the owner fixes that cause, then sends the lane's merge ask, then the operator opens the PR it links, Then the PR body lists that criterion as a capture fault with the cause fixed, the commit that fixed it, and its outcome in a recapture of just that criterion.

Given a lane owner whose QA capture shows a criterion failed in old code the lane did not change, with a consequence for its users, When the owner sends the lane's merge ask, then the operator opens the PR it links, Then the PR body lists that criterion as outside the change with that consequence, to file at lane close, and the PR is ready for review.

Given a lane owner whose QA capture shows a criterion failed, When the owner sends the lane's merge ask, then the operator opens the PR it links, Then the PR body lists that criterion with what the judge saw, whose decision it was and the head it was judged at, its triage, its cause or reason, and its outcome.

Given a lane owner whose QA capture shows a criterion failed where the judge reached the state it names and saw the product not match it, When the owner triages it as a capture fault, then sends the lane's merge ask, then the operator opens the PR it links, Then the PR body lists that criterion as a capture fault naming the specific way the capture went wrong.

Given a lane owner whose QA bundle carries a criterion's failure from an older head, When the owner sends the lane's merge ask, then the operator opens the PR it links, Then the PR body lists that criterion as judged at the merge ask's head, never as carried.

Given a lane owner with a PR to capture, When the owner runs a QA capture of that PR and the capture publishes its bundle, Then the QA program lists none of that PR's environments running.

Given a lane owner whose PR's environments went down after its first bundle, When the owner runs a recapture of that PR at a new head and the recapture publishes its bundle, Then the QA program lists none of that PR's environments running.

Given the fleet operator and a Bitbucket release the plugin watch reports red, When the fleet operator receives the watch's report, Then Herdr shows a new lane space for a fix of that release.

Given the fleet operator with a lane's accepted PR to merge, needs an induced failure: the target's main CI fails after the merge, When the fleet operator merges the PR, then main's CI run ends, Then Herdr shows a new lane space for a fix of the target's main.

Given the fleet operator and a human who asks it to launch a self improvement lane on a goal the human names in a project, When the fleet operator acts on the ask, Then Herdr shows a new lane space for that goal holding its steward and the three scientists the steward spawned.

Given the fleet operator and a human who asks it to launch a self improvement lane naming no goal, When the fleet operator acts on the ask, Then the fleet operator's pane shows one question to the human asking which goal the lane works on, with its answers offered and its pick marked.

Given the fleet operator and a human who asks it to launch a self improvement lane on a goal of the workbench's own, such as Jev's precision on its eval set, When the fleet operator acts on the ask, Then Herdr shows a new lane space for that goal holding its steward and three scientists.

Given a project whose instructions declare a goal with the check that scores it, a fixture that must be added to provide it, When the human launches a self improvement lane on that goal and its team sets its eval, Then the lane's experiment log names that check as the eval, which no screen shows.

Given an operator with a project whose instructions declare no check for the goal the operator names, When a self-improvement lane on that goal writes one and its steward sends the merge ask, then the operator opens the PR it links, Then the PR adds that goal with its check to the project's instructions.

Given a self-improvement lane on a goal only live users can score, such as a product's checkout rate, a fixture that must be added to provide it, When the team sets its eval, Then the lane's experiment log names as the eval a check that scores the goal on the box, such as a replay of recorded traffic, and no experiment's result comes from live traffic, which no screen shows.

Given a self-improvement lane whose scientist's experiment beats the champion and fails a test of the code it touched, When the scientist records the result, Then the lane's experiment log shows that experiment discarded, naming the failed test, and the lane branch does not move to it, which no screen shows.

Given the fleet operator that launched a self-improvement lane, When the lane's steward spawns its scientists, Then the lanes directory holds one record for the lane, naming the steward's pane as its owner, and none for a scientist, which no screen shows.

Given a self-improvement lane whose scientists work two hypotheses, When one scientist runs an experiment it proposed, Then the lane's experiment log holds, before that experiment's result, a critique of its proposal saying go from a scientist working the other hypothesis, which no screen shows.

Given a self-improvement lane whose experiment log holds a dead end, a fixture that must be added to provide it, When a scientist proposes the same change again without saying what differs, Then the lane's experiment log holds a critique of that proposal saying no and naming that dead end, and no result for it, which no screen shows.

Given a self-improvement lane of three scientists, When one scientist records an experiment that failed, Then the lane's other scientists and its steward each receive a teammate's message from it naming that result, recorded in their conversations, which no screen shows.

Given a self-improvement lane whose hypothesis had four experiments in a row gain nothing, a fixture that must be added to provide it, When a scientist records a fifth under it that gains nothing, Then the lane's experiment log shows that hypothesis retired with what it taught, and no later proposal names it, which no screen shows.

Given a self-improvement lane, When its first round ends, Then the lane's experiment log shows every hypothesis of that round opened by a scientist, and the steward's messages to its scientists name no hypothesis and no experiment, which no screen shows.

Given a self-improvement lane on a goal whose check's items mostly lack the data it needs to run the code under improvement, a fixture that must be added to provide it, When the team sets its eval, Then the lane's experiment log counts the items lacking that data and holds no experiment changing that code until a change disabling it moves the eval's main number, which no screen shows.

Given a self-improvement lane whose eval, with every item the code under improvement reaches scored right, would not beat the champion by more than its noise, a fixture that must be added to provide it, When the team sets its eval, Then the lane's experiment log holds no experiment changing that code, which no screen shows.

Given a self-improvement lane whose eval lacks an input only the human can give, such as criteria text its spec owns, a fixture that must be added to provide it, When the team finds the missing input, Then the operator receives one question from the steward naming that input, with its answers offered and the steward's pick marked.

Given a self-improvement lane whose scientist's experiment beats the champion by less than the eval's noise, When the scientist records the result, Then the lane's experiment log holds a second run of that experiment, and the lane branch moves to it only when both runs beat the champion, which no screen shows.

Given a self-improvement lane in a round with no keep so far, When the round's last open hypothesis retires, Then the operator receives the steward's stop report naming no gain as its reason, with the lane's spend.

Given an operator with a running self-improvement lane, When the operator tells the fleet operator to stop it, Then the operator receives the steward's stop report naming the operator's stop, with the lane's spend and its gain.

Given an operator with a running self-improvement lane, When its steward sends the operator a status report, Then the report names the lane's spend so far.

Given an operator with a running self-improvement lane whose team needs an input only the operator can give, When its steward sends the operator that question, Then the question names the lane's spend so far.

Given a self-improvement lane whose scientist runs an experiment sweeping many settings, When the scientist records its result, Then the lane's experiment log gains one result line for that experiment, which no screen shows.

Given an operator with a stopped self-improvement lane whose champion beats its baseline, When the steward sends the lane's merge ask, then the operator opens the PR it links, Then the PR body gives the main number at the baseline and at the champion on the dev and held-out splits, each keep with its gain, and the lane's spend.

Given an operator with a self-improvement lane whose kept change alters a value its project's spec states, a fixture that must be added to provide it, When the steward finishes the lane, Then the operator receives that spec change's review link before any merge ask.

Given an operator with a self-improvement lane stopped with no keep and its eval unchanged from main, When the steward closes the lane, Then the operator receives the close report linking the lane's report and naming no PR to merge.

Modular boundaries

octo-lite owns and publishes the lane record and hand-off formats; roles write them at the named moments. The caller-facing seam is the files in each Herdr session's state directory, plus the lane's Herdr space and spawn names for workers. Direction is self-contained: readers such as a board depend on the format and locate a session's files from the Herdr session key; octo-lite names no reader. Observable scope: file contents and the lane's space membership.

Role contracts and skills own shaping, delivery, review, and gates. The caller-facing seam is the role contracts in agents/ and the skills in skills/. Direction is downward: roles use the wrappers, Herdr's own agent state, and the lane record format; external providers are Linear, GitHub, Spec Chat, whose mockup set is each changed screen's accepted target and whose mockup page shows a first round's directions side by side, the Stageshow skill, whose story, cursor, and framing rules octo-lite's round video recorder follows and whose fit check and rehearsal each round gets, and annotateanything's QA capture program, whose rules (when QA runs, outcomes, owner triage) live in its jev-capture spec under QA rules, while the finish rule that ends each failure, like each review note, is octo-lite's. Observable scope: tickets, the PR, and the lane record.

The filing rule and the repo-health skill own turning review notes and health findings into health tickets. The caller-facing seam is the health tickets in the box's tracker, with their Health label and priority, and the tagged notes in each PR body. Direction is external-provider: the filer depends on the tracker the lanes already file in, and octo-lite names no reader of health tickets. Observable scope: health tickets, their labels, priorities, comments, and states, and the pass's one message.

The orchestrator contract's steward rule and the scientist contract own a self-improvement lane's team: its experiment log, its eval's headroom, critique, keeps, and stops. The caller-facing seam is the experiment log in the lane's notes, the lane branch whose head is the champion, the steward's reports and gates, the scientists' spawn names in the lane's space, and the goals a project's AGENTS.md declares. Observable scope: the experiment log, the lane branch and PR, the lane's space, and the steward's messages.

The caller-facing seam is the report folders in each Herdr session's state directory, their paths, their summary.html, and the marks the page rules name, plus the scope whose owner a comment wakes: the lane's review slug, whose row its owner registers, or the fleet operator's own scope row. Roles

agents/*.md are the hand-written role contracts: orchestrator, implementer, integrator, code-reviewer, researcher, scientist, and meta-operator; none pins a model.

Every spawned agent with a role contract (orchestrator, implementer, integrator, code-reviewer, researcher, scientist, or meta-operator) loads it: Claude through --agent ROLE, Codex as developer instructions, and pi as an appended system prompt, via herdr-spawn --role ROLE.

An implementer loads by name each skill the target AGENTS.md declares under Repo skills: that bears on its ticket, beside the octo-lite skills its contract lists; a declared skill outranks an octo-lite skill only where it states its own rule, as a project's UI skill outranks frontend-design loaded beside it (layout explains). Its report to the owner names the declared skills it loaded; a declared skill it needs that does not resolve is a missing environment, reported as a blocker.

An implementer or prototype worker that designs or builds a screen avoids unnecessary secondary labels and descriptions and lets the layout do the explaining. Grouping, order, alignment, and spacing show what each part is and how the parts relate, and a part gets a caption, helper line, or subtitle only where the layout cannot show it. An accepted mockup's copy still decides each screen it draws (mockup). The frontend-design skill states this rule once, where it guides UI work; a project's own UI skill, loaded beside it, outranks it only where that skill states its own rule for labels and descriptions (repo skills), so loading one never drops the rule.

An implementer or prototype worker that writes a user-facing string, such as a label, hint, empty state, toast, confirmation, or button text, first asks whether the string should exist, and cuts each string or clause that should not before phrasing what stays. A string should not exist when its user would never have wondered about what it says, when the label, field, or value beside it already says it, or when it rules out a failure, such as a bug already fixed, in place of describing a behavior; it stays only where its user cannot act without it, such as a consequence at the moment of choosing, a scope fact they cannot see, what a blank state means and what to do next, or the unit of a bare value. A code reviewer judges each user-facing string a diff adds or changes the same way, and lists each one that should not exist as a note to fix in this PR (notes), naming its file and line, its cut or rewrite, and in a few words why. An accepted mockup's copy still decides each screen it draws (mockup). The clean-copy skill states this rule, the implementer and code-reviewer contracts list it among their skills, and the frontend-design skill names it for every user-facing string, beside the layout explains rule.

Tautological labels, tests, and UI components are harmful: an implementer or prototype worker writes none, and removes each one it finds in what its ticket changes, never keeping or updating it. A tautological label restates what the screen already says, judged by the clean copy rule; a tautological test only re-asserts what the code or its own setup states, such as a mock's return asserted back, a constant pinned to itself, or contract prose pinned by a pattern; a tautological UI component only passes through to another and adds nothing. A code reviewer lists each one a diff adds or changes as a note to fix in this PR (notes), naming its file and line and what it only restates. The implementer contract states this where it writes code and tests, pointing at the clean-copy skill for labels, and the code-reviewer contract where it judges a diff.

An implementer implements the general rule the spec states, so every case the rule covers holds, not only the criterion, fixture, label, or evaluation case at hand. A code reviewer blocks code keyed to the instances at hand, such as a named criterion, fixture, label, or evaluation case, in place of the rule the spec states: it passes the check while the behavior stays wrong.

An implementer working test-first takes the seams it tests at from the canonical spec, never from the user, since no human loop runs mid-implementation, and writes no test at a seam the spec does not name. Each seam a spec names is a deep-module seam, a small interface over large behavior; a spec whose seams are not is a shaping defect that goes back to shaping, and the implementer never invents seams. The one patch octo-lite carries on the pinned tdd skill (ADR 0006) states this where the skill picks seams.

An octo-lite agent mostly runs in a pane nobody watches, where a command its CLI cannot rule out as safe stops it at a permission prompt that nobody answers and that refuses itself minutes later, so every octo-lite agent runs its shell work in forms that raise none. It writes or edits a file with its own file tool, such as Claude's Write and Edit, and runs a script by writing it to a file in its scratch folder with that tool, then running that file, never passing a script or a file's text to the shell through a heredoc. It removes nothing from its scratch folder, which goes when it is closed (scratch end): a run that needs a clean folder makes a fresh one with mktemp -d in place of emptying an old one. Any other file it removes is one it made, removed by its literal path, never by a glob, a variable, or a folder's whole contents (own only). The every-role part states this once, for every role, and every recipe a contract or skill gives follows it.

Link to the source, edit the source: every fact, rule, or decision has one source, and anything else that needs it links that source at its anchor and never restates it, so nothing drifts from it. A change, or a fix for a wrong line, is made in the source, never as a correction beside a copy. It holds for every octo-lite agent on every box and repository, whatever operating model the box gives, so the every-role part states it once, as its first rule, never a copy per contract. A role contract or skill that restates it, whole or in part, drops the restatement, since every agent loads that part.

A repo-wide rule is an every-feature acceptance criterion its home spec marks as a project rule, Spec Chat's data-project-rule mark, which Jev checks against every spec at shaping and each review hand-off names under rules checked. A line in a target AGENTS.md only points implementers at such a criterion; a rule stated only there, or in spec prose outside a criterion, is not yet a repo-wide rule. When a lane's spec settles a cross-cutting decision, such as an identity key, an exposure contract, or a single source, that no project-rule criterion states, its owner names the decision and its home spec in its review hand-off. The fleet operator then asks a lane on that home spec, this lane when the home is its own spec, for a criterion marked as a project rule that states the decision, so Jev enforces it from the next shaping, and that spec's acceptance is recorded by the PR receipt like any other. A general rule the human states to the fleet operator in chat, such as one saying always, never, in general, or regardless of, that is neither a design-system convention nor a standing rule for how agents work, takes the same route: when no project-rule criterion states it, the fleet operator asks the human one question, whether to make it a criterion marked as a project rule in the home spec it names, with its recommendation, and on yes asks a lane on that home spec as above. The set stays small: a decision or rule earns a project rule only if it is a promise the product or system makes, such as tabs keeping their place, consent records reading plain stable values and never rendered text, or an identity key, that a user would notice breaking or a later feature could plausibly break. Nothing here waits on Jev: when Jev is off or backed up, every marked criterion still binds the briefs that cite it, an owner still names a settled decision in its review hand-off, and the fleet operator still offers a rule stated in chat. A review hand-off whose spec's Jev checks did not answer says so and names, by spec and anchor, each marked rule left unchecked, so a skipped check is never silent. The meta-operator and orchestrator contracts and the implement-spec skill state this where they ask, shape, and brief.

A design-system convention, how a product's UI looks or moves or which shared part draws a pattern, such as text changes morphing or every loading state using the shared skeleton, is never a project rule. It lives in the product's design system: its one source, such as a DESIGN.md, the shared part that carries the behavior, and a code check, such as a lint rule or a design-rules test the repository's suite runs, that fails on a hand-rolled version, so code enforces it exactly. A lane whose spec settles one adds all three in its PR, and its owner never names it in a review hand-off as a decision for a project rule. A repository keeps at most one project rule for its design system, that every feature's UI uses the design system's shared parts, its criterion pointing at the design system, so a spec that adds a shared part needs no rule of its own. A design-system convention the human states in chat gets the fleet operator's one question offering it to the design system, with its recommendation, never as a project rule. A repository whose specs mark design-system conventions as project rules folds them: asked for its repo-wide rules, the fleet operator names those as ones to fold and asks the human one question, whether a lane on the design system folds them, adding each one's code check, marking the one design-system rule, and removing their marks in one PR. A project's root AGENTS.md names its design system's one source, so every agent finds it from there. A code reviewer reads that source and blocks a part a diff draws by hand, or as a near copy, where a shared part draws it, naming that shared part, and a shared part a diff adds without its entry in that source stating its convention, or without its code check, naming what is missing, since either leaves a pattern no check of the design system holds. The meta-operator and orchestrator contracts and the grill-with-docs skill state this where they ask, shape, and record rules, and the code-reviewer contract where it judges a diff.

A standing rule is one the human sets for how agents work from now on, such as how owners report or what a review link names, as distinct from a repo-wide rule, a promise the product makes, and a design-system convention. Its one home is the role contract or the operating model that governs that work, so there is no separate rules file: the fleet operator files it in the box's tracker as an issue against that contract or operating model, and its reply to the human names the issue filed. The rule reaches agents once that change merges: each lane started after it loads it at start, and a running owner, or the fleet operator itself, gets it as a contract change. The fleet operator never sends a standing rule to running lanes as messages, since a message reaches only the agents running now and sits beside the contract each loaded, not in it. Only a lane whose current step the rule changes right now is told, that lane alone. The meta-operator contract states this where it handles a rule the human states.

An agent loads its role contract and the operating model only when it starts, so a message asking a running agent to re-read them leaves the instructions it loaded in place beside the new text; the fleet operator never sends one. A merged change to a role contract or the operating model reaches a running lane owner by parking and resuming it, since a resume starts the owner with them as they are then, its conversation kept. An owner parked at a human gate or on another lane gets the change when its wake resumes it. A working owner whose remaining steps the change touches is parked at its next idle point and resumed at once by a message naming the change; one whose remaining steps it does not touch is left running. A lane started after the change gets it at start. The fleet operator is no lane owner, so nothing parks it: a change to the meta-operator contract or the operating model reaches it by a reload it starts on itself once its pull of the box's live install clones holds the merge. Once the human has gone quiet, never while the human is in dialogue with it, the reload has it write its brief, then replaces it in its own pane with a fresh session under the same goal, which opens on a message naming the change and reads that brief first, so it also sheds the context its old conversation built up. Its pane stays the one the session's operator.toml names, so every report sent to it still lands. The meta-operator contract states this where it handles a merged change to a contract or the operating model.

The fleet operator's brief, operator.brief.md beside operator.toml, is the short hand-over it writes for the fresh session a reload starts: what is in flight and recent, its open lanes and their gates, questions put to the human and not yet answered, each owner whose reply it still awaits, since its waits end with the old session, and decisions not yet landed anywhere durable, plus the high-level context. It points at the durable sources, lane records, operator.handoffs.jsonl, the tracker, and pull requests, rather than copying them. It is no second rules store: a standing direction the human gave about how the fleet operator works is filed as a standing rule and lands in its contract, and until that merges the brief names its issue rather than restating it. The fresh session waits again on each owner the brief names and asks again none of the questions it names, which the human answers in its pane as before. It is its own file because no store holds prose hand-over context for one whole session: operator.toml is control state, operator.handoffs.jsonl an append-only trace, a lane's notes belong to one lane, and the old session's transcript is what the reload leaves behind; each reload rewrites it.

A shared surface is a part of a product every screen or feature builds on, such as its design system: a UI-system spec, its DESIGN.md, and its shared components. One lane at a time edits a shared surface: a lane whose work edits one that another open lane edits waits on that lane, its record's waiting_on naming that lane's issue, parked until that lane's PR merges, then merges main and goes on. The fleet operator keeps at most two lanes open on one shared surface, or the cap the human sets, and holds any further one as an unstarted issue until one of them merges. An owner whose spec turns out to edit a shared surface tells the fleet operator before editing it. An app-wide UI change, one that reaches every screen or many at once, such as wrapping every in-place text change or every loading state, merges one at a time: the next merges only once main's required checks and the project's smoke check pass on the last one's merge. The smoke check is a cheap capture of the product's main screens on each merge that touches them, kept on when full QA is off; it is a delivery step of the project's QA, whose rules for when it runs, what it captures, and its outcomes live there, as annotateanything's live in its QA rules, never in octo-lite, and a project whose QA declares none checks main's required checks alone. The meta-operator contract states this where it starts lanes and orders merges, and the orchestrator contract where it shapes.

A problem of the box is a part of it a role works without because it is missing or out of date, such as Stageshow not installed, a review service whose lane command takes no --prototype, or an after-pull step a spawn printed as failing. The lane owner reports each problem of the box to the fleet operator once, the first time it meets it in a worker's report or a step of its own, naming the problem and the step that fixes it, besides saying so wherever its role contract says the fallback is said. The fleet operator relays each problem of the box to the human once, however many lanes report it. The orchestrator contract states this where it reads worker reports and spawns, and the meta-operator contract where it writes to the human.

Before it finishes, every octo-lite agent answers one question: Did anything about the system annoy you? On no, it records nothing and finishes; on yes, it gives one sentence saying what annoyed it. Each role answers in its last step: a worker in its last report, as one line starting Annoyed:; a lane owner as it closes its lane, after its last worker's closed line and before its files move into the archive; and the fleet operator before each reload, as it writes its brief. The agent whose log a report reaches records the sentence there as one complaint line: the lane owner in its lane's hand-off log for its workers and itself, and the fleet operator in its own log for itself and each agent that reports to it. A complaint is box state, never repository truth, so it is one more kind of line in those logs and no new store; each log keeps its one writer. It is asked in the role contracts, the point of action, and by no hook, since a hook run as an agent finishes could make it answer only by stopping it from finishing (hooks only inform). A complaint is no report, review note, or ticket: no agent is sent a message for it, and nothing files it. The fleet operator reads a lane's complaint lines when that lane closes and relays each to the human in its message telling of that close, one plain line naming the agent and its sentence, and its own and those it recorded in its next message to the human; a complaint naming a problem of the box it relays as that problem, once with the step that fixes it. The implementer, integrator, code-reviewer, and researcher contracts state this in their last step, the orchestrator contract where it closes its lane, and the meta-operator contract where it reloads and writes to the human.

The fleet operator relays to the human only gates, decisions, real blockers, lane closes with their complaints, and each problem of the box once, plus the line telling of an addendum receipt; progress gets one line or nothing. A merge ask it relays keeps every See it line the owner sent, without the human asking. Questions that each have a clear recommended answer go to the human together, as one question asking whether to take the recommendations, with one plain line per question naming its recommendation; a yes takes them all, and the human may answer any one differently. A question that weighs real trade-offs goes alone, never inside that bundle. The meta-operator contract states this where it writes to the human.

Every status report a lane owner sends the operator carries its ETA: the time it expects its next ask of the human, such as the review link, an answer, or the merge ask, as a UTC time with the time from now, such as 19:40 UTC, in about 2 h, which reads right in any time zone, how sure it is, and what could slip it, most likely first. When that time moves later than the one it last sent, the owner sends a report with the new time and what moved it, so the human never waits on a stale time. The fleet operator's line telling the human of a lane's progress carries that lane's latest ETA. The orchestrator contract states this in its output, and the meta-operator contract where it writes to the human.

Every heavy job of a lane, such as a full test suite, a QA capture, a build, or a recording, runs under the box lock, whatever the box's load: it takes the lock as it starts and lets it go when it ends, reporting its wait. An executive summary is one very easy to digest page that a reader who is not an engineer takes in within minutes, on a phone or a desktop, carrying only what bears on its question. Its headline states the answer, with one plain line under it and at most three numbers that carry it, each beside what it compares to, such as a coin flip. Each section's heading states its finding as a sentence, never a topic label, and shows that finding in the one form that makes it plain, such as a number, a chart, a comparison, a ladder, or a few real examples, so the findings decide the sections and their forms, never a fixed template. Each decision it needs from the reader is one question naming its answers, the writer's pick first with a one-line reason, which the comment control offers as starters, so the reader answers in place. Every claim links the finding behind it in the research findings. It closes with one line on how the research was done: what it read and whether it changed anything, what it cost, whose names it shows, and when. It shows no customer's name or personal data, and draws in the target product's own design system when the target declares one, so it reads as the product's own document.

The research findings are the supporting page: every finding the research made, whether or not the summary uses it, one anchored block each, giving the finding in one sentence, its source linked at the exact place, such as a page's anchor, a post, a file's line at a commit, or a query with what it read, the date it was read, and its trust label. The trust label is paper, a peer-reviewed study; preprint, a study not yet peer reviewed; primary, from the source's own owner, such as a platform's own help page; practitioner, a named person's or team's own account of what they do or found, such as an engineering post or a post on X; vendor, a seller's claim about itself; or unverified, from memory, when the source could not be fetched. A finding links its source and never restates another finding. It opens with the research's plan: each answer the question could have and the evidence that would settle it. It ends with its dead ends, each direction the research tried that came to nothing, such as a search that found nothing, a source that did not hold up, or an answer the evidence ruled out, with what was tried and why it failed, and then its gaps: each source the research sought and could not read, why, and what that leaves unknown.

A researcher is the deep research worker, under the researcher contract: it answers a question for a human who decides, such as the current best practice for an approach or what a product's users are doing, and makes its answer a report with the report skill. A lane owner spawns one for each research question its brief or the human puts to its lane, the research coming before shaping when its answers decide what to shape; the fleet operator spawns one itself for a question no lane owns, such as what a product's users are doing, in no lane's space, and owns its report as a lane owner owns a lane's. It writes only its report, so it needs no worktree, as a code reviewer needs none. It reads code, outside sources, and the data its brief names, production data only read-only and only where the brief allows; it changes no product code or data, runs no experiment that needs a build, a model, or large compute, and keeps within the spend its brief caps. The researcher and orchestrator contracts state this where they research and spawn, and the meta-operator contract where it spawns a researcher of its own.

The researcher goes to the best sources a question has, beside the code and data its brief names. Before it searches deep, it writes its plan and critiques it once: it adds an answer or a source the plan left out, and drops a search that could settle nothing, so the research spends its effort only where evidence can decide. Where published studies bear on the question, it answers from them: it searches the scholarly literature itself, its indexes and each relied-on paper's references and the papers citing it, and reads each paper the summary relies on, its method and results, never only its abstract; that paper's finding names its authors, year, venue, link by DOI or preprint id, what it measured and on how many, and the number the summary uses. It finds the current best practice of the people and teams leading the field, from their own documentation, engineering posts, standards, and talks, newest first: a practice's finding names who follows it and when they said so, and any practice it replaced, so the reader sees what is current rather than what was. X is one of its sources, since practitioners and researchers often post there first what they found or now do: it searches X for the question through X's API with the box's X token, reads each post it relies on in full, and treats a post as a lead to that person's paper, repository, or longer account wherever one exists. The researcher contract names the indexes and services it searches and the access each needs.

No agent carries the token from its start: the researcher contract, which each researcher loads at its start, names that file, and the researcher reads it before each X search, so a new token works at the next search with no restart. The researcher never writes the token anywhere: no page, report, log, or command line it shows holds it. A missing token, and a token X refuses, such as one revoked or on a plan without search, leave X search unread: the researcher reads only the posts it finds linked elsewhere, the research findings' gaps name X search with the reason, for a refusal X's own answer, and its last report to the owner names it. The owner reports it once as a problem of the box, naming the fix the setup check names.

A project declares its goals in its AGENTS.md, under Goals:, one line per goal naming it and its check's command, beside the commands that file already owns; a launch on a declared goal starts from its check, and a lane whose team writes a check for a goal not declared adds that goal's line in its PR, so the next lane on it finds the check.

It is octo-lite's one orchestration beside the ticket graph implement-spec delivers, by the human's decision, since a ticket graph fixes its steps before work starts while an experiment's next step comes from the last one's result. Everything else it runs on is octo-lite's own or a peer's already: Herdr spawns and messages, the lane's space, record, hand-off log, and notes, the box lock, annotateanything's lane spend, and the report skill whose pages Proof shows.

The lane's owner, the pane its lane record names, is its steward: the lane owner under the orchestrator contract, which on a self-improvement lane shapes no spec, files no ticket graph, runs no experiment, and never names a hypothesis or an experiment to a scientist. It spawns the scientists, holds the lane branch and the PR, reads the lane's spend, stops the team, and sends the human every question, review link, and merge ask, each with its gate line, as any owner does. It writes the lane branch only by moving it to a scientist's keep, as an owner merges a prototype worker's commit (prototype). The fleet operator launches, watches, parks, and resumes it, and hears its gates and reports, as it does any lane owner's; scientists report to the steward, never to the fleet operator.

The steward spawns three scientists into the lane's space, each under the scientist contract in its own worktree off the lane branch and numbered by its spawn name, as scientist1-ann-64: the smallest team in which two hypotheses run at once and each proposal has a critic on the other. A scientist proposes, critiques, runs, and records experiments in turn. What it knows lives in the experiment log, never only in its conversation, so a scientist that dies is spawned again under its name and goes on from the log.

The shared experiment state is the lane branch, whose head is the champion, and the lane's experiment log, experiments.jsonl in its notes: one JSON line per event, appended whole by the scientists and the steward and never rewritten. Every scientist reads the log before each step it takes, so the teams, the dead ends, and the champion's score are read from it and declared nowhere else.

The team's first work is the eval, the goal's check: the one its project declares, else one the team writes in the goal's repository on the lane branch, scoring a dev split and a held-out split when it scores a set of items, its first run on a small sample. The check runs on the box and changes nothing outside it: a goal only live users can score is scored by a check that stands for it on the box, such as a replay of recorded traffic, and no experiment is tried on live traffic, which only the human shifts (gates). Two runs of the champion give its noise. Its headroom is measured next: a change that disables the code under improvement must move the main number by more than the noise, so the eval reaches that code, and the main number with every item that code reaches scored right must beat the champion by more than the noise, so a change can win; each item the code cannot reach is counted with the input it lacks. Until both hold, no experiment changes the code under improvement: the team's experiments build the missing inputs, and an input only the human can give, such as text a spec owns or data outside the repository, goes to the human as one question the steward sends. Once set, the eval is fixed: an experiment never changes it, and a change to the eval is its own proposal, after whose keep the champion is scored again before anything compares to it. The held-out split is scored only when the eval is set and at the finish, so no scientist sees a held-out score while it chooses.

A scientist opens a hypothesis, saying what result would refute it, or joins one by proposing under it; a team is the scientists whose latest proposal names that hypothesis, and nobody assigns one. Choosing from the log, a scientist prefers a direction nobody has tried, a follow-up of what made the latest keep win, and the hypothesis fewest scientists work. A hypothesis retires once five experiments in a row under it gain nothing, its scientist writing what it taught; a round lasts until every hypothesis opened in it has retired, and the scientists then regroup around new ones read from the whole log.

Before an experiment spends tokens, its proposer asks one scientist working another hypothesis, else any other, to critique it, and runs it only on that critic's go. The critic says no, naming why, to a proposal that repeats a dead end without saying what differs, duplicates a running experiment, or changes nothing the eval reaches.

An experiment is one critiqued proposal, run on top of the champion, and one result line, however many settings it sweeps: its runs' own output stays in the scientist's scratch folder. One that loads the box, such as a suite, a training run, or a build, runs under the box lock. It is kept when its main number beats the champion's by more than the noise, every floor holds, and the tests of the code it touched pass; a gain within the noise is run once more and kept only when both runs beat the champion. The scientist sends a keep's commit to the steward, who moves the lane branch to it and pushes; when the branch has moved since the experiment started, the scientist merges the new champion into it, scores it again, and sends it only if it still wins.

The team stops on the first of two: a round ending with no keep, or the human's stop, given to the fleet operator or on the lane's report. The steward then tells every scientist to stop; each records the experiment it is running, starts none, answers the annoyance question, and is closed.

The lane's spend is annotateanything's lane spend, which prices by the box's price table every Claude Code session run from a pane directory of the lane, each claude -p call an experiment makes from a scientist's worktree included; octo-lite keeps no spend record of its own. The steward reads it at every result and names the spend so far in every report and every ask it sends, its merge ask included. A paid service outside Claude that an eval calls, such as Jev's provider, is not in it, so the eval names that service's cost per run.

No budget caps a self-improvement lane's spend, by the human's decision: the team spends the tokens it needs while it gains, and the human, who sees the spend in every report and ask, stops it at will.

The steward pushes the lane branch and opens the draft PR once the branch holds its first commit past main, the check the team writes or else its first keep, then pushes at every keep, as consent allows. A lane stopped with a keep, or with an eval that is new or changed, finishes as every lane does (path, finish rule): main merged once, the full suite, a fresh review and its fix batch, and QA as the target's rules decide, then one merge ask. Its PR body gives the main number at the baseline and at the champion on both splits, each keep with its gain and what made it win, and the spend, and links the lane's report. A kept change that alters a behavior or value a spec states carries that spec's edit in the keep's commit, written by its scientist, and the steward sends that spec's review link to the human for acceptance before the merge ask (gates); one the spec on main already covers rides on that spec's commit, as a single ticket does. A lane stopped with neither closes its PR unmerged, if one is open, and closes on its report.

The lane's report is the executive summary and research findings the report skill writes in its notes, shown in Proof: the summary leads with what the team gained and spent, and the findings hold every experiment with its result, every retired hypothesis with what it taught, and the eval with its headroom.

Repo health

A health ticket is a tracker ticket for one real architecture or cleanliness issue in a repository, in the box's tracker, the one its lanes already file tickets in; no other store holds health issues. It names the issue, its consequence, where in the repository it lives, and each source that raised it: a PR or a health pass. It carries one label of the tracker's Health label group, naming its category, and a priority from its rank. It is filed unassigned, with no parent, in a state not yet started, so it waits in the tracker beside the bugs a human triages and fires off.

The categories are architecture, cleanliness, naming, duplication, test, and docs. A consequence is what the issue will cost or break, named concretely, such as the next change to acceptance must edit four copies. A note or finding that names no consequence stays history and never becomes a ticket.

A code reviewer gives every non-blocking note the end the finish rule gives it, tagged with its category, so a note never buries what matters: a note to fix is marked to fix in this PR, and a note to file names its consequence. The owner has every note marked to fix fixed in the PR before the merge ask, in the one fix batch of the head the review judged (path), whose fix delta review covers it, or, with no blocker, one last batch of its own, which is no fix round but whose delta a fresh reviewer reviews beside the full suite on its head, so no fix reaches the merge ask unreviewed, and lists every note to file in the PR body, tagged as given, so the PR keeps it and a filer reads it there. At lane close, after the PR merges and before teardown, the agent closing the lane, its owner or the fleet operator, files the PR's notes by the filing rule.

One filing rule turns notes and findings into health tickets: one PR's notes at lane close, many PRs' notes in one batch, and a health pass's findings. The filer first reads every open health ticket and the target's current main, then gives each note or finding the first disposition below that fits. Two notes name the same issue when one fix would remove both, whatever their wording. A filing checks only its own notes and findings against main; only the health pass checks the open health tickets themselves against main. Each source, one PR or one pass, files at most five new tickets, highest rank first; the rest stay history, and a later pass that still finds one files it then.

A health issue's rank is its consequence: high when it will cause wrong behavior or block a change, medium when it makes the next change in that area cost more, such as a duplicate, a dead store, or a misleading name, and low when it costs only reading time. The rank is the ticket's tracker priority, so it orders health tickets among the tracker's other work.

The repo-health skill is the repo health pass, fired by hand by the fleet operator, at its own call or when the human asks for one, and never on a timer. The fleet operator starts one fresh agent for it on the target's main checkout; that agent changes no repository file and writes only health tickets. It reads the target's instructions, its specs' modular boundaries, the open health tickets, and the code, and looks across the whole repository for architecture, cleanliness, best-practice, and trimming issues, a deletion first wherever one would do. It checks every open health ticket against main, closing each one main fixed as done, with a comment naming the main commit it was checked at and why the issue is gone, and files its findings by the filing rule. Its result is the tickets, never a report: its one message to the fleet operator names each ticket it filed, commented on, or closed, by key, and the fleet operator relays that list to the human who asked.

The code-reviewer, orchestrator, and meta-operator contracts and the implement-spec skill state these moves where they review, list notes, close a lane, and fire the pass.

Lane record

Octo-lite owns and publishes the lane record format: one TOML file per open lane in the lanes/ directory of its Herdr session's state directory, named by the owner agent name, with the keys below, written at the moments below. A closed lane's record, hand-off log, and notes live in archive/ inside that directory. A lane record's name is never reused, not even after its record is archived: the fleet operator starts each lane under a name no open or archived record has, so one name always means one lane. Readers follow this format; octo-lite names no reader.

The record holds no ticket state: a ticket's state, holder, and repair passes live in the tracker only.

The record lists no workers. A lane's workers are the Herdr agents in the lane's space other than the owner; each worker's pane is its Herdr pane id, and its role and ticket come from its spawn name.

At each hand-off moment the owner appends one line to <lane record name>.handoffs.jsonl beside the lane record, per the hand-off field list; only the owner writes the file, except the parked line for the owner itself, which the operator appends when it parks the owner.

Every line of a hand-off log is one JSON object, appended whole. A reader of hand-off logs skips a line that is not one, naming that log and the line's number once, so one bad line hides nothing else in its log and breaks no other lane.

An asked gate line carries what the human needs to decide from the ask itself, in plain words, each field optional: why, one line saying why the owner asks now, for an answer gate the question and why it comes up; evidence, one line naming what backs the ask, each link in it a full URL; and answers, a list of one to four objects, each answer, a few words naming one way to answer, and line, one sentence saying what choosing it does. The owner writes why with every ask, evidence when something backs it, such as checks passed, a review verdict, or a QA bundle, and answers when the human answers by choosing: each option of a question, Accept spec on a spec review, Accept and merge on a merge ask. A line without them is a complete gate line read by its verb and link, so readers take the fields up before or after owners write them.

Human gates

Spec acceptance, acceptance of delivered work, merge of unaccepted work, preproduction promotion, and live traffic shifts require explicit human instruction.

A spec acceptance the human gives the fleet operator in chat is recorded by the fleet operator at once, as the receipt comment on the PR, and the owner is told; an owner never records it, since that reads as self-approval. A standing acceptance the human gives the fleet operator before the spec head exists is recorded the same way, at once, when the lane owner sends the fleet operator that spec's review link or head, quoting the human's standing words. The fleet operator also runs review-host.py reviewed --id <resource id> for each accepted spec, which moves its review row's base to the accepted commit and records no acceptance.

Every acceptance, of a spec or of delivered work, is recorded once, as a receipt comment on the lane's PR, and everything that needs it reads that comment. The receipt quotes the human's words, gives the date, names what is accepted (the spec or the PR), the exact accepted commit, and who recorded it. A spec receipt starts Spec acceptance receipt: and names each accepted spec once, by its full repository path followed by at and the accepted commit. A spec accepted on the review page is recorded by the owner processing that hand-off, quoting the action; a spec accepted in chat by the fleet operator; delivered work by the agent receiving the instruction, before it merges. A delivered-work receipt goes on the PR before the merge, and the merge commit closes it; nothing else records the merge. Spec Chat records no acceptance: the Accept spec hand-off in its spool is the instruction a spec receipt quotes, never a second record.

On a human instruction to merge, the receiving agent checks that the PR head is the accepted commit and that required checks pass, then records the receipt and merges. Every receipt the merge needs, an addendum receipt included, is on the PR before the merge: when one cannot be recorded, the merge does not happen and the agent reports why. The merge is pinned to the accepted commit, a merge set to run once checks pass included, so a head pushed after the human's go is never merged; a pinned merge that finds a moved head does not happen and the agent reports it. The meta-operator contract and the octo-lite-github skill state this where they merge. It re-checks no QA evidence: a merge ask goes out only after every step it needs, that evidence included.

Where consent allows push (consent), a commit is pushed only when the remote branch holds it: before a message names a commit as pushed, or a spec or PR as ready for accept, its sender fetches the branch and proves each commit it names is an ancestor of the remote head, and a commit that fails, such as one made on a worktree that left its branch, goes onto the branch and is pushed first. A spec receipt is recorded the same way, only once the PR's remote head holds the accepted commit, so a receipt never pins a head missing what the human was shown. The orchestrator, integrator, and meta-operator contracts and the push skill state this where they report a push or record a receipt.

A spec commit after acceptance that is wording-only keeps the original acceptance, with no new review and no new receipt. Wording-only means the commit changes only wording, labels, or anchors: it adds or removes no criterion and changes no stated behavior, value, or outcome. The lane owner decides, and lists each such commit in the PR body with one line saying what it rewords, so the human sees it at the merge gate. A commit the owner cannot plainly call wording-only is not: it keeps the acceptance by an addendum receipt when it only restates an accepted decision, and otherwise goes back to spec review for a fresh acceptance.

A spec commit after acceptance that only restates a decision the accepted spec already states, such as removing a leftover sentence that contradicts it, or adding to a step a second address an accepted step already names, keeps that acceptance by an addendum receipt. The lane owner sends the fleet operator the commit and the accepted text it restates, quoted with its anchor; an owner never records an addendum receipt, since that reads as self-approval. The fleet operator records it, as it records a spec acceptance given in chat, only when the commit adds no behavior, value, or outcome the quoted text does not already state, then tells the human in one line; otherwise it tells the owner to send the commit's review link for a fresh acceptance. An addendum receipt is a spec acceptance receipt: it names each spec by its full repository path then at the addendum commit, and quotes the accepted text with its anchor and accepted commit and the human words that accepted it. The meta-operator and orchestrator contracts state this where they handle a spec commit after acceptance.

Not present

There is no sweep or host timer, loop workflow, role resolver or roles.toml, control CLI, owner file, readiness envelope, trust root, conformance checker, or wording-only diff detector. There is no cross-session coordination, and no record octo-lite writes holds a session key: the session scopes state by directory alone, and the one cross-session address is a review row's wake owner. The lane record is a read-only declaration for observation that nothing gates on.
