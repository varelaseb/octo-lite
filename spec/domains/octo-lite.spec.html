octo-lite

Specifications / octo-lite

This spec states how octo-lite works.

It is octo-lite's domain spec for roles, delivery, lane records, repo health, and human gates; Herdr transport and install have their own, and its decisions are the ADRs the index lists.

User stories

As an operator, I can shape an idea into an accepted spec, then have it filed as a ticket graph and delivered on one PR ready for my review.

As the fleet operator, I append one line per prod, note to the human, lane I start, and issue I file to my own hand-off file, so the floor shows what I did beside each lane's own lines.

As a lane owner, I append one line per hand-off moment to my lane's hand-off file, so the floor shows what happened on my lane, and each ask I make of the human is one gate line naming where to answer and the one action, so the human's pages show the ask without the operator relaying it.

As a lane owner, each ask I make of the human also carries why I ask, what backs it, and the answers I offer, up to four, each with its own line saying what choosing it does, so the human decides from the ask itself, with one choice, wherever a reader shows it.

As an operator, every QA criterion that failed on my lane reaches my merge ask ended by the lane's one finish rule: fixed and recaptured when it is about the change, proven by a named test when no browser can show it, or, outside the change, filed with its consequence or dropped, beside what the judge saw and the head it judged, so no failure of the change ships as a note and no wrong triage reaches my merge.

As an operator, a Bitbucket release annotateanything's plugin watch reports red starts a fix lane of that release without my asking.

As an operator whose project declares a changelog or worklog convention, every change my lanes ship that the convention logs carries its entry in the same PR, in my project's format, and my merge ask names that entry or why there is none, so the log never falls behind what shipped.

As an operator, a wording-only correction to a spec I accepted rides on my original acceptance, a fix that only restates a decision I accepted rides on that acceptance too, by a receipt quoting the decision that I hear of in one line, and any other change to what the spec makes the system do comes back to me for acceptance.

As an operator, a merge I approve merges only the head I approved: its receipt is on the PR before the merge, a merge whose receipt cannot be recorded does not happen, and a merge set to run once checks pass never merges a commit pushed after my go.

As an operator, work that passes the cases at hand without following the rule the spec states never reaches my merge ask.

As an operator, every agent takes a repo-wide rule to mean one thing, an every-feature criterion its home spec marks as a project rule so Jev checks it at every shaping, and a cross-cutting decision a lane settles becomes one, so I never explain the term again.

As an operator, a general rule I state in chat comes back to me as one question offering it as a project rule in its home spec, and a lane whose Jev checks did not run says which rules went unchecked, so no rule I set lives only in chat or goes unchecked silently.

As an operator, my lanes offer a project rule only for a promise my product or system makes, and a convention for how my UI looks or moves goes into my design system with a code check that enforces it, under at most one project rule saying UI uses the design system's shared parts, so my rule set stays small and my design conventions are enforced exactly.

As an operator, lanes that need the same shared surface of my product, such as its design system, take turns editing it, at most two open on it at once, and app-wide UI changes merge one at a time with a check between them, so no wave of UI changes collides or reaches my users with no clear culprit.

As an operator, the fleet operator relays to me only gates, decisions, real blockers, and lane closes, gives me progress in one line or none, and brings its clear-cut questions together as one question asking whether to take its recommendations.

As an operator, no change a lane shapes depends on my remembering which step comes next: its steps across systems trigger each other and are safe in any order, and only my explicit gates wait on me.

As an operator, review never buries what matters: a note about the change is fixed in its PR, a privacy, data loss, money, or security consequence blocks the merge until it is fixed, a note about old code outside the change becomes a tracker ticket when the lane closes only when it names a real consequence, at most five per PR, labeled by its kind, and every other note is dropped.

As an operator, a PR that review keeps sending back comes to me with its open blockers after two fix rounds, instead of looping.

As an operator, every merge ask opens with a few plain lines anyone can read, saying what changes, what review found that matters, and the QA call, and everything else waits in the PR.

As an operator, a merge ask means my whole issue is done in that one PR, built, tested, and QA-captured, with nothing in scope left to a later slice, a follow-up ticket, a phase 2, or an open question, and anything that truly cannot be done before merge reaches me with why before it is cut.

As an operator, a screen my lane changes ships looking like the mockup I accepted with its spec: the implementer builds it from that mockup, review compares the built screen with it, and QA shows them side by side, so I never find the drift after merge.

As an operator, I can fire a repo health pass on a repository whenever I choose, and its few real findings on architecture and cleanliness arrive as ranked tickets, never a report, that I triage and fire off like bugs.

As an operator, my lanes keep no QA environment up that they are not capturing in: a lane takes its PR's environments down as soon as its bundle is published and brings one back only for a recapture, so idle environments never fill the box's shared QA services.

As an operator, no spec a lane shapes lives only on the box: the lane pushes its branch at every spec commit and opens its draft PR at the first, so a lost box loses no accepted or pending spec.

As an operator, a spec my lane shapes that changes my product's screens comes to review, without my asking, as a working prototype of those screens in the product itself, built from its shipped components on real data where that is safe, with a short captioned video and a table placing each surface on its route, and every round of my notes comes back with both updated.

As an operator, the first round of a screen my lane prototypes shows me two directions for it side by side, each saying what it gives up, with the lane's pick and its reason, and one press picks another, so I see the choice weighed without an extra round.

As an operator, every prototype round reaches me already watched by the lane as a first-time user would watch it, with what read unclear or slow fixed, so my notes go to what only I can judge.

As an operator, I give a note on a prototype as the problem I hit, and the next round brings the fix the lane chose for it, without asking me how.

As an operator, a lane that tells me a commit is pushed, or that a spec or PR is ready for my accept, has first proved the remote branch holds every commit it names, so I never accept a head missing what I was shown.

As an operator, every screen an agent designs or builds for my project, prototype included, carries no secondary label or description it does not need, since its layout does the explaining, even when my project has its own UI skill.

Acceptance criteria

Given an operator with an accepted spec in a lane, When the lane owner runs implement-spec to completion and the operator opens the lane's PR, Then that one PR shows every ticket's work, a clear review, and passing required checks, ready for the operator's review.

Given the fleet operator and a live lane owner, When the fleet operator sends the lane owner a prod, Then the operator's hand-off file gains one prod line naming the lane, proven by a unit test: no screen shows it.

Given the fleet operator woken by an action event that asks it to start a lane, When it starts that lane, Then the operator's hand-off file gains one start line naming the lane's issue and the event, proven by a unit test: no screen shows it.

Given the fleet operator woken by an action event that asks it to file an issue, When it files that issue, Then the operator's hand-off file gains one filed line naming the new issue and the event, proven by a unit test: no screen shows it.

Given a lane owner with a choice for the human to answer on a review page, When it sends the human that page's review link, Then the lane's hand-off file gains one gate line asked, naming the gate answer, the verb Answer, and that link, proven by a unit test: no screen shows it.

Given a lane owner whose lane's QA is skipped, When it sends the lane's merge ask, Then the lane's hand-off file gains one gate line asked, naming the gate merge, the verb Accept and merge, the PR as its link, and its QA call in words, proven by a unit test: no screen shows it.

Given a lane owner with a question for the human that has two answers, When it sends the human the question, Then the lane's hand-off file gains one gate line asked carrying why it asks, its evidence, and both answers, each with its own line saying what choosing it does, proven by a unit test: no screen shows it.

Given a lane owner whose lane is ready to merge, When it sends the lane's merge ask, Then the lane's hand-off file gains one gate line asked carrying why it asks, its evidence, and the answer Accept and merge with its own line saying what choosing it does, proven by a unit test: no screen shows it.

Given a lane owner whose spec is ready for review, When it sends the spec's review link, Then the lane's hand-off file gains one gate line asked carrying why it asks and the answer Accept spec with its own line saying what choosing it does, proven by a unit test: no screen shows it.

Given a lane owner whose lane served a report under review that is removed before merge, When the owner closes the lane, Then before its review rows are removed the lane's PR body holds a permalink to that report at the last commit holding it, proven by a unit test: no screen shows it.

Given a lane owner waiting on an implementer, When the owner consumes the implementer's result, Then the lane's hand-off file gains one attempt line naming the worker's role, ticket, pane, and commit, proven by a unit test: no screen shows it.

Given a lane owner whose worker's result is consumed, When the owner closes that worker's tab with what the close prints appended to the lane's hand-off file, Then the lane's hand-off file gains one closed line naming that tab, proven by a unit test: no screen shows it.

Given a lane owner with an idle worker, When the owner parks that worker with both what the park prints and its error output appended to the lane's hand-off file, Then the lane's hand-off file gains one closed line and one parked line and nothing else, proven by a unit test: no screen shows it.

Given an operator whose kept consent answer refuses push, When the lane owner runs implement-spec to completion, Then the owner's report to the operator names the local integration head that holds every ticket's work.

Given an operator whose kept consent answer refuses push, When the lane owner runs implement-spec to completion, Then the lane's work stands at a local integration head and no lane branch is pushed, proven by a unit test: no screen shows it.

Given an operator whose lane owner may push and is shaping a new spec, When the owner commits the spec's first draft and sends its review link, Then the repository's remote shows the shaping branch at that commit and a draft PR for it.

Given an operator whose lane owner may push and has a spec in review, When the owner commits a spec change from that review, Then the repository's remote shows the shaping branch at that commit.

Given an operator whose lane owner's worktree has left its branch holding two new spec commits, When the owner reports them pushed and the spec ready for accept, then the operator opens the lane's PR, Then the PR's head holds both commits.

Given an operator with a lane whose spec review page shows a commit the lane's PR branch lacks, When the operator presses Accept spec, then the owner records the receipt, then the operator opens the lane's PR, Then the receipt names that commit and the PR's head holds it.

Given an operator with a ticket whose behavior the spec on main already states, When the lane owner runs implement-spec on that ticket to completion and the operator opens the lane's PR, Then no spec review was asked, and that one PR shows the ticket's work, a clear review, and passing required checks, ready for the operator's review.

Given an operator with a lane's spec under review, When the operator accepts the spec in chat with the fleet operator, the fleet operator records it, and the operator opens the lane's PR, Then the PR shows a receipt comment from the fleet operator, not from the lane owner.

Given an operator who told the fleet operator in chat that a lane's spec changes are accepted ahead of review, When the lane's owner sends the fleet operator its spec's review link, then the operator opens the lane's PR, Then the PR shows a receipt comment from the fleet operator quoting the operator's words and naming that spec at the commit the owner sent.

Given an operator with a lane whose two specs are under review, When the operator accepts both in chat with the fleet operator, the fleet operator records it, and the operator opens the lane's PR, Then the receipt comment names each spec by its full repository path, each followed by at and the accepted commit.

Given an operator with a lane's PR whose merge ask is out and whose acceptance receipt cannot be posted (needs an induced failure: posting the PR comment fails), When the operator tells the fleet operator to merge it, then opens the lane's PR, Then the PR is still open and not merged.

Given an operator with a lane's PR whose checks are still running, When the operator tells the fleet operator to merge it once checks pass, then the lane pushes a new commit to the PR before they pass, then the operator opens the lane's PR, Then the PR is still open and not merged at the new commit.

Given an operator with a lane's spec under review, When the operator accepts the spec in chat with the fleet operator and the fleet operator records it, Then the box holds no record of that acceptance besides the PR's receipt comment, proven by a unit test: no screen shows it.

Given a lane owner delivering a ticket graph, When the owner moves a ticket to its next state, Then the lane record holds only its lane keys and no ticket entry, proven by a unit test: no screen shows it.

Given an operator with a lane owner delivering a ticket graph, When the owner moves a ticket to its next state, then the operator opens that ticket in the tracker, Then the tracker shows the ticket's new state.

Given an operator with an accepted spec in a lane whose spec issue is filed, When the lane owner files the spec's tickets with implement-spec, then the operator opens the lane's PR, Then the PR body holds one Closes line naming the spec issue and one naming each ticket.

Given a live lane owner and a fleet operator started in place of the one that launched its lane, When the new fleet operator takes over the fleet, Then the owner's pane shows a message from the new fleet operator naming that operator's pane as the one to report gates and completion to.

Given a live lane owner whose lane has no lane record and a fleet operator started in place of the one that launched it, a fixture that must be added to provide it, When the new fleet operator takes over the fleet, Then the lanes directory holds a record for that lane naming the owner's pane, which no screen shows.

Given an operator with a lane's PR ready to merge, When the operator tells the fleet to merge it and the PR merges, Then the box holds no record of that acceptance besides the PR's receipt comment, proven by a unit test: no screen shows it.

Given an operator with a lane's PR ready to merge, When the operator tells the fleet to merge it, the PR merges, and the operator opens the PR, Then the PR shows one receipt comment quoting the operator's words and the accepted commit.

Given a lane owner whose QA capture shows a criterion failed because the product does not do what it states, When the owner triages that failure and the operator opens the lane's issue in the tracker, Then the tracker shows a repair ticket under that issue naming the criterion, worked by a new implementer.

Given a lane owner whose QA capture shows a criterion failed because the product does not do what it states, When the owner has the repair integrated, then sends the lane's merge ask, then the operator opens the PR it links, Then the PR body lists that criterion as a code fault with its repair ticket and its outcome in a recapture at the repaired head.

Given a lane owner whose QA capture shows a criterion failed because the capture never reached or showed the state it names, When the owner fixes that cause, then sends the lane's merge ask, then the operator opens the PR it links, Then the PR body lists that criterion as a capture fault with the cause fixed, the commit that fixed it, and its outcome in a recapture of just that criterion.

Given a lane owner whose QA capture shows a criterion failed in old code the lane did not change, with a consequence for its users, When the owner sends the lane's merge ask, then the operator opens the PR it links, Then the PR body lists that criterion as outside the change with that consequence, to file at lane close, and the PR is ready for review.

Given a lane owner whose QA capture shows a criterion failed, When the owner sends the lane's merge ask, then the operator opens the PR it links, Then the PR body lists that criterion with what the judge saw, whose decision it was and the head it was judged at, its triage, its cause or reason, and its outcome.

Given a lane owner whose QA capture shows a criterion failed where the judge reached the state it names and saw the product not match it, When the owner triages it as a capture fault, then sends the lane's merge ask, then the operator opens the PR it links, Then the PR body lists that criterion as a capture fault naming the specific way the capture went wrong.

Given a lane owner whose QA bundle carries a criterion's failure from an older head, When the owner sends the lane's merge ask, then the operator opens the PR it links, Then the PR body lists that criterion as judged at the merge ask's head, never as carried.

Given a lane owner with a PR to capture, When the owner runs a QA capture of that PR and the capture publishes its bundle, Then the QA program lists none of that PR's environments running.

Given a lane owner whose PR's environments went down after its first bundle, When the owner runs a recapture of that PR at a new head and the recapture publishes its bundle, Then the QA program lists none of that PR's environments running.

Given the fleet operator and a Bitbucket release the plugin watch reports red, When the fleet operator receives the watch's report, Then Herdr shows a new lane space for a fix of that release.

Given the fleet operator with a lane's accepted PR to merge, needs an induced failure: the target's main CI fails after the merge, When the fleet operator merges the PR, then main's CI run ends, Then Herdr shows a new lane space for a fix of the target's main.

Given an operator whose project's instructions point to a rule file stating a worklog convention, When a lane delivers a change its users can see, then the operator opens the files the lane's PR changes, Then the worklog the rule file names gains one entry for that change, in the format the rule file states.

Given an operator whose project declares a changelog convention, When a lane delivers a change the convention does not log and the operator opens the lane's PR, Then the PR's description holds one Changelog line saying none, with the reason.

Given an operator whose project declares a changelog convention, When a lane delivers a change the convention logs, then its owner sends the operator the lane's merge ask, Then the merge ask carries one Changelog line naming the lane's entry.

Given an operator whose project declares a changelog convention, When a lane delivers a change the convention does not log, then its owner sends the operator the lane's merge ask, Then the merge ask carries one Changelog line saying none, with the reason.

Given an operator whose project declares no changelog convention, When a lane's owner sends the operator the lane's merge ask, Then its Changelog line says none, because the project declares no convention.

Given a lane owner whose integration head makes a change its project's changelog convention logs and adds no entry, When a fresh code reviewer judges the head, Then its verdict to the owner blocks on the missing entry.

Given a lane owner whose integration head adds a changelog entry off its project's declared format, When a fresh code reviewer judges the head, Then its verdict to the owner blocks on that entry, naming the format rule it breaks.

Given an operator with an accepted spec on a lane, When the owner commits a correction that only rewords that spec, then the operator opens the lane's PR, Then the PR body names that commit as wording-only in one line, and the PR shows no new acceptance receipt for it.

Given an operator with an accepted spec on a lane, When the owner commits a spec change that alters a behavior the spec states, Then the operator receives a review link for that change before any merge ask.

Given an operator with an accepted spec on a lane, When the owner commits a spec fix that only restates a decision the accepted spec states, then the operator opens the lane's PR, Then the PR shows an addendum receipt from the fleet operator that names the fix's commit and quotes the accepted decision it restates.

Given an operator with an accepted spec on a lane, When the owner commits a spec fix that only restates a decision the accepted spec states, Then the operator receives one line from the fleet operator saying it recorded an addendum receipt for that fix, and no review link for it.

Given a lane owner whose integration head passes a named criterion through code keyed to that criterion's own case instead of the rule the spec states, When a fresh code reviewer judges the head, Then its verdict to the owner is changes, with a blocker naming the keyed case.

Given a lane owner whose integration head adds a second store beside an existing one, with no reason in its spec for a second, When a fresh code reviewer judges the head, Then its verdict to the owner lists that second store as a blocker.

Given an operator whose project's specs mark project-rule criteria and whose agent instructions state one more rule only as prose, When the operator asks the fleet operator for the project's repo-wide rules, Then the reply lists each marked criterion by its spec and anchor, and names the prose-only rule as not yet a repo-wide rule.

Given an operator with a lane whose spec settles a cross-cutting decision, such as an identity key, that a later feature could plausibly break and no project-rule criterion states, When the lane's owner sends that spec's review link to the fleet operator, Then a lane on the decision's home spec receives the fleet operator's ask for a criterion marked as a project rule that states the decision.

Given an operator whose project's specs mark no project-rule criterion stating a rule that a later feature could plausibly break, When the operator states that rule to the fleet operator in chat as a general rule, such as one saying always, never, or regardless of, Then the fleet operator's reply asks one question, whether to make the rule a criterion marked as a project rule in the home spec it names, with its recommendation.

Given an operator whose project's specs mark project-rule criteria and a lane whose spec's Jev checks did not answer (needs an induced failure: Jev does not answer in time), When the lane's owner sends that spec's review link to the fleet operator, Then the message says the Jev checks did not run and names each marked rule left unchecked by its spec and anchor.

Given an operator whose project's specs mark project-rule criteria and a lane whose spec's Jev checks are off, When the lane's owner sends that spec's review link to the fleet operator, Then the message says the Jev checks did not run and names each marked rule left unchecked by its spec and anchor.

Given an operator with a lane whose spec settles a design-system convention, such as every loading state using the shared skeleton, that no project-rule criterion states, When the lane's owner sends that spec's review link to the fleet operator, Then no lane receives an ask for a criterion marked as a project rule that states the convention.

Given an operator with a lane whose accepted spec settles a design-system convention, When the lane's owner sends its merge ask and the operator opens the lane's PR, Then its changes hold the convention in the design system's source, the shared part that carries it, and a code check that fails on a hand-rolled version.

Given an operator whose project has a design system, When the operator states a design-system convention to the fleet operator in chat as a general rule, such as every tab row always using the one switch, Then the fleet operator's reply asks one question, whether to add the convention to the design system with a code check, with its recommendation, and offers no project rule for it.

Given an operator whose project's specs mark design-system conventions as project rules, When the operator asks the fleet operator for the project's repo-wide rules, Then the reply names those rules as ones to fold into the one design-system rule and asks one question, whether a lane on the design system folds them.

Given an operator with an open lane whose work edits a product's design system, When the operator asks the fleet operator to start a second lane whose work also edits that design system, Then the second lane's record shows it waiting on the first lane's issue.

Given an operator with two open lanes whose work edits a product's design system and no cap the human set, When the operator asks the fleet operator to start a third lane whose work edits it, Then the fleet operator's reply says the third lane is held unstarted until one of the two merges.

Given an operator whose project's QA declares a smoke check, with two accepted PRs that each change every screen of its product, When the operator tells the fleet operator to merge both, then opens the second PR, Then it shows merged only after main's required checks and the project's smoke check passed on the first PR's merge.

Given an operator with a running lane and no question open, When the lane's owner reports progress to the fleet operator that needs no decision from the operator, Then the operator's chat with the fleet operator shows at most one new line about that progress.

Given an operator with two lanes each holding a question that has a clear recommended answer, When the lanes' owners send those questions to the fleet operator, Then the operator receives one message asking whether to take the fleet operator's recommendations, with one plain line per question naming its recommendation.

Given an operator with one lane holding a question that has a clear recommended answer and another lane holding a question that weighs real trade-offs, When the lanes' owners send those questions to the fleet operator, Then the operator receives the trade-off question as a message of its own, apart from the message asking whether to take the recommendations.

Given an operator with a lane whose change spans systems, such as a sender and a receiver that deploy apart, When the operator opens that spec's review link, Then the spec states what triggers each later step and that the steps are safe in any order, and no step waits on the operator except an explicit human gate, after which every step follows by itself.

Given a lane owner whose integration head adds a cross-system step that runs only if a human remembers to run it after another, When a fresh code reviewer judges the head, Then its verdict to the owner blocks on that step, citing the any-order check.

Given a lane owner whose integration head works but leaves a function no caller uses, When a fresh code reviewer judges the head, Then its verdict to the owner lists a cleanliness note naming that function, marked to fix in this PR.

Given an operator with a lane whose review verdict lists a note marked to fix in this PR, When the lane's owner sends its merge ask and the operator opens the PR's changes, Then they hold that fix.

Given a lane owner whose integration head works and splits a module where the reviewer would split it otherwise, at no cost to any user, data, money, security, or reliability, When a fresh code reviewer judges the head, Then its verdict to the owner holds no note about that split.

Given a lane owner whose integration head works but lets any signed-in user read another user's private records, When a fresh code reviewer judges the head, Then its verdict to the owner lists that as a blocker naming its privacy consequence.

Given an operator with a lane whose PR lists one review note naming a consequence and one naming none, When the PR merges and the lane's owner closes the lane, then the operator opens the tracker's open health tickets, Then they show one new ticket for the note naming a consequence, with its category label, its consequence, and a link to the PR, and none for the other note.

Given an operator with a lane whose PR lists seven review notes about old code outside its change, each naming a different issue with a consequence that is not a privacy, data loss, money, or security one, and that no open health ticket names, When the PR merges and the lane's owner closes the lane, then the operator opens the tracker's open health tickets, Then they show new tickets for that PR's five highest-ranked notes and none for the other two.

Given an operator with a lane whose PR review sent back twice, the second time to a step-back pass, When the review after that pass still finds a blocker, Then the operator gets a message from the owner naming each open blocker and asking how to go on, in place of a third fix round.

Given an operator with a lane whose review, validation, and QA are done, When the owner sends the lane's merge ask, Then the operator's message opens with three to five plain lines, with no file path, anchor, or command, saying what changes for the user, what review found that matters, and the QA call, followed by the PR's link.

Given a lane owner whose integration head leaves part of its accepted spec unbuilt, When a fresh code reviewer judges the head, Then its verdict to the owner lists a blocker naming the unbuilt part.

Given an operator with a lane ready for its merge ask, When the lane's owner sends its merge ask and the operator opens the lane's PR, Then its body leaves no work its issue or accepted spec holds to a later slice, a follow-up ticket, a phase 2, or an open TBD.

Given an operator with a lane whose accepted spec holds a measurement only production gives, When the lane's owner finishes every other step its merge ask needs, Then the operator gets a message from the owner naming that measurement and why it cannot be done before merge, asking whether to cut it, in place of a merge ask.

Given a lane owner whose integration head works but copies one new check into four of the handlers it adds, When a fresh code reviewer judges the head, Then its verdict to the owner lists a duplication note naming the four copies, marked to fix in this PR.

Given a lane owner whose integration head works and calls an old function, outside its change, whose check is copied into four handlers, When a fresh code reviewer judges the head, Then its verdict to the owner lists a duplication note naming the copies and what a fix to only one of them would break, not marked to fix in this PR.

Given a lane owner whose QA capture could not test a criterion of the lane's change because its outcome shows only in a native tooltip, When the owner sends the lane's merge ask, then the operator opens the PR it links, Then the PR body lists that criterion as proven by the test it names.

Given an operator with a lane whose accepted spec's mockup set draws a screen a ticket changes, When the owner starts that ticket's implementer and the operator opens the implementer's pane, Then its brief names that screen's mockup at the spec's accepted commit.

Given a lane owner whose integration head shows a changed screen with a section its accepted mockup does not draw, When a fresh code reviewer judges the head, Then its verdict to the owner lists a blocker naming that section.

Given an operator with a lane that changes a screen its accepted mockup draws, When the lane's owner sends its merge ask and the operator opens that screen at the width of one of its mockup's frames, Then the screen shows what that frame shows, in its layout and proportions, with only sample values differing.

Given an operator in a repository whose specs are Spec Chat's, with a ticket that changes a screen its spec's mockup set does not draw, When the lane owner runs implement-spec on that ticket, Then the operator gets the spec's review link, with a mockup of that screen, before any implementer starts.

Given an operator whose lane shapes a spec that changes a screen of a product that runs on the box, When the lane owner reports the spec ready for accept and the operator opens that screen's mockup, Then it shows the screen running in the product, inside the product's own navigation and header, and a short captioned video of it.

Given an operator whose lane shapes a spec that changes a screen of a product that runs on the box, on a box whose review service frames no prototype, When the lane owner reports the spec ready for accept and the operator opens that screen's mockup, Then it shows the screen drawn at production fidelity.

Given an operator whose lane prototypes a screen on a route the product already ships, When the operator opens the changes on the lane's PR, Then they show the screen on that route built from the product's existing shell and components, with a new component only for a part the spec marks New.

Given an operator whose lane prototypes one screen the product ships and one it does not, When the operator opens the spec's review link, Then the spec shows a table with one row per prototype surface naming its route or component, the screen the product does not ship marked New.

Given an operator whose lane prototypes a screen listing records the product holds, some of them customers', When the operator opens that screen's mockup, Then it lists the product's own records and no customer's.

Given an operator with a prototyped spec in review, When the operator sends a hand-off with notes on the prototype, then opens the next review link and that screen's mockup, Then it shows the prototype with those notes answered and a new captioned video recorded from it.

Given an operator with a prototyped spec in review whose screen reaches a step when its user presses a button, on a box where Stageshow is installed, When the operator opens the review link, then that screen's mockup, then plays the round's desktop video, Then the video shows a cursor travel to that button and press it, that step's change appear under the cursor, and that step's result hold still before the next step begins.

Given an operator and a fleet operator with a prototyped spec in review on a box where Stageshow is not installed, When the lane owner sends the round's review link, then the operator opens the fleet operator's pane, Then the message carrying that review link says the round's video was recorded without Stageshow's checks.

Given an operator with a prototyped spec in review, When the operator sends a hand-off with a note the lane could read two ways, then opens the next review link and that note's thread, Then it holds the lane's reply naming the reading it took and what it changed.

Given an operator whose lane's prototype shows a value its spec states differently, When the owner sends the round's review link, then the operator opens it, Then the spec and the screen's prototype show the same value.

Given an operator whose lane shapes a spec that changes a screen of a product that runs on the box, with that screen's first prototype round running, When the operator opens the spec's review link, then that screen's mockup, Then it shows two directions of the screen running side by side, each named with one line saying what it gives up, the lane's pick marked with its reason, and a captioned video of the pick.

Modular boundaries

octo-lite owns and publishes the lane record and hand-off formats; roles write them at the named moments. The caller-facing seam is the files in each Herdr session's state directory, plus the lane's Herdr space and spawn names for workers. Direction is self-contained: readers such as a board depend on the format and locate a session's files from the Herdr session key; octo-lite names no reader. Observable scope: file contents and the lane's space membership.

Role contracts and skills own shaping, delivery, review, and gates. The caller-facing seam is the role contracts in agents/ and the skills in skills/. Direction is downward: roles use the wrappers, Herdr's own agent state, and the lane record format; external providers are Linear, GitHub, Spec Chat, whose mockup set is each changed screen's accepted target and whose mockup page shows a first round's directions side by side, the Stageshow skill, whose story, cursor, and framing rules each round's video follows, and annotateanything's QA capture program, whose rules (when QA runs, outcomes, owner triage) live in its jev-capture spec under QA rules, while the finish rule that ends each failure, like each review note, is octo-lite's. Observable scope: tickets, the PR, and the lane record.

The filing rule and the repo-health skill own turning review notes and health findings into health tickets. The caller-facing seam is the health tickets in the box's tracker, with their Health label and priority, and the tagged notes in each PR body. Direction is external-provider: the filer depends on the tracker the lanes already file in, and octo-lite names no reader of health tickets. Observable scope: health tickets, their labels, priorities, comments, and states, and the pass's one message.

An implementer implements the general rule the spec states, so every case the rule covers holds, not only the criterion, fixture, label, or evaluation case at hand. A code reviewer blocks code keyed to the instances at hand, such as a named criterion, fixture, label, or evaluation case, in place of the rule the spec states: it passes the check while the behavior stays wrong.

An implementer working test-first takes the seams it tests at from the canonical spec, never from the user, since no human loop runs mid-implementation, and writes no test at a seam the spec does not name. Each seam a spec names is a deep-module seam, a small interface over large behavior; a spec whose seams are not is a shaping defect that goes back to shaping, and the implementer never invents seams. The one patch octo-lite carries on the pinned tdd skill (ADR 0006) states this where the skill picks seams.

A repo-wide rule is an every-feature acceptance criterion its home spec marks as a project rule, Spec Chat's data-project-rule mark, which Jev checks against every spec at shaping and each review hand-off names under rules checked. A line in a target AGENTS.md only points implementers at such a criterion; a rule stated only there, or in spec prose outside a criterion, is not yet a repo-wide rule. When a lane's spec settles a cross-cutting decision, such as an identity key, an exposure contract, or a single source, that no project-rule criterion states, its owner names the decision and its home spec in its review hand-off. The fleet operator then asks a lane on that home spec, this lane when the home is its own spec, for a criterion marked as a project rule that states the decision, so Jev enforces it from the next shaping, and that spec's acceptance is recorded by the PR receipt like any other. A general rule the human states to the fleet operator in chat, such as one saying always, never, in general, or regardless of, takes the same route: when no project-rule criterion states it, the fleet operator asks the human one question, whether to make it a criterion marked as a project rule in the home spec it names, with its recommendation, and on yes asks a lane on that home spec as above. The set stays small: a decision or rule earns a project rule only if it is a promise the product or system makes, such as tabs keeping their place, consent records reading plain stable values and never rendered text, or an identity key, that a user would notice breaking or a later feature could plausibly break. Nothing here waits on Jev: when Jev is off or backed up, every marked criterion still binds the briefs that cite it, an owner still names a settled decision in its review hand-off, and the fleet operator still offers a rule stated in chat. A review hand-off whose spec's Jev checks did not answer says so and names, by spec and anchor, each marked rule left unchecked, so a skipped check is never silent. The meta-operator and orchestrator contracts and the implement-spec skill state this where they ask, shape, and brief.

A design-system convention, how a product's UI looks or moves or which shared part draws a pattern, such as text changes morphing or every loading state using the shared skeleton, is never a project rule. It lives in the product's design system: its one source, such as a DESIGN.md, the shared part that carries the behavior, and a code check, such as a lint rule or a design-rules test the repository's suite runs, that fails on a hand-rolled version, so code enforces it exactly. A lane whose spec settles one adds all three in its PR, and its owner never names it in a review hand-off as a decision for a project rule. A repository keeps at most one project rule for its design system, that every feature's UI uses the design system's shared parts, its criterion pointing at the design system, so a spec that adds a shared part needs no rule of its own. A design-system convention the human states in chat gets the fleet operator's one question offering it to the design system, with its recommendation, never as a project rule. A repository whose specs mark design-system conventions as project rules folds them: asked for its repo-wide rules, the fleet operator names those as ones to fold and asks the human one question, whether a lane on the design system folds them, adding each one's code check, marking the one design-system rule, and removing their marks in one PR. The meta-operator and orchestrator contracts and the grill-with-docs skill state this where they ask, shape, and record rules.

A shared surface is a part of a product every screen or feature builds on, such as its design system: a UI-system spec, its DESIGN.md, and its shared components. One lane at a time edits a shared surface: a lane whose work edits one that another open lane edits waits on that lane, its record's waiting_on naming that lane's issue, parked until that lane's PR merges, then merges main and goes on. The fleet operator keeps at most two lanes open on one shared surface, or the cap the human sets, and holds any further one as an unstarted issue until one of them merges. An owner whose spec turns out to edit a shared surface tells the fleet operator before editing it. An app-wide UI change, one that reaches every screen or many at once, such as wrapping every in-place text change or every loading state, merges one at a time: the next merges only once main's required checks and the project's smoke check pass on the last one's merge. The smoke check is a cheap capture of the product's main screens on each merge that touches them, kept on when full QA is off; it is a delivery step of the project's QA, whose rules for when it runs, what it captures, and its outcomes live there, as annotateanything's live in its QA rules, never in octo-lite, and a project whose QA declares none checks main's required checks alone. The meta-operator contract states this where it starts lanes and orders merges, and the orchestrator contract where it shapes.

The fleet operator relays to the human only gates, decisions, real blockers, and lane closes, plus the line telling of an addendum receipt; progress gets one line or nothing. A question that weighs real trade-offs goes alone, never inside that bundle. The meta-operator contract states this where it writes to the human.

Shaping checks every new spec whose change spans systems, such as a deploy, a promotion, a backfill, a migration, or a switch: each later step is triggered by an earlier step's effect or converges by itself, and the steps are safe in any order, with nothing broken or lost between them, so none depends on a human remembering the sequence. Repo health

A health ticket is a tracker ticket for one real architecture or cleanliness issue in a repository, in the box's tracker, the one its lanes already file tickets in; no other store holds health issues. It names the issue, its consequence, where in the repository it lives, and each source that raised it: a PR or a health pass. It carries one label of the tracker's Health label group, naming its category, and a priority from its rank. It is filed unassigned, with no parent, in a state not yet started, so it waits in the tracker beside the bugs a human triages and fires off.

The categories are architecture, cleanliness, naming, duplication, test, and docs. A consequence is what the issue will cost or break, named concretely, such as the next change to acceptance must edit four copies. A note or finding that names no consequence stays history and never becomes a ticket.

A code reviewer gives every non-blocking note the end the finish rule gives it, tagged with its category, so a note never buries what matters: a note to fix is marked to fix in this PR, and a note to file names its consequence. The owner has every note marked to fix fixed in the PR before the merge ask, in a fix batch already running, whose fix delta review covers it, or one batch of its own, which is no fix round but whose delta a fresh reviewer reviews the same way, so no fix reaches the merge ask unreviewed, and lists every note to file in the PR body, tagged as given, so the PR keeps it and a filer reads it there. At lane close, after the PR merges and before teardown, the agent closing the lane, its owner or the fleet operator, files the PR's notes by the filing rule.

One filing rule turns notes and findings into health tickets: one PR's notes at lane close, many PRs' notes in one batch, and a health pass's findings. The filer first reads every open health ticket and the target's current main, then gives each note or finding the first disposition below that fits. Two notes name the same issue when one fix would remove both, whatever their wording. A filing checks only its own notes and findings against main; only the health pass checks the open health tickets themselves against main. Each source, one PR or one pass, files at most five new tickets, highest rank first; the rest stay history, and a later pass that still finds one files it then.

A health issue's rank is its consequence: high when it will cause wrong behavior or block a change, medium when it makes the next change in that area cost more, such as a duplicate, a dead store, or a misleading name, and low when it costs only reading time. The rank is the ticket's tracker priority, so it orders health tickets among the tracker's other work.

The repo-health skill is the repo health pass, fired by hand by the fleet operator, at its own call or when the human asks for one, and never on a timer. The fleet operator starts one fresh agent for it on the target's main checkout; that agent changes no repository file and writes only health tickets. It reads the target's instructions, its specs' modular boundaries, the open health tickets, and the code, and looks across the whole repository for architecture, cleanliness, best-practice, and trimming issues, a deletion first wherever one would do. It checks every open health ticket against main, closing each one main fixed as done, with a comment naming the main commit it was checked at and why the issue is gone, and files its findings by the filing rule. Its result is the tickets, never a report: its one message to the fleet operator names each ticket it filed, commented on, or closed, by key, and the fleet operator relays that list to the human who asked.

The code-reviewer, orchestrator, and meta-operator contracts and the implement-spec skill state these moves where they review, list notes, close a lane, and fire the pass.

Stores

Every file or folder octo-lite writes on the box, each with one lifetime and the writer that ends it. A Log is appended to, or rewritten only by its writers, and is never deleted automatically; it ends in its lane's archive or by the box owner's hand. octo-lite keeps no Cache, and no store keeps a copy of a fact another store owns: an acceptance is the PR receipt, a ticket's state is the tracker's, and a lane's workers are its Herdr space. A path no row names is no store of octo-lite: a lane's worktrees are the target repository's, in Git, and the owner removes them and its own /tmp scratch at lane close; the installer's links are its install, and the wake provider file it registers is Spec Chat's provider configuration (wake provider).

Lane record

Octo-lite owns and publishes the lane record format: one TOML file per open lane in the lanes/ directory of its Herdr session's state directory, named by the owner agent name, with the keys below, written at the moments below. A closed lane's record, hand-off log, and notes live in archive/ inside that directory. A lane record's name is never reused, not even after its record is archived: the fleet operator starts each lane under a name no open or archived record has, so one name always means one lane. Readers follow this format; octo-lite names no reader.

The record holds no ticket state: a ticket's state, holder, and repair passes live in the tracker only.

The record lists no workers. A lane's workers are the Herdr agents in the lane's space other than the owner; each worker's pane is its Herdr pane id, and its role and ticket come from its spawn name.

At each hand-off moment the owner appends one line to <lane record name>.handoffs.jsonl beside the lane record, per the hand-off field list; only the owner writes the file, except the parked line for the owner itself, which the operator appends when it parks the owner.

Every line of a hand-off log is one JSON object, appended whole. A reader of hand-off logs skips a line that is not one, naming that log and the line's number once, so one bad line hides nothing else in its log and breaks no other lane.

An asked gate line carries what the human needs to decide from the ask itself, in plain words, each field optional: why, one line saying why the owner asks now, for an answer gate the question and why it comes up; evidence, one line naming what backs the ask, each link in it a full URL; and answers, a list of one to four objects, each answer, a few words naming one way to answer, and line, one sentence saying what choosing it does. The owner writes why with every ask, evidence when something backs it, such as checks passed, a review verdict, or a QA bundle, and answers when the human answers by choosing: each option of a question, Accept spec on a spec review, Accept and merge on a merge ask. A line without them is a complete gate line read by its verb and link, so readers take the fields up before or after owners write them.

{"at": "2026-11-05T20:10:00Z", "kind": "gate", "gate": "answer", "event": "asked", "link": "https://review.example.net/ann1722/", "verb": "Answer", "why": "The phone criterion needs a BB release that is not out yet: cut it from this PR, or wait?", "evidence": "BB release plan: https://github.com/example/bb/milestone/12", "answers": [{"answer": "Cut it", "line": "Ships the PR without the phone criterion."}, {"answer": "Wait", "line": "Holds the PR until that BB release ships."}]}

The fleet operator appends one line per operator moment to operator.handoffs.jsonl beside operator.toml, with the same common fields and the kinds below; it is the file's only writer. This is the lane hand-off mechanism with a different writer; readers follow this format, and octo-lite names no reader.

Human gates

Spec acceptance, acceptance of delivered work, merge of unaccepted work, preproduction promotion, and live traffic shifts require explicit human instruction.

A spec acceptance the human gives the fleet operator in chat is recorded by the fleet operator at once, as the receipt comment on the PR, and the owner is told; an owner never records it, since that reads as self-approval. A standing acceptance the human gives the fleet operator before the spec head exists is recorded the same way, at once, when the lane owner sends the fleet operator that spec's review link or head, quoting the human's standing words. The fleet operator also runs review-host.py reviewed --id <resource id> for each accepted spec, which moves its review row's base to the accepted commit and records no acceptance.

Every acceptance, of a spec or of delivered work, is recorded once, as a receipt comment on the lane's PR, and everything that needs it reads that comment. The receipt quotes the human's words, gives the date, names what is accepted (the spec or the PR), the exact accepted commit, and who recorded it. A spec receipt starts Spec acceptance receipt: and names each accepted spec once, by its full repository path followed by at and the accepted commit. A spec accepted on the review page is recorded by the owner processing that hand-off, quoting the action; a spec accepted in chat by the fleet operator; delivered work by the agent receiving the instruction, before it merges. A delivered-work receipt goes on the PR before the merge, and the merge commit closes it; nothing else records the merge. Spec Chat records no acceptance: the Accept spec hand-off in its spool is the instruction a spec receipt quotes, never a second record.

On a human instruction to merge, the receiving agent checks that the PR head is the accepted commit and that required checks pass, then records the receipt and merges. Every receipt the merge needs, an addendum receipt included, is on the PR before the merge: when one cannot be recorded, the merge does not happen and the agent reports why. The merge is pinned to the accepted commit, a merge set to run once checks pass included, so a head pushed after the human's go is never merged; a pinned merge that finds a moved head does not happen and the agent reports it. The meta-operator contract and the octo-lite-github skill state this where they merge. It re-checks no QA evidence: a merge ask goes out only after every step it needs, that evidence included.

Where consent allows push (consent), a commit is pushed only when the remote branch holds it: before a message names a commit as pushed, or a spec or PR as ready for accept, its sender fetches the branch and proves each commit it names is an ancestor of the remote head, and a commit that fails, such as one made on a worktree that left its branch, goes onto the branch and is pushed first. A spec receipt is recorded the same way, only once the PR's remote head holds the accepted commit, so a receipt never pins a head missing what the human was shown. The orchestrator, integrator, and meta-operator contracts and the push skill state this where they report a push or record a receipt.

A spec commit after acceptance that is wording-only keeps the original acceptance, with no new review and no new receipt. Wording-only means the commit changes only wording, labels, or anchors: it adds or removes no criterion and changes no stated behavior, value, or outcome. The lane owner decides, and lists each such commit in the PR body with one line saying what it rewords, so the human sees it at the merge gate. A commit the owner cannot plainly call wording-only is not: it keeps the acceptance by an addendum receipt when it only restates an accepted decision, and otherwise goes back to spec review for a fresh acceptance.

A spec commit after acceptance that only restates a decision the accepted spec already states, such as removing a leftover sentence that contradicts it, or adding to a step a second address an accepted step already names, keeps that acceptance by an addendum receipt. The lane owner sends the fleet operator the commit and the accepted text it restates, quoted with its anchor; an owner never records an addendum receipt, since that reads as self-approval. The fleet operator records it, as it records a spec acceptance given in chat, only when the commit adds no behavior, value, or outcome the quoted text does not already state, then tells the human in one line; otherwise it tells the owner to send the commit's review link for a fresh acceptance. An addendum receipt is a spec acceptance receipt: it names each spec by its full repository path then at the addendum commit, and quotes the accepted text with its anchor and accepted commit and the human words that accepted it. The meta-operator and orchestrator contracts state this where they handle a spec commit after acceptance.

Not present

There is no sweep or host timer, loop workflow, role resolver or roles.toml, control CLI, owner file, readiness envelope, trust root, conformance checker, or wording-only diff detector. There is no cross-session coordination, and no record octo-lite writes holds a session key: the session scopes state by directory alone, and the one cross-session address is a review row's wake owner. The lane record is a read-only declaration for observation that nothing gates on.
