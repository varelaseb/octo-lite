Disk

Specifications / Disk

This spec states how octo-lite keeps the disk its lanes use: each agent's scratch folder, the installed packages a lane's worktree shares with main, what parking an agent and closing a lane remove, and the warning the operator gets before the box's disk fills.

Spawning, closing, and parking agents are in the Herdr transport spec; the hook that checks the disk is in the Command time spec; lane teardown and lane notes are in the octo-lite spec.

User stories

As an operator, every temporary file an agent's commands make lands in that agent's own scratch folder, where its test suites and browsers run as they would in /tmp, which stays through a park and goes when the agent is closed, so nothing an agent made is left in /tmp with no owner.

As an operator, an agent in its own lane's worktree links the packages my box's main checkout installed from the same lockfile instead of installing them, with no download and almost no disk, and installs its own wherever linking is dangerous, as when its lockfile differs or main's install is stale or mid-update, so nothing a lane installs ever changes main's packages or breaks a lane already running.

As an operator, parking an agent frees the installed packages in its own worktree, which it installs again when it next needs them, while my box's main checkouts, its install clones, any tree another agent works in, and a worktree a server it left running for my review uses keep theirs.

As an operator, a finished lane leaves no disk behind but its archived record, hand-off log, and notes, and its notes hold only what cannot be made again.

As an operator, I am told when my box's disk reaches 85% full and again at 90%, with the folders holding the most of it, so I hear before a full disk crashes a service, and the warning only tells me: it never removes, blocks, or stops anything.

Acceptance criteria

Given a lane owner, When it spawns a worker, then the worker runs a test suite that makes temporary folders, Then each of those folders is inside the worker's own scratch folder, which no other agent shares: no screen shows it.

Given an operator on a box shared with another user, a fixture that must be added to provide it, When a lane owner spawns a worker, Then the other user cannot read, write, or replace the worker's scratch folder, and a browser the worker starts runs: no screen shows it.

Given a lane owner on a box whose home folder's path is 15 characters or fewer, When it spawns a worker, then the worker runs a test suite that nests its own temporary folders 30 characters deep under its scratch folder and starts Chromium in the deepest, Then Chromium starts: no screen shows it.

Given a lane owner whose worker has made temporary files, When the owner closes the worker, Then the worker's scratch folder is gone, and the owner's own scratch folder is still there: no screen shows it.

Given a lane owner whose idle worker has made temporary files, When the owner parks the worker, Then the worker's scratch folder is still there, holding those files: no screen shows it.

Given a lane owner that parked its worker after the worker made temporary files, When the owner sends the worker a message, then the resumed worker makes a temporary file, Then that file is in the scratch folder the worker had before its park, beside the files it made then: no screen shows it.

Given the operators of two Herdr sessions, each with a lane agent under the same name that has made temporary files, When the operator of one session closes its agent, Then the other session's agent keeps its scratch folder: no screen shows it.

Given an operator who updates octo-lite while a lane agent still runs that was started before its box gave agents scratch folders, When the agent's owner closes it, Then the close ends the agent and its processes as before and removes no file: no screen shows it.

Given an operator who updates octo-lite while a lane agent still runs whose scratch folder an earlier octo-lite put in the user's cache folder, and that agent has made temporary files, When the agent's owner closes it, Then that scratch folder is gone: no screen shows it.

Given a lane owner whose repository's main checkout has its packages installed from the lockfile the lane branch also has, When it briefs a worker in a new worktree of the lane with a ticket whose tests need those packages, Then the worker's tests run on main's packages linked into its worktree, with none installed, and the box's free disk is about what it was before the brief: no screen shows it.

Given a lane owner whose lane branch changed its lockfile from main's, When it briefs a worker in a new worktree of the lane with a ticket whose tests need its packages, Then the worker installs its own packages with its repository's install command before its tests run, and main's packages are as they were: no screen shows it.

Given an operator whose main checkout was pulled to a new lockfile with no install since, a fixture that must be added to provide it, When a lane owner briefs a worker in a new worktree whose lockfile is main's new one, with a ticket whose tests need its packages, Then the worker installs its own packages with its repository's install command before its tests run: no screen shows it.

Given an operator whose main checkout is installing its packages, a fixture that must be added to provide it, When a lane owner briefs a worker in a new worktree whose lockfile is main's, with a ticket whose tests need its packages, Then the worker installs its own packages with its repository's install command before its tests run, and main's install ends as it would alone: no screen shows it.

Given a repository whose install writes into its installed packages' files, as a patch step does, and whose main checkout has its packages installed from the lockfile the lane branch also has, a fixture that must be added to provide it, When a lane owner briefs a worker in a new worktree of the lane with a ticket whose tests need its packages, Then the worker installs its own packages with its repository's install command before its tests run, and main's packages are as they were: no screen shows it.

Given a lane owner whose repository's tests keep a cache inside its installed packages, as a test runner's result cache, and whose main checkout has its packages installed from the lockfile the lane branch also has, with that cache, a fixture that must be added to provide it, When it briefs a worker in a new worktree of the lane with a ticket whose tests need those packages, Then the worker's tests run on main's packages linked into its worktree, and main's packages, their cache included, are as they were: no screen shows it.

Given a lane worker whose worktree has main's packages linked, and another lane whose worktree has them linked too, When the worker's owner briefs it with a ticket that adds a package, Then main's packages and the other lane's are as they were, the other lane's tests run, and the worker's tests run on its own install: no screen shows it.

Given a lane worker whose worktree has main's packages linked, a fixture that must be added to provide it, When the operator pulls main to a new lockfile, then installs main's packages again, Then the worker's tests run on the packages its worktree had: no screen shows it.

Given a lane owner that parked its idle worker, whose park removed the main packages linked in its worktree, When the owner sends the worker its next brief, Then the worker's tests run on main's packages linked again, with none installed: no screen shows it.

Given an octo-lite contributor's change to any feature that runs in a lane, and a repository whose main checkout has its packages installed, a fixture that must be added to provide it, When a lane agent, or a wrapper or hook it runs, does its lane's work in the lane's worktree, then installs, adds, or removes packages there, Then every file of the main checkout, its installed packages included, is as it was: no octo-lite feature lets a lane's work write a main checkout's files (why): no screen shows it.

Given a lane owner whose idle worker's worktree has its packages installed, When the owner parks the worker, Then the node_modules folders Git ignores in that worktree are gone, and every other file in it is unchanged: no screen shows it.

Given an operator whose idle agent works in the box's main checkout of a repository, on its main branch, When the operator parks that agent, Then the main checkout keeps its node_modules folders: no screen shows it.

Given an operator whose idle agent works in a live install clone, such as octo-lite's own, When the operator parks that agent, Then the install clone keeps its node_modules folders: no screen shows it.

Given a lane owner whose idle worker's worktree is also the working folder of another live agent, When the owner parks the worker, Then the worktree keeps its node_modules folders: no screen shows it.

Given a lane owner idle at a spec review whose prototype runs from its worktree for that review, When the operator parks the owner, Then the worktree keeps its node_modules folders: no screen shows it.

Given a lane owner parked at a human gate, whose lane branch changed its lockfile from main's and whose park removed its worktree's node_modules folders, When a review hand-off resumes it, then it restarts its prototype, Then it installs the packages again with its repository's install command before the restart, and the prototype runs: no screen shows it.

Given a lane owner that parked its idle integrator between two integration rounds, on a lane branch that changed its lockfile from main's, whose park removed the integration worktree's node_modules folders, When the owner sends the integrator its next round, Then the integrator installs the packages again with its repository's install command before it runs the repository's checks, and the checks run: no screen shows it.

Given an operator with a finished lane whose owner and worker have each made temporary files, and another lane running, When the operator closes the finished lane's space, Then no scratch folder of the finished lane's agents is left, and the other lane's agents keep theirs: no screen shows it.

Given an operator with a finished lane whose PR merged and whose worktree holds no uncommitted work, When the operator tears down the lane, Then the lane's worktree is gone, and its repository's main checkout is unchanged: no screen shows it.

Given an operator with a finished lane whose worktree holds uncommitted work, When the operator tears down the lane, Then the worktree is kept with that work, and the operator's report of the lane's close names it: no screen shows it.

Given a lane worker that draws frames from a recording to read it and writes a report of what it read, When the lane closes, Then the lane's archived notes hold the worker's report and none of those frames: no screen shows it.

Given an octo-lite contributor's change to any feature that removes files or folders on the box, and another lane whose agent has files of its own in use, a fixture that must be added to provide it, When an agent, wrapper, or hook runs that removal, Then the removal takes only what its own lane or agent made, and the other lane's files and anything a live process uses are kept: no octo-lite feature removes another lane's or agent's files, or anything in use (why): no screen shows it.

Given an operator on a box whose disk is just under 85% full, a fixture that must be added to provide it, When a lane agent runs a command that fills it past 85%, Then the operator gets one message saying how full the disk is and how much is free, and naming the folders holding the most of it, each with its size: no screen shows it.

Given an operator told that its box's disk is past 85% full, When lane agents run more commands while the disk stays under 90% full, Then that one message is the only disk message the operator has: no screen shows it.

Given an operator told that its box's disk is past 85% full, When a lane agent runs a command that fills it past 90%, Then the operator gets one more message saying how full the disk is and how much is free, and naming the folders holding the most of it, each with its size: no screen shows it.

Given an operator told that its box's disk is past 90% full, When the disk is freed to under 80% full, then a lane agent runs a command that fills it past 85% again, Then the operator gets a new message saying how full the disk is: no screen shows it.

Given an agent in a Herdr session with no operator, on a box whose disk is just under 85% full, a fixture that must be added to provide it, When the agent runs a command that fills it past 85%, Then the agent is told, beside that command's result, how full the disk is and how much is free: no screen shows it.

Given a lane agent on a box whose disk is past 90% full, a fixture that must be added to provide it, When the agent runs a command, Then the command runs and its result reaches the agent as it would without the warning, and the warning removes nothing: no screen shows it.

Modular boundaries

herdr-spawn owns giving each agent its scratch folder, and herdr-close owns removing it at a close and removing a parked agent's packages. The caller-facing seam is the TMPDIR each agent's tab carries, which every program the agent runs reads for where its temporary files go. Direction is self-contained: the wrappers extend their own spawn, close, and park, and agents' programs depend on TMPDIR as they do on any box; no role or skill names the folder's path. Observable scope: the scratch folders in the user's home folder and the packages in a parked agent's worktree.

The role contracts of the agents that work in a lane worktree own each agent's choice, where it installs, to link main's packages or install its own. The caller-facing seam is the node_modules folder beside each lockfile in the agent's worktree, which every program the repository runs reads as its installed packages. Direction is external-provider: the choice reads the main checkout's lockfile and npm's record of its install there, and writes nothing there; nothing depends on which way it went. Observable scope: the packages in an agent's own worktree.

octo-lite's command-time hook owns checking the disk after each shell command and sending the warning. The caller-facing seam is the message the operator's pane receives, or, with no operator, the line beside the agent's command. Direction is external-provider: the hook depends on herdr-say and the session's operator.toml; nothing depends on the warning. Observable scope: the operator's messages and the agent's command line.

Scratch

herdr-spawn gives each agent it starts a scratch folder of its own, on disk in a folder of octo-lite's own at the top of the user's home folder, created empty, and exports it as TMPDIR into the agent's tab, as it exports the caller's HOME. Only that user can write there, so no other user of the box can make, read, swap, or redirect an agent's folder. The folder's name is drawn from the agent's Herdr session and agent name. Its path is short, since a browser puts its socket under TMPDIR and fails to start once that path is too long: Chromium starts only while TMPDIR is 62 characters or fewer. On a box whose home folder's path is 15 characters or fewer, such as /home/admin, the scratch folder's path leaves a program at least 30 of those characters to nest its own temporary folders in, as a parallel test suite's per-unit folders do. It is not in /tmp, which every user of the box shares, nor in the user's runtime folder, which is memory, nor in the user's cache folder, whose path is too long. Every program that puts its temporary files where TMPDIR says, as mktemp, Python's tempfile, and Node's os.tmpdir do, puts them there, so the test suites, browsers, and recordings an agent runs leave their temporary files in its folder.

herdr-close removes the scratch folder of each agent in the tab or space it closes, once it has stopped the processes started there. Agent names repeat across Herdr sessions, so a close removes only its own session's folders. A park closes nothing, so a parked agent keeps its folder, and its resume in the same pane finds it as it was, as a server the park kept running needs. An agent resumed in a new tab, as one whose pane was gone, gets an empty scratch folder again under its old name.

An agent writes its temporary files under $TMPDIR, never at a path of its own in /tmp, and keeps there anything it can make again, such as frames drawn from a recording to read it. What must outlive the agent goes where it is kept: a report in the lane's notes, work in its worktree and the PR. The role contracts say so where agents write.

An agent started before its box had this has no scratch folder, and its close removes nothing more than it did, so a box updates octo-lite whenever it is ready, with nothing to migrate. An agent whose scratch folder an earlier octo-lite put in the user's cache folder keeps it while it runs, and herdr-close removes it there at that agent's close, so no scratch folder waits on the box owner to remove it. Nothing sweeps /tmp: a folder left there before the update stays until the box owner removes it.

Shared packages

Before an agent installs packages in a worktree of its own lane, as parking counts one, at its start or once resumed from a park, it decides, for each package-lock.json Git tracks there with no node_modules folder beside it, whether to link main's packages or install its own. It links only when the main checkout, its worktree on the main branch, has the same lockfile byte for byte at the same path and a node_modules folder beside it, and no case below makes linking dangerous. It links by making the worktree's node_modules a folder of hard links to main's files, so its packages are installed with nothing downloaded and almost no disk taken. The decision is the agent's, at the point it installs: no wrapper links packages or checks for it, and the role contracts of the agents that work in a lane worktree carry this recipe where they install.

Right after linking, the agent removes from the linked folder every folder at its top whose name starts with a dot, but .bin, which takes only its own links: tools keep caches there that they rewrite in place, as a test runner's result cache under .vite is, and through a hard link that write would land in main's. A tool then makes its cache afresh, of the worktree's own files.

In each of these cases linking is dangerous, and the agent installs its own packages with its repository's install command, as the target AGENTS.md names it:

Main's install is stale: npm's record of its last install there is missing or older than main's lockfile, as after a pull with no install since, so main's folder holds packages the lockfile does not name.

Main's install is mid-update: an install runs in the main checkout now, so main's folder may be half removed or half written.

The repository's install writes into installed packages' files: its package.json runs a script at install, or its install command adds a step after the package manager's own that writes into node_modules, such as a patch or generate step, and in a linked folder that write lands in main's files. A step that writes elsewhere, as a browser download into the user's cache does, is no such case.

Once linked, before the agent adds, removes, or updates a package, or runs any install, rebuild, or other step that writes into installed packages' files in that folder, such as a generate step, it removes the linked folder, which takes only its own links, then installs its own: an install in a linked folder rewrites npm's record of the install in place, and through a hard link that write lands in main's. A link that fails partway is removed the same way, and the agent installs its own.

The folder is the worktree's own, of the same files on disk as main's, never a link to main's folder. Git ignores it as it ignores any installed packages. A link to main's folder would let a worktree's clean install empty main's, since it removes what the folder holds, and Git would not ignore it as a folder. When main installs again, as after a pull, the worktree keeps the files it had, so a lane already running keeps working on them.

An agent whose worktree has its packages, linked or its own, runs its install command only once its lockfile changes, removing a linked folder first as above. Linking only adds a folder the worktree lacks, and removing one takes only the worktree's own links: neither writes in the main checkout.

A lane only reads a main checkout: its work, installs and tests and builds included, writes in its own worktrees, as every octo-lite feature's does (rule), since a main checkout serves every lane and the box's installed tools, and one lane's write there breaks the rest. The install's after-pull step, which herdr-spawn runs when octo-lite's own clone has moved, is octo-lite's upkeep of its own install clone for the operator, not a lane's work.

Parking

Parking an agent also removes the node_modules folders Git ignores in its worktree, the folder it works in, since they are most of an idle lane's disk, and its resume links main's again or its repository's install command restores them. Only installed packages go: every other file, tracked or not, stays.

Only a worktree of the agent's own lane counts: a Git linked worktree not checked out on its repository's main branch. A box's main checkouts and its live install clones stay on main and serve every lane and the box's installed tools, so they keep their packages. A worktree that a live process other than the parked pane's shell still has as its working folder once the park has ended the agent, such as another live agent or a server the parked agent left running, keeps its packages too, since that process may be using them.

A resumed agent that finds its packages gone links main's again or installs its own, as shared packages decides, before it runs anything that needs them, such as its tests or the prototype. The role contracts of the agents that work in a lane worktree say so where they resume, since each works in a worktree its park may free, an integrator in the lane's integration worktree between its rounds.

Closing an agent removes no packages: a closed worker's worktree goes whole once its commits are integrated, and the lane's own worktree goes at lane close.

Lane close

At teardown the owner removes its workers' worktrees (teardown), and the operator, once it has closed the lane's space or owner tab, removes the lane's own worktree, the one it added at lane start. It removes it with Git's worktree remove, which keeps a worktree holding uncommitted work, and its report of the lane's close names a worktree so kept. Closing the lane's space or owner tab removes the scratch folder of every agent it closes, so a finished lane leaves only its archived record, hand-off log, and notes.

Disk warning

After each shell command any agent runs, octo-lite's command-time hook also reads how full the box's disk is, as df shows it for the root filesystem. The read is cheap and needs no timer or service: the commands that fill the disk are what check it.

When the disk is 85% full or more, the session's operator, the pane in its operator.toml, gets one message by herdr-say, and at 90% one more. Each says how full the disk is and how much is free, names the folders holding the most of it, each with its size, and says that nothing was removed and that each lane frees only what it made. Each level is told once per session until the disk is back under 80% full; then each is told again the next time the disk passes it.

In a session with no operator, the agent whose command found the disk past a level is told instead, in that command's line.

The warning only informs, as every hook octo-lite registers does (rule): it never removes, blocks, or stops anything, and the operator decides what to free and asks the lanes holding it. A failed check or send adds nothing, and the command and its result are as they would be without it.

Not built

octo-lite keeps no per-lane disk budget and has no disk command: scratch folders and packages end with the agent that made them, and the warning names what holds the disk. It sweeps nothing: no /tmp sweep, no cache cleaning, and no other lane's files, so every removal here is of what its own lane or agent made, as every octo-lite cleanup's is (rule), since a sweep by guesswork can delete a live lane's tree mid-test. It removes no build output, since only installed packages have one restore every repository names. It links only npm's packages: pnpm's store already links each worktree's packages to one copy on disk, and a build folder, such as Cargo's, is built, not installed, and goes unshared.

Install: the installer links and registers nothing new for this, since the wrappers and the hook it already installs carry it, so every install run still passes as the first (rule).
